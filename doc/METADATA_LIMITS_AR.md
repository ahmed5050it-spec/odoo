# ما الذي لا يمكن الحصول عليه من ميتاداتا Odoo المدمجة؟
# (Limits of ir.model / ir.module / ir.actions / ir.ui.* metadata)

> الوثيقة السابقة (`REVERSE_ENGINEERABLE_FROM_CODE_AR.md`) بيّنت ما **يُعكَس** من الكود.
> هنا السؤال المعاكس والدقيق: ميتاداتا Odoo المدمجة (`ir.model`, `ir.model.fields`,
> `ir.module.module`, `ir.actions.*`, `ir.ui.menu`, `ir.ui.view`) تلتقط **البنية
> والتصريحات** — فما الذي **لا** تلتقطه؟
>
> الجواب باختصار: **الميتاداتا تعرف «ما يوجد» و«توقيعه»، لا «ما يفعله».** تعرف أن حقلاً
> محسوب وعلى أيّ دالة، لا **منطق** الحساب. مبنية على فحص `ir_model.py` و`ir_actions.py`.

---

## 1. القاعدة: تصريح (Declaration) ≠ تنفيذ (Implementation)

```
   ما تلتقطه الميتاداتا                ما لا تلتقطه
   ──────────────────                ────────────
   الهيكل: نماذج، حقول، أنواع          منطق الأعمال: أجسام الدوال
   العلاقات (m2o/o2m/m2m)             الخوارزميات والآثار الجانبية
   التصريحات: compute='_x' (اسم)      جسم الدالة _x (الدلالة)
   العروض، الإجراءات، القوائم          سلوكها وقت التشغيل
   تصريحات الأمان (ir.rule)           فحوص الوصول البرمجية (sudo/check)
```

**دليل من الكود:** `ir.model.fields` يخزّن:
- `compute = fields.Text` ← **اسم** دالة الحساب، لا جسمها.
- `depends = fields.Char` ← أسماء الحقول المعتمَدة كنصّ، لا كيفية استخدامها.
- `related`, `store`, `ttype`, `relation` ← توقيع الحقل، لا سلوكه.

و`ir.actions.server.code = fields.Text` ← بايثون **كنصّ مبهم**؛ الميتاداتا لا «تفهم» أثره.

## 2. ما الذي لا يُستخرَج من الميتاداتا — مصنّفاً

### ٢.١ منطق الأعمال ودلالة الدوال ✗ (الأهم)
- **جسم دوال الحساب** (`@api.depends('a','b') def _compute_x`): الميتاداتا تعرف الاسم
  والاعتماديات، لا **المعادلة** (كيف يُحسب `amount_total`).
- **القيود** (`@api.constrains`): تعرف أن هناك قيداً، لا **شرط** الرفض.
- **onchange / دوال الأزرار** (`action_confirm`, `action_post`): توقيع فقط، لا أثر.
- **default الديناميكي** (`default=lambda self: ...`): مرجع دالة لا قيمة.

### ٢.٢ الآثار الجانبية بين النماذج ✗
- أن «تأكيد `sale.order` يُنشئ `stock.picking` و`account.move`» **ليس في أيّ علاقة
  ميتاداتا** — إنه منطق في `action_confirm()` (بايثون). الميتاداتا ترى الحقول، لا
  **سلاسل المستندات** (انظر `PRIMARY_SUPPORT_INTEGRATION_AR.md`).

### ٢.٣ كود الأتمتة والإجراءات الخادمية ✗/◐
- `ir.actions.server.code` و`base.automation` تُخزَّن كـ**نصّ**؛ تستطيع قراءته لكن
  الميتاداتا لا تُهيكِل أثره (أيّ نماذج يكتب، أيّ شروط).

### ٢.٤ الواجهة الأمامية (JS / OWL / web client) ✗
- سلوك العميل (مكوّنات OWL، JS، حِزم الأصول) في ملفات `static/`، **خارج ميتاداتا
  بايثون** تماماً. `ir.ui.view` يخزّن XML/QWeb، لا منطق JavaScript.

### ٢.٥ منطق QWeb الديناميكي ◐
- القالب في `ir.ui.view` (نصّ)، لكن نتيجة `t-if`/`t-esc`/`t-foreach` **وقت تشغيل** على
  بيانات حقيقية — ليست في الميتاداتا.

### ٢.٦ البيانات الفعلية والحالة (Runtime state) ✗
- الميتاداتا = **المخطّط (schema)**، لا **المحتوى**. السجلات الفعلية، الأرصدة،
  المعاملات، حالة سير العمل — تحتاج **قاعدة بيانات حيّة** (شغّلها عبر مهارة `run-odoo`).

### ٢.٧ خصائص الأداء وأنماط الاستعلام ✗
- الفهارس جزئياً في الميتاداتا (`index`)، لكن **أنماط الاستعلام، N+1، الزمن، عدد
  الاستعلامات** لا تُعرَف إلا بالتشغيل والـ **profiler** (`PROFILING_SUBSYSTEM.md`).

### ٢.٨ التكاملات الخارجية ✗
- استدعاءات HTTP/API لخدمات خارجية، مكتبات الدفع، البريد — منطق في الكود، لا أثر له في
  الميتاداتا (سوى `external_dependencies` في المanifest كقائمة أسماء).

### ٢.٩ الأمان البرمجي (ما وراء التصريحات) ◐
- قواعد السجلّات (`ir.rule`) ونطاقاتها **في الميتاداتا** ✅، لكن:
  `sudo()`، `with_user()`، `check_access`, تجاوزات `_check_*` البرمجية ✗ — في الكود.

### ٢.١٠ النيّة / الـ«لماذا» ✗
- الاستراتيجية، المتطلّبات، سبب وجود الحقل/الموديول — قرارات بشرية، ليست في أيّ جدول
  (تأكيد للوثيقة السابقة).

### ٢.١١ ترتيب العمليات والمعاملات ✗
- تسلسل `create→write→unlink`، `savepoint`/`flush`، إدارة المعاملات — سلوك تشغيلي في
  الكود وطبقة `sql_db`، لا تصريح ميتاداتا.

## 3. الجدول: المصدر ↔ ماذا يلتقط ↔ ماذا يفوته

| المصدر (ميتاداتا) | يلتقط ✅ | يفوته ✗ |
|--------------------|---------|---------|
| `ir.model` | الكيانات (`_name`, `_table`, الوراثة) | لماذا وُجد، سلوكه |
| `ir.model.fields` | الحقول، الأنواع، العلاقات، **اسم** compute/depends | **منطق** الحساب، المعادلة |
| `ir.module.module` | الموديولات، الاعتماديات، الحالة | ما الذي يفعله الكود داخلها |
| `ir.actions.server` | وجود الإجراء + الكود **كنصّ** | أثر الكود المُهيكَل |
| `ir.actions.act_window` | الإجراء، النموذج، العرض | منطق دوال الأزرار |
| `ir.ui.menu` | شجرة القوائم | تدفّق المستخدم الفعلي |
| `ir.ui.view` | بنية XML/QWeb للعرض | منطق JS/OWL، نتيجة QWeb وقت التشغيل |
| `ir.rule` / `ir.model.access` | تصريحات الوصول | `sudo()`/الفحوص البرمجية |

## 4. كيف تُسدّ كل فجوة (المصدر البديل)

```
   ما يفوت الميتاداتا            كيف تحصل عليه
   ─────────────────            ─────────────
   منطق الدوال/الخوارزميات   ⟶  تحليل AST للكود (revres extract_module.py
                                 يعدّ الدوال؛ لقراءة المنطق: اقرأ المصدر)
   الآثار الجانبية والتدفّقات ⟶  تتبّع: --log-handler=odoo.sql_db:DEBUG +
                                 chatter (LOGS_AND_MESSAGES_*)
   البيانات والحالة          ⟶  قاعدة بيانات حيّة عبر مهارة run-odoo
                                 (odoo shell + JSON-RPC)
   الأداء وأنماط الاستعلام   ⟶  المعالِج (Profiler) — PROFILING_SUBSYSTEM
   الواجهة JS/OWL            ⟶  قراءة static/src/js + تشغيل المتصفّح
   النيّة/الاستراتيجية        ⟶  إنسان (وثائق أعمال، مقابلات)
```

> محرّك **revres** يسدّ جزءاً من الفجوة: `extract_module.py` يحلّل **AST** فيستخرج أسماء
> النماذج والحقول والعلاقات و**عدد** الدوال والمسارات — أكثر ممّا في الميتاداتا وحدها —
> لكنه أيضاً **لا يقرأ دلالة** الدوال؛ لذلك يتركها كـ«أسئلة مفتوحة» في كل بريف.

---

## 5. الخلاصة — جواب «ما لا يُحصَّل من الميتاداتا»

الميتاداتا المدمجة (`ir.*`) تعطيك **الهيكل العظمي الساكن**: النماذج، الحقول، العلاقات،
العروض، الإجراءات، القوائم، الموديولات، وتصريحات الأمان. **لا تعطيك:**

1. **منطق الأعمال** — أجسام دوال الحساب/القيود/الأزرار (تعرف الاسم لا الدلالة). ✗
2. **الآثار الجانبية بين النماذج** — سلاسل المستندات (sale→stock→account). ✗
3. **سلوك الواجهة الأمامية** — JS/OWL ونتيجة QWeb وقت التشغيل. ✗
4. **البيانات والحالة الفعلية** — تحتاج قاعدة حيّة لا مخطّطاً. ✗
5. **الأداء وأنماط الاستعلام** — تحتاج profiler. ✗
6. **التكاملات الخارجية** — استدعاءات API في الكود. ✗
7. **الأمان البرمجي** — `sudo()`/الفحوص (عكس `ir.rule` التصريحية). ◐
8. **النيّة والاستراتيجية** — قرارات بشرية. ✗

القاعدة الذهبية: **الميتاداتا تصف «ما هو مُصرَّح»، لا «ما يُنفَّذ ولا ما يحدث وقت
التشغيل».** لذا الهندسة العكسية الكاملة تحتاج ثلاث طبقات: **الميتاداتا** (الهيكل) +
**تحليل الكود/AST** (المنطق، عبر revres) + **التشغيل الحيّ** (الحالة والأداء، عبر run-odoo
والـ profiler) — والميتاداتا وحدها تغطّي الطبقة الأولى فقط.
