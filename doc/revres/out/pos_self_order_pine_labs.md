# pos_self_order_pine_labs — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from

The **POS Self Order Pine Labs** module (`pos_self_order_pine_labs`, category
*Sales/Point Of Sale*, `application=False`, author *Odoo IN Pvt Ltd*, LGPL-3) is
a thin, **auto-installed** bridge that "allows customers to pay using the Pine
Labs POS Terminal" from the **self-order kiosk**. It sits between two parents —
`pos_pine_labs` (the Pine Labs terminal integration) and `pos_self_order` (the
customer-facing kiosk/QR app) — and adds **no new model and no new fields**: it
overrides two `pos.payment.method` methods, exposes **two public jsonrpc routes**
(poll status / cancel), and patches the kiosk OWL app. ~108 Python LOC, 0 XML,
3 JS files. It owns no value logic of its own — the actual order is created and
the tender recorded by the host `pos_self_order` plumbing; this module only wires
the **Pine Labs handshake** into that flow.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `pos_self_order` | The kiosk self-order app. Provides the `/kiosk/payment/<config>/kiosk` route, the `_payment_request_from_kiosk` extension hook, `_load_pos_self_data_domain`, `pos.order._send_payment_result` (PAYMENT_STATUS bus), and the public OWL `PaymentPage`/`SelfOrder` it patches. |
| `pos_pine_labs` | The Pine Labs terminal. Provides `use_payment_terminal='pine_labs'`, the credential fields, and `pine_labs_make_payment_request` / `pine_labs_fetch_payment_status` / `pine_labs_cancel_payment_request` (UploadBilledTransaction / GetCloudBasedTxnStatus / CancelTransactionForced against the Pine Labs cloud; INR/paisa). |

**Adds on top:** kiosk self-payment via the Pine Labs terminal — a `_payment_request_from_kiosk` override, a `_load_pos_self_data_domain` override that exposes the terminal to the kiosk client, two poll/cancel routes, and a JS `PineLabs` polling handler.

## Behavior & Surfaces

- **Routes (2, public jsonrpc):** `/pos-self-order/pine-labs-fetch-payment-status/`
  and `/pos-self-order/pine-labs-cancel-transaction/`, both subclassing
  `PosSelfOrderController` and gated by `_verify_pos_config(access_token)`
  (resolves the config by token, drops to `self_ordering_default_user_id`;
  `NotFound` if the order doesn't belong to the config).
- **The handshake (code-read):** the **trigger** is the host's
  `/kiosk/payment/<config>/kiosk`, not these routes. The JS posts the serialized
  order there; the host runs `process_order` (creates the `pos.order` in the open
  session) and calls `payment_method._payment_request_from_kiosk(order)`. This
  module's override (only when `use_payment_terminal == 'pine_labs'`) builds
  `amount = order.amount_total * 100` (**paisa**, 1 INR = 100 paisa),
  `transactionNumber = '<config>/Order/<id>/<uuid4>'`, calls
  `pine_labs_make_payment_request` (→ `plutusTransactionReferenceID`) and stamps
  `payment_ref_no`.
- **Settlement (code-read):** the client polls
  `pine-labs-fetch-payment-status` → `pine_labs_fetch_payment_status`
  (GetCloudBasedTxnStatus). On **`"TXN APPROVED"`** the route writes a
  `pos.payment` via `order.add_payment({amount, transaction_id=TransactionLogId,
  payment_method_authcode=ApprovalCode, card_brand=Card Type, card_no=last 4,
  pine_labs_plutus_transaction_ref, …})`, calls `action_pos_order_paid()` and
  `_send_payment_result('Success')` — which fires
  `config._notify('PAYMENT_STATUS')` and sends the receipt + kitchen order.
  Cancel → `pine_labs_cancel_payment_request` (CancelTransactionForced).
- **Exposure (code-read):** `_load_pos_self_data_domain` OR-extends the public
  data domain so Pine Labs methods reach the kiosk client **only** when
  `self_ordering_mode == 'kiosk'`.
- **Frontend (gap #3):** 3 JS files, **0 OWL components**, bundle
  `pos_self_order.assets`. A non-OWL `PineLabs` class (`pine_labs.js`) +
  `PaymentPage.prototype` / `SelfOrder.prototype` patches. `PineLabs.startPayment`
  posts to `/kiosk/payment`, then `paymentPolling()` hits the status route every
  **5 s** (`REQUEST_TIMEOUT`), correlating on `plutusTransactionReferenceID` /
  `paymentRefNo` held in `localStorage`; a **~110 s** inactivity timer auto-fires
  the cancel route. Client logic, not in Python metadata.
- **Integrations (gap #7):** **0 direct call-sites here** — the actual HTTPS calls
  to the Pine Labs cloud (`call_pine_labs`) live in `pos_pine_labs`.

## Value-Configuration Classification

**Primary model: Value Chain (transform).** `pos_self_order_pine_labs` is a thin
payment-terminal bridge inside the in-store self-service checkout: its only act
is collecting the customer's tender on the Pine Labs terminal and completing a
`pos.payment` on the kiosk `pos.order`. It inherits the `point_of_sale →
pos_self_order` **chain / primary** sell classification. It has a **network**
overtone (mediating between the diner and the Pine Labs cloud via public
poll/cancel routes), but the value logic it completes is the chain sell. *(The
host `pos_self_order` is itself classed `network` as the mediating self-order
channel; this child adds only a tender device to that channel's kiosk mode, so
it reads with the underlying POS sell.)*

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — capturing payment to close the
kiosk sale is part of selling/closing the counter transaction, mirroring the POS
parents rather than treasury/AR (APQC 9.0), realized downstream by the base POS
session closing entry.

## Fit-to-Standard & How to Drive It

**Standard out-of-box:** kiosk order paid on a Pine Labs terminal
(`use_payment_terminal='pine_labs'`); order creation + terminal request in one
`/kiosk/payment` round-trip; 5 s status polling until `TXN APPROVED` →
auto `pos.payment` + order-paid; ~90–110 s inactivity auto-cancel; terminal
auto-exposed to the kiosk only in kiosk mode.

**Common gaps:** **INR-only** (parent constraint); completion depends on the
polling tab staying alive; no module-specific reconciliation/reporting beyond the
`pos.payment`; refunds/partial captures not in this bridge; depends on
`pos_pine_labs` reaching the Pine Labs cloud.

```python
# Pine Labs methods on kiosk configs
env['pos.payment.method'].search([('use_payment_terminal','=','pine_labs')]) \
    .mapped(('name','pine_labs_merchant','pine_labs_test_mode','config_ids.self_ordering_mode'))

# kiosk-sourced Pine Labs tenders
env['pos.order'].search([('source','=','kiosk'),
    ('payment_ids.payment_method_id.use_payment_terminal','=','pine_labs')], limit=5) \
    .mapped(('name','state','amount_total'))
```

Open a kiosk POS (`self_ordering_mode='kiosk'`) with a Pine Labs method and place
an order to trigger `PaymentPage.startPayment → PineLabs.startPayment`.
