# cloud_storage — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Cloud Storage** module (`cloud_storage`, category *Technical Settings*,
`application=False`) is a **provider-agnostic framework** for offloading chatter
attachment blobs from the Odoo filestore to an external cloud object-storage
service (Google GCS, Azure Blob Storage, or similar). It is thin by design —
320 Python LOC, no new ORM models — and is intended to be paired with a concrete
provider module (e.g. `cloud_storage_google`) that implements the abstract hooks
it defines. The Odoo server is removed from both the upload and the download data
path; only small metadata calls go through it.

## Behavior (code-read)

### Upload flow (browser → cloud, bypassing Odoo)

When the browser uploads a file larger than `cloud_storage_min_file_size`
(default **20 MB**) via the chatter:

1. The OWL `AttachmentUploadService._upload` patch detects the threshold,
   stores the real `File` object in `uploadingCloudFiles`, and sends an **empty
   stub file** body to the Odoo upload endpoint with `cloud_storage=true`.
2. `CloudAttachmentController.mail_attachment_upload` creates an `ir.attachment`
   record (with empty body) via `super()`, then calls
   `attachment._generate_cloud_storage_upload_info()` and appends `upload_info`
   to the response.
3. The browser's `_processLoaded` patch opens an `XMLHttpRequest.PUT` directly
   to the cloud provider URL using the returned `method`, `url`, and optional
   `headers`. The Odoo server is never in the upload data path.

### Download flow (redirect, not proxy)

`ir.attachment._to_http_stream` — called by `/web/content/<id>` — checks
`type == 'cloud_storage'` and returns `Stream(type='url', url=signed_url)` with
`max_age = time_to_expiry - 10` seconds. The Odoo server issues a **302
redirect** to a time-limited signed URL; the browser downloads directly from
the cloud provider.

### Provider-switch guard

`res.config.settings.set_values` calls `_check_cloud_storage_uninstallable()`
before allowing a provider change, preventing orphaned blobs. If the provider is
changed and existing blobs cannot be migrated, the switch is blocked. The
migration helper `_migrate_remote_to_local` downloads each blob via
`requests.get` and rewrites the attachment as `type='binary'` / `raw=content`.

### Model exclusions

`_get_cloud_storage_unsupported_models` excludes models inheriting
`mail.thread.main.attachment` (the Documents app attachment model) and
`documents.mixin` from cloud offload — these models read attachment bytes
directly in business code and cannot tolerate the cloud redirect.
