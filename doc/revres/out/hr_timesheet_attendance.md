# hr_timesheet_attendance — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + targeted code-read of the report model.*

The **Timesheets/attendances reporting** module (`hr_timesheet_attendance`,
category *Human Resources/Attendances*, `application=False`) is a thin,
**auto-installed bridge** that appears whenever both `hr_timesheet` and
`hr_attendance` are present. Its sole purpose is **reconciliation**: for each
employee on each day it compares the hours the employee was *present*
(attendance) against the hours they actually *logged on timesheets*, and flags
the difference — in both hours and labour cost. It owns no business object of its
own; its single model is a read-only Postgres SQL view.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `hr_attendance` | Source of recorded presence (`hr_attendance.worked_hours`, `check_in`). |
| `hr_timesheet` | Source of logged time (`account.analytic.line.unit_amount` on project lines) and the security groups. |

**Adds on top:** one aggregate analysis report (`hr.timesheet.attendance.report`),
its search/pivot/graph views and menu, four record rules, and an `ir.ui.menu`
patch that hides the menu from non-timesheet users. `auto_install=True` means it
is invisible to the end user as a separate app — it just lights up the
*Timesheets / Attendance Analysis* report.

## Data Model (the ERM)

| Element | Detail |
|---------|--------|
| `hr.timesheet.attendance.report` | `_auto=False` SQL view, 9 fields, no table. |
| `employee_id` | Many2one → `hr.employee` (the subject of each row). |
| `company_id` | Many2one → `res.company` (multi-company scope). |
| `date` | Day bucket (attendance truncated in the employee's calendar tz). |
| `total_attendance` / `total_timesheet` / `total_difference` | Float hours: present, logged, and (present − logged). |
| `timesheets_cost` / `attendance_cost` / `cost_difference` | Same three quantities valued at `hr_employee.hourly_cost`. |

The view's data is sourced (read-only, never written back) from `hr_attendance`,
`account_analytic_line`, `hr_employee.hourly_cost` and the
`resource_calendar.tz` reached via `hr_version.resource_calendar_id`.

## Behavior & Surfaces

The whole module is one SQL view built in `init()` (`report/hr_timesheet_attendance_report.py`):

- **UNION ALL of two sources.** Attendance rows pull `worked_hours` (id negated to
  avoid PK collision, `check_in` cast to a date *in the employee's
  resource_calendar timezone*); timesheet rows pull `unit_amount` from
  `account_analytic_line` where `project_id IS NOT NULL`. Both are limited to
  dates `<= CURRENT_DATE`.
- **Aggregation.** The outer query `GROUP BY employee_id, date, company_id,
  emp_cost` and sums each side. `total_difference = sum(attendance) −
  sum(timesheet)` is the headline KPI — the graph view plots *only* this measure.
- **Cost valuation.** Each hours sum is multiplied by `emp_cost`
  (`hr_employee.hourly_cost`), with `NULLIF(...,0)` blanking zero cells, turning
  the hours gap into a labour-cost variance.
- **Sort override.** `formatted_read_group` defaults `date:` groupings to DESC so
  the most recent days appear first.
- **Visibility.** `ir.ui.menu._load_menus_blacklist` (`models/ir_ui_menu.py`)
  hides the report menu from users lacking `hr_timesheet.group_hr_timesheet_user`.

**Frontend (static):** none. `extract_frontend` reports 0 JS files and no OWL
components, registry adds, patches or asset bundles — the UI is purely
declarative search + pivot + graph XML reusing the inherited `timesheet_uom`
widget. All logic lives in SQL.

**Security:** four record rules — multi-company scope; a user sees only their own
employee row; approvers (`group_hr_timesheet_approver`) and timesheet managers
(`group_timesheet_manager`) see all rows.

## Value-Configuration Classification

**value_model = support**, **activity_class = support**. This is a Stabell &
Fjeldstad *support* configuration: an HR/firm-infrastructure control activity with
no business object and no delivered output. It does not convert demand into a
product — it only measures and values a discrepancy between two existing record
streams. It is read-only analytics layered on top of the primary timesheet and
attendance flows.

## How to Drive It

```python
# rows: hours present vs logged per employee/day
env['hr.timesheet.attendance.report'].search([], limit=5).read(
    ['employee_id','date','total_attendance','total_timesheet','total_difference'])
# aggregate the gap and its cost by employee
env['hr.timesheet.attendance.report'].formatted_read_group(
    [], ['employee_id'], ['total_difference:sum','cost_difference:sum'])
```
```sql
-- the underlying view
SELECT employee_id, date, total_attendance, total_timesheet, total_difference
FROM hr_timesheet_attendance_report ORDER BY date DESC LIMIT 5;
```
