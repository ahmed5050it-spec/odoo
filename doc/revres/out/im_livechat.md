# im_livechat — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + code-read of `addons/im_livechat/`, narrated per
> `PROMPT.md`. Odoo 19.0.*

The **Live Chat** module (`im_livechat`, category *Website/Live Chat*,
`application=True`) lets website visitors talk to operators (or chatbots) in real
time. It is **not** auto-installed and builds directly on the messaging
subsystem: it depends on `mail` (so a live chat is just a `discuss.channel` of
`channel_type='livechat'`, messages stay `mail.message`, delivery rides the
**bus**), plus `rating`, `digest`, and `utm`. Its center of gravity is the pair
`im_livechat.channel` (the chat button/config + the operator pool) and the
`discuss.channel` livechat extension (the live session, ~31 added fields). It is
**frontend-heavy**: 53 routes and 102 JS files, with a Shadow-DOM OWL widget
embeddable on non-Odoo sites.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `mail` | The whole runtime: `discuss.channel`/`discuss.channel.member`, `mail.message`, `mail.guest` (anonymous visitors) and the **bus** real-time push. |
| `rating` | Per-session satisfaction (`rating.mixin` on the session, `rating.parent.mixin` on the channel) — the good/ok/bad feedback. |
| `digest` | Periodic digest KPIs (rating, conversation count, response time). |
| `utm` | Campaign/source attribution; `chatbot.script` inherits `utm.source.mixin`. |

**Adds on top:** an operator-matching/routing engine, channel rules
(URL/country/auto-popup), scripted chatbots with forward-to-operator hand-off,
conversation tags/notes/escalation, transcripts (email + PDF), and a live chat
analytics report.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`im_livechat.channel`** | Livechat Channel (button + operator pool) | 22 | `user_ids→res.users`, `rule_ids→im_livechat.channel.rule`, `channel_ids→discuss.channel` |
| **`discuss.channel`** *(extension)* | Live chat **session** | +31 | `livechat_channel_id→im_livechat.channel`, `livechat_operator_id→res.partner`, `chatbot_current_step_id→chatbot.script.step` |
| `im_livechat.channel.rule` | Display/auto-popup/hide rule | 8 | `channel_id→im_livechat.channel`, `chatbot_script_id→chatbot.script`, `country_ids→res.country` |
| `im_livechat.channel.member.history` | Per-session operator/visitor record | 26 | `channel_id→discuss.channel`, `partner_id→res.partner`, `rating_id→rating.rating` |
| `chatbot.script` / `.step` / `.answer` | Scripted automated operator | 7 / 10 / 5 | `script_step_ids→chatbot.script.step`, `operator_partner_id→res.partner` |
| `im_livechat.expertise` | Operator skill tag (routing) | 2 | `user_ids→res.users` |
| `im_livechat.report.channel` | Support Channel Report (SQL view) | 33 | `channel_id→discuss.channel`, `livechat_channel_id→im_livechat.channel` |

**Central models:** `im_livechat.channel` (config + agents) and the
`discuss.channel` livechat extension (the running conversation). The module is
**relational-heavy** — `Many2one` (35) and `Many2many` (25) dominate, reflecting
the visitor ↔ operator ↔ channel ↔ rating web. `im_livechat.report.channel` is a
read-only SQL-view analytics model, not a stored table.

## Behavior & Surfaces

- **Routes:** 53 — almost all `auth='public'` (visitors are anonymous
  `mail.guest`s). A `/im_livechat/*` + `/chatbot/*` set is **mirrored under
  `/im_livechat/cors/*`** so the widget works when embedded cross-origin; a few
  operator-only routes (`/session/update_*`, `/conversation/*`, transcript email)
  are `auth='user'`.
- **Operator matching (code-read, not in metadata):** `_get_operator` filters
  agents by **live presence**, `max_sessions`, and in-call state, then runs a raw
  SQL ranking over `im_livechat.channel.member.history` + RTC sessions and applies
  a **preference ladder** (same language → expertise → same country → least-active)
  with a 120 s anti-flood buffer and previous-operator stickiness.
- **Session lifecycle:** `/im_livechat/get_session` creates the
  `discuss.channel`, builds agent/visitor members, and `_broadcast`s to the
  operator over the bus; `_close_livechat_session` stamps `livechat_end_dt` when
  the visitor or last operator leaves; two `@api.autovacuum` crons GC empty/idle
  sessions.
- **Frontend:** a Shadow-DOM OWL app (`LivechatRoot` → `ChatHub` +
  `LivechatButton`), 11 backend OWL components, 21 patches into mail/discuss, and
  dedicated embed asset bundles (`assets_embed_external` / `assets_embed_cors`).
- **Security:** 15 ACLs, 3 record rules, 2 groups (operator `im_livechat_group_user`,
  manager `im_livechat_group_manager`); CHECK constraints enforce an operator on
  every livechat channel and `max_sessions > 0`.

## Value-Configuration Classification

**Primary model: Value Network (mediating technology).** `im_livechat` is a
network, not a chain: its value is **connecting** two populations — website
visitors and operators/chatbots — in real time over the bus, and its central
asset is the **matching/routing layer** (`_get_operator`: availability, language,
expertise, country, load). It runs the network *infrastructure-operation*
activity (provisioning + operating the chat service) and *promotion/contract*
activity (channel rules, auto-popup, chatbot gating). It is a **primary**
customer-service activity — it builds on `mail`/`discuss` + `bus` rather than
moving a document down a chain.

## APQC PCF Hint

**6.0 Manage Customer Service** — real-time customer-contact handling

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i im_livechat` database:

```python
# odoo shell
chans = env['im_livechat.channel'].search([])
print(chans.mapped('name'), chans.mapped(lambda c: c.available_operator_ids.mapped('name')))
sessions = env['discuss.channel'].search([('channel_type','=','livechat')], limit=5)
print(sessions.mapped(('name','livechat_status','livechat_outcome')))
# visitor entry point (operator matching):
#   curl -X POST .../im_livechat/get_session  {channel_id, persisted:false}  (auth=public, jsonrpc)
print(env['im_livechat.report.channel'].read_group([], ['duration:avg','rating:avg'], ['livechat_channel_id']))
```
