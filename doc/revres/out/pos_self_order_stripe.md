# pos_self_order_stripe — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from
> `extract_module.py` / `extract_frontend.py` + code-read of the model,
> controller, self-order JS, the injected SDK template & the test. Odoo 19.0.*

The **POS Self Order Stripe** module (`pos_self_order_stripe`, category
*Sales/Point Of Sale*, `application=False`, author *Odoo S.A.*, LGPL-3) is a
thin, **auto-installed** bridge that "allows customers to pay by Stripe" from the
**self-order kiosk** using a **Stripe Terminal reader**. It sits between
`pos_stripe` (the Stripe Terminal integration) and `pos_self_order` (the kiosk/QR
app) and adds **no new model and no new fields**: it overrides two
`pos.payment.method` methods, exposes **two public jsonrpc routes** (connection
token / capture), injects the **Stripe Terminal JS SDK** via a template, and
patches the kiosk OWL app. ~222 Python LOC, ~10 XML LOC, 3 JS files. Unlike the
Pine Labs / Razorpay siblings there is **no server polling** — the Stripe Terminal
SDK drives the reader client-side; the server only mints the intent and captures.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `pos_self_order` | The kiosk self-order app. Provides `/kiosk/payment/<config>/kiosk`, the `_payment_request_from_kiosk` hook, `_load_pos_self_data_domain`, `pos.order._send_payment_result` (PAYMENT_STATUS bus), `_verify_authorization`, and the `pos_self_order.index` template + OWL `PaymentPage`/`SelfOrder` it patches. |
| `pos_stripe` | The Stripe Terminal integration. Provides `use_payment_terminal='stripe'`, `stripe_serial_number`, and `stripe_connection_token` / `stripe_payment_intent` / `stripe_capture_payment` / `_stripe_calculate_amount` (talking to the Stripe API via the `'stripe'` `payment.provider`). |

**Adds on top:** kiosk self-payment via a Stripe reader — a `_payment_request_from_kiosk` override, a `_load_pos_self_data_domain` override exposing the terminal to the kiosk client, a connection-token route, a capture route with a server-side amount guard, the injected SDK `<script>`, and a JS `Stripe` SDK wrapper.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Notes |
|-----------------|-------------|--------:|-------|
| **`pos.payment.method`** *(inherit)* | POS Payment Methods, Stripe kiosk bridge | +0 | Adds **no fields**; adds 2 methods: `_payment_request_from_kiosk(order)` and `_load_pos_self_data_domain(data, config)` (`@api.model`). |

No own models, **no security rules, no groups, no backend views**. One data file,
`views/assets_stripe.xml`, **inherits `pos_self_order.index`** and injects
`<script src="https://js.stripe.com/terminal/v1/">` into `<head>` (it can't be an
asset because the URL has no `.js` suffix). The tender is realized as a base
`pos.payment` line via `order.add_payment(...)`.

## Behavior & Surfaces

- **Routes (2, public jsonrpc, `website=True`):**
  `/pos-self-order/stripe-connection-token/` and
  `/pos-self-order/stripe-capture-payment/`, subclassing `PosSelfOrderController`,
  gated by `_verify_authorization(access_token, '', {})`. (The parent Stripe
  methods require `group_pos_user`, met via the `self_ordering_default_user_id`
  the gate impersonates.)
- **The handshake (code-read) — two tokens, no poll:** (1) the **trigger** is the
  host's `/kiosk/payment/<config>/kiosk`; the JS posts the serialized order, the
  host runs `process_order` and calls `_payment_request_from_kiosk(order)` →
  `stripe_payment_intent(order.amount_total)`, which mints a PaymentIntent
  (`payment_method_types[]='card_present'`, `capture_method='manual'`) and returns
  it so the client gets `payment_status.client_secret`. (2)
  `stripe-connection-token` → `stripe_connection_token()` (Stripe
  `terminal/connection_tokens`); the SDK consumes its `.secret`
  (`onFetchConnectionToken`) to authenticate the reader, then discovers/connects
  it by `stripe_serial_number`.
- **Settlement (code-read):** `stripe-capture-payment` →
  `stripe_capture_payment(payment_intent_id)` (Stripe
  `payment_intents/<id>/capture`), finds the order by `(access_token, config_id)`
  (`Unauthorized` otherwise), then **re-validates server-side**:
  `float_is_zero(_stripe_calculate_amount(order.amount_total) -
  stripe_confirmation['amount'], …)` **and** `status == 'succeeded'`. Only then
  `order.add_payment({amount, payment_date, transaction_id=id,
  payment_status='succeeded', …})`, `action_pos_order_paid()`, and (kiosk)
  `_send_payment_result('Success')` (`config._notify('PAYMENT_STATUS')` + receipt
  + kitchen order). Mismatch → `_send_payment_result('fail')`. This
  amount-equality guard against a client-supplied `payment_intent_id` is the key
  integrity behavior.
- **Exposure (code-read):** `_load_pos_self_data_domain` OR-extends the public
  data domain so Stripe methods reach the kiosk client **only** when
  `self_ordering_mode == 'kiosk'`.
- **Frontend (gap #3):** 3 JS files, **0 OWL components**, bundles
  `pos_self_order.assets` + `pos_self_order.assets_tests`. A non-OWL `Stripe`
  class (`stripe.js`) wrapping the global `StripeTerminal` SDK +
  `PaymentPage.prototype` / `SelfOrder.prototype` patches. `Stripe.startPayment`:
  POST `/kiosk/payment` → `client_secret` + `savedOrder` → `connectReader()`
  (`StripeTerminal.create`, fetch connection token, discover + connect by serial)
  → `collectPaymentMethod` → `terminal.processPayment` →
  `capturePayment(intent.id, order)` → `stripe-capture-payment`. **No polling
  loop** — the SDK is event-driven; only the capture round-trip settles. A test
  tour (`static/tests/tours`) and a Python test exercise the flow.
- **Integrations (gap #7):** **0 direct call-sites here** — the Stripe API calls
  (`_send_api_request`) live in `pos_stripe`/the payment engine; the browser also
  talks directly to Stripe via the Terminal SDK.

## Value-Configuration Classification

**Primary model: Value Chain (transform).** `pos_self_order_stripe` is a thin
payment-terminal bridge inside the in-store self-service checkout: its only act
is collecting the customer's tender on a Stripe Terminal reader and completing a
`pos.payment` on the kiosk `pos.order`. It inherits the `point_of_sale →
pos_self_order` **chain / primary** sell classification. It has a **network**
overtone (mediating between the diner, the reader and the Stripe API via public
token/capture routes), but the value logic it completes is the chain sell. *(The
host `pos_self_order` is itself classed `network` as the mediating self-order
channel; this child adds only a tender device to that channel's kiosk mode.)*

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — capturing payment to close the
kiosk sale is part of selling/closing the counter transaction, mirroring the POS
parents rather than treasury/AR (APQC 9.0), realized downstream by the base POS
session closing entry.

## Fit-to-Standard & How to Drive It

**Standard out-of-box:** kiosk order paid on a Stripe Terminal reader
(`use_payment_terminal='stripe'`); order creation + card_present/manual
PaymentIntent in one `/kiosk/payment` round-trip; SDK reader connection
(connection token, discover/connect by serial) + client-side card collection;
manual capture with a **server-side amount-equality + `succeeded` guard** before
writing the `pos.payment`; PAYMENT_STATUS bus Success/fail; terminal auto-exposed
to the kiosk only in kiosk mode.

**Common gaps:** requires the Stripe Terminal `<script>` to load and a reachable
Stripe API (no offline charge); the reader serial must match
`stripe_serial_number`; refunds live in `pos_stripe.stripe_refund` (not exposed
to the kiosk); tip/over-capture isn't used from the kiosk path; a published
`'stripe'` `payment.provider` is required.

```python
# Stripe methods + reader serials on kiosk configs
env['pos.payment.method'].search([('use_payment_terminal','=','stripe')]) \
    .mapped(('name','stripe_serial_number','config_ids.self_ordering_mode'))

# kiosk-sourced Stripe tenders
env['pos.order'].search([('source','=','kiosk'),
    ('payment_ids.payment_method_id.use_payment_terminal','=','stripe')], limit=5) \
    .mapped(('name','state','amount_total'))
```

Open a kiosk POS (`self_ordering_mode='kiosk'`) with a Stripe method + reader
serial and place an order to trigger `PaymentPage.startPayment →
Stripe.startPayment`; or run
`addons/pos_self_order_stripe/tests/test_self_order_kiosk_stripe.py` (mocks
capture, asserts order state `paid`).

## Open Questions

- Exact OWL reaction to the `PAYMENT_STATUS` bus message vs the synchronous
  `capturePayment` return after the capture route already wrote the `pos.payment`.
- Handling if `terminal.processPayment` succeeds client-side but the capture route
  then fails the amount check (card authorized but not captured).
- Whether a non-kiosk (mobile) mode ever reaches the capture path — the success
  bus signal is gated on `kiosk` only.
- Reader-sharing / `fail_if_in_use` when two kiosks point at the same
  `stripe_serial_number` reader concurrently.
