The **Repairs** module (`repair`, category *Supply Chain/Inventory*,
`application=True`, v1.0) manages **repair orders** — the after-sales operation of
fixing or refurbishing returned or owned products by consuming spare parts and
re-producing the serviced good, optionally billing it. It is **not** auto-installed
and depends on `sale_stock` + `sale_management`, inheriting the whole
sale/stock/product/account/mail stack. Its center of gravity is `repair.order`, a
**43-field** work order that orchestrates `stock.move` records (the parts and the
repaired product) and binds to a `sale.order` for quotation/invoicing.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `sale_stock` | Couples sale orders to stock moves/pickings — repair reuses `stock.move` for parts and links the originating return `stock.picking`. |
| `sale_management` | Full quotation/order UI — repairs auto-create `sale.order.line`s for added parts and drive `qty_delivered`-based invoicing. |

**Adds on top:** the `repair.order` lifecycle, a dedicated `repair_operation`
picking type with add/remove/recycle locations, a warranty zero-pricing flag,
auto-creation of repairs from sale lines (`service_tracking='repair'`) and from
customer returns, parts availability/forecasting, and a Repair Order PDF report.

**Central model:** `repair.order` (52 methods, 43 fields) — everything points at
it. `repair` is mostly an **`_inherit` module**: only 3 own models, but 13
inherit-only extensions wire repair into stock/sale/product. The field profile is
**relational + state**: `Many2one` (18, mostly locations + product/lot/SO/picking)
and `Selection`/`Boolean` (the state machine and UI flags) dominate — an
operational work-order document, not a money document.

## Behavior & Surfaces

- **State machine** draft→confirmed→under_repair→done/cancel, driven by
  `action_validate`→`_action_repair_confirm`, `action_repair_start`,
  `action_repair_end`→`action_repair_done`, `action_repair_cancel`.
  `action_validate` checks on-hand qty (owner-first) and either confirms or raises
  the `stock.warn.insufficient.qty.repair` wizard. Confirm runs
  `move_ids._action_confirm()` + `_trigger_scheduler()` to procure parts (code-read).
- **Consume + produce.** `action_repair_done` marks part moves `picked`, then
  **creates a new `stock.move`** (`move_id`) for the product-to-repair
  (`product_location_src_id`→`product_location_dest_id`) whose `consume_line_ids`
  link the consumed parts, then `_action_done(cancel_backorder=True)` commits all
  moves to `stock.quant` (code-read).
- **Part flows by `repair_line_type`:** `add` (into production, `_is_consuming`=True
  → draws down stock), `remove` (→ inventory-loss/scrap), `recycle` (→ recycle
  location). Repair moves bypass reservation/split (`_should_be_assigned`/`_split`
  return early) and carry no `stock.picking` (code-read).
- **Sale & invoicing.** `sale.order._action_confirm`→`_create_repair_order` spawns
  a repair for each `service_tracking='repair'` line; `add` parts auto-create SO
  lines (`_create_repair_sale_order_line`); `under_warranty` zero-prices them;
  `qty_delivered` on done feeds standard invoicing (code-read).
- **Reverse logistics.** `stock.picking.action_repair_return` opens a pre-seeded
  repair from a return (`picking_id` constrained to `return_id != False`); partner,
  qty and lot are computed from that return's move lines (code-read).
- **Routes:** **0** — pure backend ORM app; one PDF report
  (`repair.report_repairorder2`), no web/RPC controllers, no API keys.
- **Frontend:** 2 JS files, **0 OWL components**, **2 patches**
  (`ProductCatalogKanbanController`/`ProductCatalogOrderLine`) extending the
  product-catalog UI to pick repair parts; bundles `web.assets_backend`,
  `web.assets_tests` (static).
- **Views/Security:** form (1), list (3), kanban/pivot/graph/activity (1 each); **3
  access rules, 1 record rule** (multi-company), **0 own groups** — it reuses
  `stock.group_stock_user`/`manager`.

## Value-Configuration Classification

**Value model: `chain` · activity_class: `support`.** Per Stabell & Fjeldstad,
repair is **value-chain (transform/flow)** logic: it consumes inputs (spare parts,
`_is_consuming`=True) and produces an output (the serviced product re-created as a
`stock.move` committed to `stock.quant`) — the same append-only move ledger and
bill-of-parts machinery as `stock`/`mrp`. It is **support**, not primary, because
(like `maintenance`) it is an **after-sales / aftermarket** service restoring
already-delivered goods rather than the firm's primary make-and-ship flow; it only
fires when a return or a service line triggers it, and rides entirely on
`sale_stock`+`sale_management`.

## APQC PCF Hint

**4.0 — Deliver Physical Products** (reverse logistics / after-sales operations).
No 4.x leaf names "repair", so 4.0 is the umbrella, qualified: repair runs inbound
from a customer return (**4.4.x** outbound transport in reverse), manages parts
inventory (**4.3.2.1** manage raw material inventory — `stock.quant` moves +
`warehouse.repair_mto_pull_id` replenishment), and re-delivers the serviced good. A
**7.x "after-sales service/support"** reading is plausible, but the dominant
evidence (stock-move consume/produce, repair picking types, warehouse routing) is
physical-fulfilment, hence 4.0.

## How to Drive It

Use the **run-odoo** skill (`odoo shell`); there are no routes to `curl`.

```python
# Lifecycle: validate -> start -> add a part -> end (produces the repaired move)
ro = env['repair.order'].create({
    'product_id': env['product.product'].search([('is_storable','=',True)],limit=1).id})
ro.action_validate(); print(ro.state)            # -> confirmed
ro.action_repair_start()                          # -> under_repair
ro.action_repair_end(); print(ro.state, ro.move_id)   # -> done, repaired stock.move

# Repair spawned from a sale order line (product service_tracking='repair')
so = env['sale.order'].create({'partner_id': <p>, 'order_line': [(0,0,{
    'product_id': <repair-service product>})]})
so.action_confirm(); print(so.repair_order_ids)

# Repair from a customer return + repair-type dashboard counts
env['stock.picking'].search([('return_id','!=',False)],limit=1).action_repair_return()
env['stock.picking.type'].search([('code','=','repair_operation')]).mapped(
    ('count_repair_confirmed','count_repair_under_repair','count_repair_late'))
```
