# payment_toss_payments — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Payment Provider: Toss Payments** module (`payment_toss_payments`, category
*Accounting/Payment Providers*, `application=False`) is the **Toss Payments
acquirer adapter** for Odoo's payment engine, covering the **South Korea** market
(Korean card / bank-transfer / easy-pay-mobile payments, KRW only). It depends on
exactly one module — **`payment`** — and exists only to make Toss a live provider:
it teaches `payment.provider`/`payment.transaction` how to talk to Toss over HTTP,
how to open the Toss-hosted payment window in the browser, and how to ingest Toss's
return/webhook notifications. It owns **no models and no views** — two `_inherit`
extensions graft Toss credentials and the confirm/payments flow onto the engine.
A textbook **metadata gap #7**: a real external integration whose endpoint,
secret-key auth and webhook trust live in code, not in field metadata.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `payment` | The provider/transaction engine + the centralized outbound HTTP helper `payment.provider._send_api_request` and the guarded transaction state machine this module plugs Toss into. |

**Adds on top:** Toss credentials (client key / secret key / computed webhook URL),
the **hosted-window direct** flow (card / bank transfer / mobile), server-side
amount-tamper validation before confirm, an **idempotent** confirm POST, and
KRW-only currency enforcement. Refunds, tokenization and manual capture are **not**
implemented.

## Data Model (the ERM)

| Model (`_name`) | Kind | #fields | Key relations |
|-----------------|------|--------:|---------------|
| `payment.provider` | _inherit | +4 | `code` (+'toss_payments'), `toss_payments_client_key`, `toss_payments_secret_key` (group_system), `toss_payments_webhook_url` (computed) |
| `payment.transaction` | _inherit | +1 | `toss_payments_payment_secret` (group_system, webhook secret); 5 methods overriding reference/processing/notification hooks; maps tx ↔ Toss payment (`provider_reference`=paymentKey, `reference`=orderId) |

**No own model, no own views** — `xml_loc≈55` is view *inheritance* (Client/Secret
Key + Webhook URL on the provider form) plus a QWeb inherit of `payment.method_form`
injecting `data-toss-payments-inline-form-values` onto the checkout radio, plus
provider seed data. The cross-system keys (`provider_reference`=paymentKey,
`reference`=orderId, `toss_payments_payment_secret`) bind Odoo records to Toss objects.

## Behavior & Surfaces

- **Routes:** 3, all HTTP public. `/payment/toss-payments/success` (GET redirect-
  return), `/payment/toss-payments/failure` (GET redirect-return),
  `/payment/toss-payments/webhook` (POST, **csrf=False**, async notifications).
- **Frontend (static):** 1 JS file, **no OWL**, 0 registry adds — it **patches**
  `PaymentForm.prototype` to force the `direct` flow and drive the Toss v2 SDK
  hosted window; assets in `web.assets_frontend`.
- **Security:** **0 own ACL/record rules/groups** — leans on `payment`; secret &
  per-payment webhook-secret fields restricted to `base.group_system`.

What metadata cannot show, established by reading the code:

- **Outbound request helper** — `_build_request_url` targets
  `https://api.tosspayments.com/`; `_build_request_auth` returns
  `(toss_payments_secret_key, '')` → **HTTP Basic** with the secret key as username
  and empty password (Toss `secret_key:` scheme); `_build_request_headers` adds an
  **Idempotency-Key** `orderId:paymentKey`. The one call site POSTs
  **`/v1/payments/confirm`** to finalize the charge.
- **Checkout / redirect flow** — `_get_specific_processing_values` returns
  order/customer fields + success/fail URLs (the fail URL carries a generated
  `access_token`). `payment_form.js` patches `PaymentForm`, `loadJS`'s the
  **Toss v2 `standard` SDK** at runtime, reads the inline JSON (client key + pm
  code via `PAYMENT_METHODS_MAPPING`) and `TossPayments(key).payment(...).requestPayment(...)`
  opens the hosted modal. `_compute_reference` forces an alphanumeric `tx-…` prefix
  Toss will accept.
- **Return / confirm + webhook** — `/…/success` finds the tx by
  `_search_by_reference` (orderId), runs **`_validate_amount`** against the
  redirected amount *before* POSTing `/v1/payments/confirm`, then `_process`.
  `/…/failure` verifies via `check_access_token` then `_set_error`.
  `/…/webhook` handles `PAYMENT_STATUS_CHANGED` and calls **`_verify_signature`**
  *before* `_process`: a **constant-time** (`hmac.compare_digest`) compare of the
  payload `secret` vs `toss_payments_payment_secret` — mismatch/missing → HTTP **403
  Forbidden** (`EXPIRED`/`ABORTED` are verification-exempt). Note this is **secret
  equality, not HMAC** as in the Stripe sibling.
- **Status mapping** — `_apply_updates` stores `paymentKey`→`provider_reference`,
  `secret`→`toss_payments_payment_secret`, then `PAYMENT_STATUS_MAPPING`:
  `DONE`→`_set_done`, `EXPIRED`→`_set_canceled`, `ABORTED`/other→`_set_error`;
  `CANCELED`/`PARTIAL_CANCELED` on a done tx is a **no-op** (refunds not
  implemented). `_extract_amount_data` forces KRW; a constraint rejects any
  non-KRW currency.

## Value-Configuration Classification

**Value model: Network (mediating-technology acquirer integration).**
`payment_toss_payments` interconnects two parties who would not otherwise transact
directly — the **South-Korean payer** and the **merchant** — by linking the merchant
into Toss's card / bank-transfer / mobile network. It shows the three mediating-
technology activities: **network promotion & contract management** (credential/key
management, webhook-URL provisioning, KRW/reference constraints), **service
provisioning** (opening the hosted window and confirming the charge per transaction
via `/v1/payments/confirm`), and **infrastructure operation** (the
`api.tosspayments.com` server link, the Toss v2 SDK client channel, the redirect +
signed-webhook settlement loop). It is **not** transformation (chain) or bespoke
problem-solving (shop). It inherits the parent `payment` engine's classification —
the engine is the generic mediator, this module its **Toss realization (gap #7)**.
Classified **network / support** (mirrors `payment.metamodel.json` and the
`payment_stripe` sibling).

## How to Drive It

Use the `run-odoo` skill. With a `-i payment_toss_payments` database and a Toss
provider in test state:

```python
# odoo shell — provider + supported currency (KRW-only)
p = env['payment.provider'].search([('code','=','toss_payments')], limit=1)
print(p.name, p.state, p.toss_payments_webhook_url, p._get_supported_currencies().mapped('name'))
# Toss-specific override surface + a transaction <-> Toss object link
print([m for m in dir(env['payment.transaction']) if 'toss' in m.lower()])
tx = env['payment.transaction'].search([('provider_code','=','toss_payments')], limit=1)
print(tx.reference, tx.state, tx.provider_reference)  # provider_reference == Toss paymentKey
```

```bash
# webhook signature gate: a wrong/missing 'secret' -> HTTP 403 Forbidden
curl -X POST https://<host>/payment/toss-payments/webhook -H 'Content-Type: application/json' \
  -d '{"eventType":"PAYMENT_STATUS_CHANGED","data":{"orderId":"tx-x","status":"DONE","secret":"bad"}}'
```
