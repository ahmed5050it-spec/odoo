# account_peppol — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Peppol** module (`account_peppol`, category *Accounting/Accounting*,
`application=False`, **`auto_install`** with `account_edi_ubl_cii`) is the
**Peppol Access Point connector** for Odoo: it plugs Accounting into the Peppol
four-corner e-delivery network so a company can **send** customer invoices and
**receive** vendor bills as structured documents through a certified access
point. It is the natural counterpart to its sibling `account_edi_ubl_cii`, which
only *builds and parses* the UBL/CII XML and explicitly **defers network
transmission to here**. The center of gravity is not a new business document but
a **network identity and a signed transport**: it extends
`account_edi_proxy_client.user` with a `peppol` proxy type, adds a Peppol
participant identity (EAS/endpoint + registration state machine) to
`res.company`, a reachability cache to `res.partner`, and per-document delivery
status to `account.move`. 5535 lines of Python implement the registration,
send/receive, verification and connection-recovery logic.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `account_edi_proxy_client` | Provides the signed (asymmetric-key) HTTPS transport to Odoo's IAP; `account_peppol` adds the `peppol` proxy_type and all Peppol endpoints on top. |
| `account_edi_ubl_cii` | Builds/parses the UBL BIS 3 / NLCIUS XML that this module actually ships and receives over the wire. |

**Adds on top:** three wizard/config models (`account_peppol.service`,
`peppol.config.wizard`, `peppol.registration`) plus extensions to
`account_edi_proxy_client.user`, `res.company`, `res.partner`, `account.move`,
`account.move.send` and `account.journal`. **Auto-installed** with the UBL/CII
engine, so on a Peppol-country Accounting database it is best read as a built-in
network capability rather than an optional app.

| `account_peppol.service` | A registrable Peppol document type | 4 | `wizard_id→peppol.config.wizard` |

| **`res.company`** (ext) | Peppol participant identity (EAS/endpoint) + proxy state machine | 15 | `account_peppol_edi_user`, `peppol_purchase_journal_id` |
| `res.partner` (ext) | Trading-partner reachability (`peppol_verification_state`) | 5 | — |
| `account.move` (ext) | Per-invoice Peppol transmission status | 3 | — |
| `account.move.send` (ext) | Peppol as a sending method on Send & Print | 0 | — |
| `account.journal` (ext) | Flags the inbound-Peppol journal | 2 | — |

**Central concept:** there is no new ledger entity — the module orbits
**`res.company` as a Peppol participant** and **`account.move` as a transmissible
document**. The only genuinely new models are transient wizards; the real state
(participant status, message UUIDs, partner reachability) lives as fields grafted
onto existing accounting models. That is why the field census is modest while the
Python LOC is large: the weight is in network/API behavior, not schema.

## Behavior & Surfaces

- **Routes:** **4 webhook controllers** — `/peppol/webhook/new-message`,
  `/peppol/webhook/message-state-update`, `/peppol/webhook/user-state-update`
  (public, signed-token) let the access point **push** state back, and
  `/peppol/authentication/callback` (user) handles the auth return.
- **Frontend (gap #3):** 7 JS files, 1 OWL component (**`WhatIsPeppol`**), 5
  registry adds and 2 controller patches (`AccountMoveForm/ListController`); a
  `peppol_auth_service` and a public interaction for the invoice sending method.
  Bundles: `web.assets_backend` (3), `web.assets_frontend` (1).
- **Integrations (gap #7):** **3 outbound HTTP call sites** via the `requests`
  SDK to **`https://peppol.api.odoo.com`** (prod) / **`https://peppol.test.odoo.com`**
  (test) plus the European **SML/SMP** DNS infrastructure. No stored API keys —
  auth is the EDI proxy user's **asymmetric signature**.
- **Views:** 0 dedicated view files; it injects fields/buttons into existing
  Accounting forms and the Send & Print wizard.
- **Security:** 3 access rules, 0 record rules, 0 groups — inherits the
  Accounting security model.

The metadata cannot show what **send / receive / register** mean over the
network. Reads of the code establish:

- `account_edi_proxy_client.user._call_peppol_proxy` — **the network bridge**:
  every operation is a signed HTTPS call to versioned proxy endpoints
  (`1/send_document`, `1/get_all_documents`, `1/get_document`, `1/ack`,
  `1/register_sender_as_receiver`, `2/participant_status`, `2/set_webhook`, …).
  It self-heals: `invalid_signature` marks the connection **out-of-sync** and
  forces *Reconnect this database*; `no_such_user` resets to `not_registered`.
- `account.move.send._send_peppol_documents` — **outbound transmission**: on Send
  & Print, applicable moves are base64-UBL POSTed in a batch to `1/send_document`
  addressed to `{peppol_eas}:{peppol_endpoint}`; returned UUIDs are zipped back
  onto the moves (`peppol_message_uuid`, state→`processing`), records locked &
  committed, and a status cron scheduled +5 min.
- `account_edi_proxy_client.user._peppol_get_new_documents` /
  `_peppol_import_invoice` — **inbound reception**: a cron polls
  `1/get_all_documents`, fetches & **AES-decrypts** payloads, creates an
  `account.move` in `peppol_purchase_journal_id` (or an `out_invoice` for
  self-billing codes 389/527/261), parses the UBL via `account_edi_ubl_cii`,
  `_autopost_bill`s it, then ACKs **only** what was saved.
- `_peppol_register_sender_as_receiver` / `_cron_peppol_get_participant_status` —
  **participant lifecycle + status polling**: a company walks
  `not_registered → sender → smp_registration → receiver`; the participant-status
  cron runs **weekly but self-re-triggers hourly while in `smp_registration`** to
  catch SMP publication, and `_get_company_info_on_peppol` blocks
  double-registration under another provider.
- `res.partner._peppol_lookup_participant` — **recipient reachability**: a live
  NAPTR-DNS **SML/SMP lookup** (via `1/lookup`) confirms the partner is on Peppol
  and advertises the chosen format, cached company-dependently in
  `peppol_verification_state`, gating whether Peppol is even offered.

## Value-Configuration Classification

**Value model: Network (Stabell & Fjeldstad mediating / value-network logic).**
`account_peppol` exists to **connect the company to its trading partners over the
Peppol network** through a certified access point. It performs the three
signature mediator activities: **network promotion & contract management**
(participant registration + SML/SMP capability lookup that establishes who is
reachable), **service provisioning** (relaying invoices/bills between corners),
and **network infrastructure operation** (maintaining the signed connection,
webhooks and status crons). Its value rises with the size of the reachable Peppol
network — a textbook network effect — and it **mediates between many parties**
rather than transforming inputs (chain) or solving a bespoke client problem
(shop). It is deliberately distinguished from the sibling `account_edi_ubl_cii`
(pure serialization → *support*). **`activity_class` is `support`**: despite the
network value-configuration, within the firm this is an infrastructure/compliance
enabler bolted onto Accounting (no app, headless bar one Send & Print dialog, no
primary-revenue activity of its own). Classified **network / support**.

## APQC PCF Hint

**9.0 Manage Financial Resources.** The module is the **transport edge** of
accounting document exchange: it dresses **9.2.x Process accounts receivable**
(transmit a posted customer invoice over Peppol) and **9.5.x Process accounts
payable** (receive a vendor bill from Peppol into a journal). It posts no ledger
entries itself — it **moves the statutory documents** that `account` posts and
receives between Peppol corners — so it sits in the regulatory/document-exchange
corner of 9.0.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i account_peppol` database:

```python
# odoo shell — inspect this company's Peppol participant identity & state
c = env.company
print(c.account_peppol_proxy_state, c.peppol_eas, c.peppol_endpoint)
u = c.account_peppol_edi_user
print(bool(u), u.edi_mode if u else None)   # proxy user present? prod/test/demo

# live recipient reachability (real SML lookup — needs outbound network)
p = env['res.partner'].browse(PARTNER_ID)
p.button_account_peppol_check_partner_endpoint()
print(p.with_company(c).peppol_verification_state)  # valid / not_valid / ...
```

For an **offline** demo, set the company `peppol_eas = 'odemo'`: the `handle_demo`
decorator routes the registration/send flow to the `demo` proxy with no real
network calls. In the UI: **Settings → Accounting → Electronic Invoicing
(Peppol)** to register, then on a posted customer invoice use **Send & Print →
"by Peppol"**. Inbound bills arrive automatically via
`PEPPOL: retrieve new documents` (cron, every 4 h).
