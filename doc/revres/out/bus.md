# bus — Reverse-Engineering Brief

> *Generated by the revres code-explorer + code-architect workflow: facts from
> `extract_module.py` / `extract_frontend.py` + source code-reads.*

The **IM Bus** module (`bus`, category *Hidden*, `application=False`,
`auto_install=True`) is Odoo's real-time messaging backbone. It carries no
business documents of its own; instead it provides a publish/subscribe pipe —
PostgreSQL `LISTEN/NOTIFY` fanned out over WebSockets (with longpolling
fallback) — that every collaboration feature above it rides on. It depends only
on `base` and `web`, making it small but foundational.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `base` | ORM, transaction precommit/postcommit hooks, autovacuum GC, `ir.*` extensions. |
| `web` | Webclient asset bundles and the OWL service registry the JS client plugs into. |

**Adds on top:** the `bus.bus` notification store, a LISTEN/NOTIFY dispatcher
thread, websocket transport, the `bus.listener.mixin` channel mixin, and a
SharedWorker-based JS client (`bus_service`).

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Notes |
|-----------------|-------------|--------:|-------|
| **`bus.bus`** | Communication Bus | 2 | `channel`, `message` (both Char). No FKs — channels encode `(db, model, id)` tuples. |
| **`bus.listener.mixin`** | Can send via bus.bus | 0 | Abstract; mixed into `res.partner`, `res.users`, `res.groups`, `res.users.settings`, `ir.attachment`. |
| **`ir.websocket`** | websocket message handling | 0 | Channel authorization + subscribe wiring. |

The store is deliberately thin (a low-level append-only table); the intelligence
lives in methods, the dispatcher thread, and the websocket layer.

## Behavioral Findings (beyond metadata)

- **Deferred publish (`_sendone` / `_ensure_hooks`):** notifications buffer into
  `cr.precommit` (bulk `create`) and `cr.postcommit`, which fires
  `SELECT pg_notify('imbus', payload)` on a dedicated postgres connection *after*
  commit so the row is fetchable; oversized payloads split recursively.
- **Dispatcher (`ImDispatch.loop`):** a lazily-started daemon thread runs
  `LISTEN imbus`, and on each NOTIFY looks up subscribed sockets in the in-memory
  `_channels_to_ws` map and calls `trigger_notification_dispatching()` — the core
  broadcast engine.
- **Dual transport (`_poll` + `_dispatch_bus_notifications`):** first poll returns
  the 50s buffer; later polls return `id > last`. Over websockets a per-socket
  `_notif_history` dedups and the server-side last id is trusted after subscribe.
- **Channel authorization (`_build_bus_channel_list`):** a client's channel list
  is augmented server-side with `broadcast` + its own groups + its own partner, so
  no one can subscribe to arbitrary records. PING/PONG heartbeats detect dead
  sockets. (There is no `bus_presence.py` here — presence lives in JS + mail.)
- **Frontend `bus_service` (static):** boots a SharedWorker, sends
  `BUS:INITIALIZE_CONNECTION/ADD_CHANNEL/SEND`, tracks `lastNotificationId` across
  tabs via `multi_tab`, and re-emits notifications by type on an `EventBus`.

## Classification

- **Value model:** `support` — Stabell & Fjeldstad enabler, not a value activity.
- **Activity class:** `support`.
- **APQC category:** `8.0 Manage Information Technology`.
- **Rationale:** Hidden, auto-installed, base+web-only infrastructure with no
  business document. It is the real-time substrate powering value-network /
  collaboration features (Discuss, presence, live UI) of higher modules, so it is
  classified as IT-service delivery rather than a primary-chain activity.

## Fit-to-Standard

**Out of the box:** websocket transport with longpolling fallback, LISTEN/NOTIFY
dispatcher, `bus.listener.mixin` channel-addressable records, server-controlled
channel authorization, multi-tab coordination, and 24h autovacuum GC of stale
rows. **Typical fits:** real-time chat/notifications once mail/discuss is present;
making custom records live by inheriting the mixin and calling `_bus_send`.
**Common gaps:** new event types need an `_build_bus_channel_list` override plus a
JS `subscribe()` handler; high volume may need `ODOO_NOTIFY_PAYLOAD_MAX_LENGTH` /
`ODOO_NOTIFY_FUNCTION` tuning; proxies must support websocket upgrades.

**Drive it live:**
- `env['res.partner'].browse(uid).partner_id._bus_send('demo.notif', {'msg': 'hi'})`
- `env['bus.bus'].search([], order='id desc', limit=3).read(['channel','message'])`
- `curl -i http://localhost:8069/websocket/health` (expects 200, auth=none)

## Open Questions

- Interplay of the 50s `_poll` buffer and per-socket `_notif_history` dedup under
  reconnect storms.
- End-to-end presence/`im_status` computation (JS presence service + mail, not bus).
- Scaling limits of the single `ImDispatch` thread / postgres LISTEN connection
  under many concurrent websockets.
