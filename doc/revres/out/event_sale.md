# event_sale — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/` + `wizard/`, narrative
> per `PROMPT.md`. Odoo 19.0.*

The **Events Sales** module (`event_sale`, category *Marketing/Events*,
`application=False`, **`auto_install=True`**) is **THE BRIDGE** that lets you
sell event tickets through sales orders. It depends only on `event_product` and
`sale_management`, and is auto-installed whenever both an Events stack and Sales
are present. It defines no new business entity of its own — instead it grafts
event ticketing onto `sale.order` / `sale.order.line` and wires `sale.order` ↔
`event.registration` so that confirming an order materializes attendees and the
order's payment status gates whether those seats become *sold*.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `event_product` | Brings the `service_tracking='event'` ticket-product + `event.event.ticket.product_id` link this module sells. |
| `sale_management` | The quotation/sales-order app whose `sale.order` / `sale.order.line` it extends and confirms. |

**Adds on top:** ticket-priced order lines, an event/slot/ticket configurator on
the line, auto-creation and bi-directional sync of `event.registration` from
confirmed orders, an attendee-detail wizard, payment-gated registration status,
and an `event.sale.report` revenue/seat analysis view.

## Data Model (the ERM)

| Model (`_name`) | Role | #fields | Key relations |
|-----------------|------|--------:|---------------|
| `sale.order.line` *(ext)* | the event ticket line | +5 | `event_id→event.event`, `event_ticket_id→event.event.ticket`, `event_slot_id→event.slot`, `registration_ids→event.registration` |
| `event.registration` *(ext)* | paid/sold attendee | +6 | `sale_order_id→sale.order`, `sale_order_line_id→sale.order.line` (+ `sale_status`, `state`) |
| `sale.order` *(ext)* | order carrying tickets | +1 | `attendee_count` |
| `event.event` *(ext)* | event w/ revenue rollup | +2 | `sale_order_lines_ids→sale.order.line`, `sale_price_total` |
| `event.event.ticket` *(ext)* | priced ticket | 0 | description override only |
| `product.template` *(ext)* | ticket product | 0 | forces `invoice_policy='order'` |
| **`event.sale.report`** | Event Sales Report | 24 | `_auto=False` SQL view: `event.registration` ⋈ `sale.order.line` |
| `event.event.configurator` | configurator wizard | 6 | `product_id`, `event_id`, `event_slot_id`, `event_ticket_id` |
| `registration.editor`(`.line`) | attendee-detail wizard | 2 / 10 | `sale_order_id`, `registration_id→event.registration` |

**Center of gravity:** the `sale.order.line` ↔ `event.registration` pair — six of
ten models are `_inherit`-only extensions (mixin-style), so the module is almost
pure glue. The only standalone, non-transient model is the read-only
`event.sale.report`. Field mix is relational-heavy (`Many2one`-dominated),
matching a join/bridge subsystem.

## Behavior & Surfaces

- **Routes:** **none** — interaction is entirely backend ORM + form views
  (no public storefront; that is `website_event_sale`).
- **Views:** the facts report 0 own view *types* extracted, but the module
  ships SO/event form extensions and the configurator/editor wizards.
- **Security:** 4 access rules, **1 record rule** (multi-company on
  `event.sale.report`), **1 group** action: `sales_team.group_sale_salesman`
  is made to **imply** `event.group_event_registration_desk` — a cross-app
  permission bridge so salespeople can run the registration desk.
- **Behavior beyond metadata (code-read):**
  `sale.order.action_confirm` → `_init_registrations` creates one
  `event.registration` per sold unit (paid → `draft`, free → `open`) and, for a
  single order, pops the `registration.editor` attendee wizard;
  `event.registration.create/write` synchronizes partner/event/ticket from the
  SO line and chatter-links back via `mail.message_origin_link`;
  `_compute_registration_status` derives `sale_status` (free / to_pay / sold)
  and the seat `state` from `sale.order.state`/`amount_total`, with
  draft→open triggering attendee-mail scheduling; an event line's unit price and
  label come from `event.event.ticket` (`price`/`price_reduce`), not the product.
- **Frontend (static):** 2 JS, 0 OWL components — registers the
  `event_configurator_form` view controller and **patches**
  `SaleOrderLineProductField.prototype` so selecting an event product opens the
  configurator dialog and writes event/slot/ticket back to the line.
- **Integration (gap #7):** none — `http_call_sites=0`, no SDK/API keys; the
  only endpoint is the `__manifest__` website URL.

## Value-Configuration Classification

**Primary model: Value Network (mediation), customer-facing — THE BRIDGE.**
`event_sale` is classified **network**: it monetizes event registrations,
turning a seat in the `event` network into a priced, invoiceable
`sale.order.line` and turning a confirmed order back into `event.registration`
rows whose `sale_status` (free/to_pay/sold) is gated by payment. The economic
logic it manages is still network logic — selling capacity-constrained
*access/membership* and provisioning attendees — not a chain's input→output
transformation. The chain (quote-to-cash) mechanics are *inherited from* `sale`
and are what this bridge plugs into, not what it is; hence network, consistent
with the bridged `event(network)` record. It is a **primary** activity (it
directly produces revenue-bearing registrations). *(Chain was considered, on the
strength of reusing `sale.order`/line and invoice-on-order revenue, but rejected:
the module's distinctive behavior is network monetization / attendee mediation.)*

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i event_sale` database:

- `env['sale.order.line'].search([('event_id','!=',False)], limit=5).mapped(('order_id.name','event_ticket_id.name','price_unit'))`
- `env['event.registration'].search([('sale_order_id','!=',False)], limit=5).mapped(('name','state','sale_status'))`
- `so = env['sale.order'].search([('order_line.event_id','!=',False)], limit=1); so.action_confirm(); so.attendee_count`
- `env['event.sale.report'].search([], limit=5).mapped(('event_id','sale_price','sale_order_state'))`
