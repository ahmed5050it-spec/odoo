# product — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + code-read, narrative per `PROMPT.md`.*

The **Products & Pricelists** module (`product`, category *Sales/Sales*,
`application=False`) is the **master-data foundation** of the Odoo suite. It is
**not** auto-installed and sits very low in the dependency graph — it depends on
only `base`, `mail`, and `uom` — yet it is one of the most depended-on hubs in
the codebase. Its center of gravity is the `product.template` /
`product.product` pair: a template describes a sellable/purchasable item and its
variants are the concrete, priced SKUs. 26 models, ~10.9k Python LOC, 4.9k XML.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `base` | Core ORM, companies, partners (vendors), currencies. |
| `mail` | `mail.thread`/`mail.activity.mixin` on templates, variants, pricelists (chatter + activities). |
| `uom` | Units of measure on products and pricelist rules (`uom.uom`). |

**Adds on top:** product templates & variants, the attribute/variant engine,
pricelists with pricing rules, categories/tags, vendor (supplier) pricelists,
product documents, and label/pricelist reports.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`product.template`** | Product | ~45 | `categ_id→product.category`, `uom_id→uom.uom`, `attribute_line_ids→…attribute.line`, `product_variant_ids→product.product` |
| **`product.product`** | Product Variant | ~37 | `product_tmpl_id→product.template`, `product_template_attribute_value_ids→…attribute.value` |
| `product.attribute` | Product Attribute | 10 | `value_ids→product.attribute.value`, `product_tmpl_ids→product.template` |
| `product.template.attribute.value` | Template Attribute Value | 15 | `product_attribute_value_id→…value`, holds **`price_extra`** |
| `product.pricelist` | Pricelist | 7 | `currency_id→res.currency`, `item_ids→product.pricelist.item` |
| `product.pricelist.item` | Pricelist Rule | 28 | `pricelist_id→…pricelist`, `product_tmpl_id`/`product_id`/`categ_id` |

**Central model:** `product.template` (everything references it). The model set
is **relational-heavy** — `Many2one` (48) dominates, with `Boolean` (30, lots of
feature/state flags) and `Float` (27, a pricing/amount-centric master record).
`product.product` carries 10 `Image` fields (variant + template image cascade).

## Behavior & Surfaces

- **Routes:** 4, all `auth='user'` — a pricelist export (`/product/export/pricelist/`,
  http), a catalog JSON surface (`/product/catalog/order_lines_info`,
  `/product/catalog/update_order_line_info`, jsonrpc) and a document upload. No
  public storefront here.
- **Frontend (gap #3):** 15 JS files, 8 XML templates, **4 OWL components**
  (`ProductCatalogOrderLine`, `ProductNameAndDescriptionField`,
  `ProductPricelistReport`, `UploadButton`), 4 registry adds, 0 patches; bundles
  `web.assets_backend` (6) + report/test assets.
- **Integrations (gap #7):** none — 0 HTTP call sites, no SDK imports, no API
  keys. This is a self-contained data module.
- **Views:** **list (24)**-heavy, form (15), kanban (6), search (9), activity (2)
  — an operational, catalog-management surface.
- **Security:** 38 access rules, **6 record rules**, 3 groups — a low
  record-rule count (mostly multi-company scoping), reflecting widely-readable
  master data.

## Behavioral Notes (beyond metadata)

- **`product.template._create_variant_ids`** materialises `product.product`
  rows as the **cartesian product** of valid attribute lines. With
  `create_variant='always'` every combination is instantiated immediately;
  `'dynamic'` defers creation to the configurator; `'no_variant'` never spawns
  variants. Bounded by `product.dynamic_variant_limit` (default 1000).
- **`price_extra`** lives on `product.template.attribute.value`;
  `_compute_product_price_extra` sums it across a variant's attribute values, and
  `lst_price = template.list_price + price_extra` (uom-context dependent).
- **`product.pricelist.item._compute_price`** resolves a unit price per rule —
  `fixed`, `percentage`, or `formula` (discount/markup, rounding, surcharge,
  min/max margin) against a configurable base — and `_compute_price_rule` picks
  the **most specific** applicable rule (variant > template > category > global).

## Value-Configuration Classification

**Primary model: Support / Firm Infrastructure (master data).** `product` is a
**support** activity (Stabell & Fjeldstad): it does not transform demand or run
an operational document flow. Instead it defines the product/variant/attribute/
pricelist **information concepts** that every primary activity consumes — the
chain (`sale`, `purchase`, `stock`, `mrp`), the shop (services/timesheets), and
the network (`pos`, `website_sale`). `product.template` is a core, widely-
depended-on Information Concept. `activity_class = support`.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i product` database:

```python
# odoo shell
tmpls = env['product.template'].search([], limit=5)
print(tmpls.mapped('name'), tmpls.mapped('list_price'), tmpls.mapped('product_variant_count'))
# variant generation + assembled price:
tmpl._create_variant_ids()
print(tmpl.product_variant_ids.mapped('lst_price'))
# pricelist engine:
pl = env['product.pricelist'].browse(1)
print(pl._get_product_price(env['product.product'].browse(1), 1.0))
# curl .../product/export/pricelist/  (auth=user, http)
```
