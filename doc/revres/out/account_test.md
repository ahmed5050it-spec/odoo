# account_test — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> code-reads of `models/`, `report/`, `data/`, `security/`, `views/`, per
> `AGENT_WORKFLOW.md` / `PROMPT.md`. Odoo 19.0.*

The **Accounting Consistency Tests** module (`account_test`, category
*Accounting/Accounting*, `application=False`) is a small **financial-controls /
audit utility** on top of `account`. It lets an auditor or controller run a
catalog of **integrity assertions against the live ledger** — balanced entries,
reconciliation correctness, posted-vs-draft invoice status, bank-statement
closing balances — and renders a pass/fail PDF. It owns **no business document**
of its own; it inspects the books that `account` produces. Not auto-installed;
depends only on `account`.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `account` | The tests read the double-entry ledger (`account_move_line`, bank statements, invoices); the menu hangs under Accounting reporting; read access is granted to `account.group_account_manager`. |

**Adds on top:** an `accounting.assert.test` rule catalog (each rule a `code_exec`
SQL/Python snippet), an `AbstractModel` report that executes those snippets, a
QWeb PDF, and ~6 bundled standard tests — all gated to debug mode.

## Data Model (the ERM)

| Model (`_name`) | Kind | #fields | Notes |
|-----------------|------|--------:|-------|
| `accounting.assert.test` | rule record | 5 | `name`, `desc`, `code_exec` (req.), `active`, `sequence`; `_order='sequence'`; **no relations, 0 own methods** — a pure assertion container. |
| `report.account_test.report_accounttest` | AbstractModel report | 0 | 2 methods: `_execute_code`, `_get_report_values`. Runs each test live, no persistence. |

**Center of gravity:** the report model. `accounting.assert.test` is inert data;
the *behavior* is the `safe_eval` runner that turns a `code_exec` string into a
pass/fail verdict at render time.

## Behavior & Surfaces

- **Routes:** 0 — pure backend, no web/JSON-RPC surface.
- **Frontend (static):** none — 0 JS, 0 OWL components, 0 registry adds, 0
  patches, no asset bundles. UI is server-rendered list/form/search + a QWeb PDF.
- **Views:** 1 list, 1 form (Description + Expression notebook pages, with inline
  Code Help), 1 search; menu *Accounting Tests* under `account.menu_finance_reports`,
  gated to `base.group_no_one` (developer mode).
- **Security:** 2 access rules, 0 record rules, 0 own groups —
  `base.group_system` has full CRUD; `account.group_account_manager` is read-only.
- **Assertion runner (code-read):** `report_accounttest._execute_code` runs the
  test's `code_exec` via `safe_eval(mode='exec')` in a sandbox exposing `cr`,
  `uid`, a `reconciled_inv()` helper and an empty `result`. **Pass/fail is by
  emptiness** of `result` — empty ⇒ "The test was passed successfully", non-empty
  ⇒ each row formatted (honouring an optional `column_order`) as the failure
  detail. No boolean flag is stored.
- **Report rendering (code-read):** the QWeb template `t-foreach`'s the selected
  tests and, per test, calls `execute_code(o.code_exec)`, printing name, desc and
  each result line live against the current database. Nothing is persisted; the
  report header stamps `datetime.now()`.
- **Ordering (code-read):** `active` (default True) + `sequence` (default 10) with
  `_order='sequence'` let an auditor curate which checks run and in what order;
  archived tests drop out of the default ORM domain.
- **Bundled tests (code-read):** Test 1 General balance (ΣDebit=ΣCredit), Test 3
  Movement lines (per-move balance + date match), Test 5.1/5.2 reconciled-invoice
  vs Payable/Receivable, Test 6 Invoice status (paid not left Open), Test 7 Bank
  statement closing balance. Test 4 and Test 8 are commented-out TODOs; several
  queries hit legacy tables (`account_invoice`, `account_bank_statement`,
  `account.period`) that changed in the modern schema.

## Value-Configuration Classification

**Support activity — Value Chain support function.** `account_test` adds nothing
to any primary value chain and owns no document; it is back-office assurance
plumbing that audits the integrity of `account`'s ledger. The rule record is inert
data and the report is a read-only renderer. `value_model = support`,
`activity_class = support`.

## How to Drive It

Use the `run-odoo` skill. With an `-i account_test` database:

```python
# odoo shell
env['accounting.assert.test'].search([]).mapped(('sequence','name','active'))
t = env.ref('account_test.account_test_01')          # 'General balance'
env['report.account_test.report_accounttest']._execute_code(t.code_exec)
# -> ['The test was passed successfully'] when ΣDebit=ΣCredit
```

Or, in developer mode: *Accounting > Reporting > Accounting Tests*, select tests,
print the **Account Test Report**.
