# hr_timesheet — Reverse-Engineering Brief

> *Generated by the code-explorer + code-architect workflow: facts from
> `extract_module.py`/`extract_frontend.py` + behavioral reads of
> `models/hr_timesheet.py`, `project_task.py`, `project_project.py`.*

The **Task Logs** module (`hr_timesheet`, category *Services/Timesheets*,
`application=False`) lets employees log time against project tasks. Its defining
move is structural: it does **not** create a "timesheet" model — it
`_inherit`s `account.analytic.line`, so **a logged hour IS an analytic cost
line**. It is not auto-installed and sits at the junction of HR and Project,
depending on `hr`, `hr_hourly_cost`, `analytic`, `project`, and `uom`. This is
the bridge that makes a value-shop engagement measurable and (downstream, via
`sale_timesheet`) billable.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `analytic` | Provides `account.analytic.line`/`account.analytic.account` — the cost vessel a timesheet posts into. |
| `project` | Provides `project.task`/`project.project`, the effort containers hours are logged against. |
| `hr` | Provides `hr.employee`, the resource whose time is logged. |
| `hr_hourly_cost` | Supplies `employee.hourly_cost`, the rate used to cost the logged hours. |
| `uom` | Hours-vs-days encoding of duration (`timesheet_encode_uom_id`). |

**Adds on top:** time encoding on tasks/projects, automatic labour costing
(hours × hourly cost) onto the project's analytic account, effort roll-up
(effective/remaining/progress), a portal listing, and a Timesheets Analysis
report.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`account.analytic.line`** *(extension)* | Analytic Line = Timesheet | 14 | `task_id→project.task`, `project_id→project.project`, `employee_id→hr.employee` |
| `project.task` *(extension)* | Task | 13 | `timesheet_ids→account.analytic.line` |
| `project.project` *(extension)* | Project | 12 | `timesheet_ids→account.analytic.line`, `account_id→account.analytic.account` |
| `timesheets.analysis.report` | Timesheets Analysis Report (SQL view) | 15 | `project_id`, `task_id`, `manager_id→hr.employee` |
| `account.analytic.line.calendar.employee` | Calendar personal filter | 4 | `employee_id→hr.employee` |

**Central model:** the `account.analytic.line` **extension** — the module owns
almost no new `_name`s (only 3 real models + report/wizard); its 14 inherit-only
extensions graft timesheet semantics onto existing models. The field mix is
**relational + measurement-heavy**: `Many2one` (30) for the
employee/task/project/department links, plus `Float` (18, the hour quantities &
roll-ups) and a single `Monetary` (the report `amount`). It is a measurement
layer, not a document.

## Behavior & Surfaces

- **Routes:** 1 HTTP route, `auth='user'` — the portal pages `/my/timesheets`
  and `/my/timesheets/page/<int:page>`. No JSON-RPC/configurator surface; the
  backend UX is view-driven.
- **Views:** form (3), list (3), kanban (3), **pivot (2) / graph (3) / calendar
  (2)** — analytics-and-calendar heavy, fitting a "encode time, then slice it"
  workflow. The OWL `timesheet_uom` widget renders duration in the company UoM.
- **Security:** 7 access rules, **9 record rules**, 4 groups
  (`group_hr_timesheet_user`, `group_hr_timesheet_approver`,
  `group_timesheet_manager`). Record rules enforce **own-timesheet** visibility:
  `_check_can_write`/`_check_can_create` block a basic user from touching lines
  that aren't theirs.

### Behavior beyond metadata (code-read)
- `_timesheet_postprocess_values` recomputes the line's `amount = -unit_amount ×
  employee.hourly_cost` (via `_hourly_cost()`), currency-converted to the
  analytic account — the **support→primary cost computation**.
- `project.task._compute_effective_hours` rolls up `timesheet_ids.unit_amount`
  (`_read_group` sum); `subtask_effective_hours` recurses over `child_ids`;
  `progress`/`overtime`/`remaining_hours` derive from allocated vs spent.
- `project.project.create` **auto-creates an `account.analytic.account`** when
  `allow_timesheets` is set, and `_check_allow_timesheet` refuses timesheets
  without one — the value vessel is mandatory.

## Value-Configuration Classification

**Primary model: Value Shop (solve), primary activity.** `hr_timesheet`
measures the **delivered effort** of the value-shop engagement: hours logged on
`project.task` become analytic cost lines on the project's
`account.analytic.account`, priced from `employee.hourly_cost`. It is the
shop's **execution / problem-resolution-control** loop, not back-office
enablement, so it is classed **primary**. Critically, it is the concrete
**support→primary integration point** (per `PRIMARY_SUPPORT_INTEGRATION_AR.md`):
the HR support activity (labour) is posted, as an analytic cost, onto the same
analytic account that later receives sale revenue — so profit-per-engagement is
computable. The `depends` (`hr`, `hr_hourly_cost`, `analytic`, `project`) wire
exactly this bridge.

## How to Drive It

Use the **run-odoo** skill (`odoo shell`):

- `env['account.analytic.line'].search([('project_id','!=',False)], limit=5).mapped(('project_id.display_name','unit_amount','amount'))`
  — see logged hours and their computed analytic cost.
- `t = env['project.task'].search([('timesheet_ids','!=',False)], limit=1); (t.effective_hours, t.remaining_hours, t.progress)`
  — inspect the effort roll-up.
- `p = env['project.project'].create({'name':'Demo','allow_timesheets':True}); p.account_id`
  — observe the auto-created analytic account.
- `curl -b session http://localhost:8069/my/timesheets` (auth=user) — the
  portal surface.
