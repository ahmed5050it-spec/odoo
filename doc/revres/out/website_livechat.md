# website_livechat — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + code-read of `addons/website_livechat/`, narrated per
> `PROMPT.md`. Odoo 19.0.*

The **Website Live Chat** module (`website_livechat`, category *Website/Live
Chat*, `application=False`, **`auto_install=True`**) is the **bridge** that wires
Odoo's generic live-chat engine into the website. It declares **zero new
models** — all 9 of its model files are `_inherit`-only extensions — and exists
purely to glue two existing subsystems together: it makes the `im_livechat`
chat button render on website pages, and it ties each anonymous chat session
(`discuss.channel` of `channel_type='livechat'`) to a tracked **`website.visitor`**
profile. Because it is auto-installed, it switches on automatically the moment
both `website` and `im_livechat` are present, so on most sites live chat *is* the
website-integrated variant. It is a thin module (1956 Python LOC, but mostly
inherited test helpers — the working models total ~390 LOC; 283 XML LOC) whose
value is integration, not new data.

## Role & Dependencies

| Depends on | Why (top dependency, 1 line) |
|------------|------------------------------|
| `im_livechat` | The engine: `im_livechat.channel`, the `discuss.channel` livechat session, `chatbot.script`, operator matching and the embeddable OWL widget — this module only patches them. |
| `website` | Supplies `website.visitor` (+ `website.track` page history), `website.page` cached-render hook, and the per-website config the chat button binds to. |

Only two dependencies are declared. **Capability added on top:** per-website
live-chat channel binding (`website.channel_id`), automatic injection of the
chat button into website page renders, **bidirectional visitor ↔ session
linkage** (operator sees who the visitor is, their page-visit history and prior
sessions; chatbot harvests the visitor's email/phone/country), and an
operator-initiated **"send chat request"** flow from the visitor backend.

## Data Model (the ERM)

The facts report `model_count: 0` and `inherit_only_count: 9` — **every model
here is an extension** (`_inherit` without `_name`), i.e. fields/methods bolted
onto models owned by `website`, `im_livechat`/`mail`, or `base`.

| Model (`_inherit`) | Role of the patch | #new fields | Key relations added |
|--------------------|-------------------|-----------:|---------------------|
| **`website.visitor`** | Enrich visitor with live-chat identity & history | 4 | `livechat_operator_id→res.partner`, `discuss_channel_ids→discuss.channel` (O2m), `session_count` |
| **`discuss.channel`** | Link the livechat **session** back to a visitor | 2 | `livechat_visitor_id→website.visitor`, `is_pending_chat_request` (Bool) |
| `website` | Hold the site's chat channel | 1 | `channel_id→im_livechat.channel` |
| `res.config.settings` | Expose that channel in Settings | 1 | `channel_id→im_livechat.channel` (related) |
| `im_livechat.channel` | Stamp visitor on new sessions; wizard-create channels | 0 | (behaviour only) |
| `chatbot.script` / `.step` | Test action + harvest visitor PII into bot vars | 0 | (behaviour only) |
| `website.page` | Inject chat info on cached page render | 0 | (behaviour only) |
| `ir.http` | Register `im_livechat` as a frontend-translation module | 0 | (behaviour only) |

**Central models of the bridge:** the `website.visitor` ↔ `discuss.channel`
pair — the new `livechat_visitor_id` FK and its reverse `discuss_channel_ids`
O2m are the join that the whole module is built to create. **Field-type
distribution** (Many2one 4, One2many 1, Boolean 1, Char 1, Integer 1): it is
**relational and join-oriented**, not attribute-rich — the few non-relational
fields (`session_count`, `livechat_operator_name`, `is_pending_chat_request`)
are derived/flag fields supporting that one join.

## Behavior & Surfaces

- **Routes:** **1** — `GET-ish` `type="http"`, **`auth="user"`**,
  `website=True`: `/chatbot/<model("chatbot.script"):chatbot_script>/test`
  (the facts truncate the path to `/chatbot/<model(`). It is an internal
  operator-only tool to *test* a chatbot script; it pre-creates a throwaway
  `discuss.channel` between the bot and the tester. The public visitor/operator
  RPC surface (get_session, message post, transcript) lives in the **parent**
  `im_livechat` and is reused via subclassing, not re-declared here.
- **Views:** the facts count **form 1** for *this module's own* records, but the
  XML actually delivers mostly **inherited view patches** into
  `website.visitor` (kanban/list/form/search — adding the "Chat" button,
  operator avatar, `session_count` stat button, and Available/In-Conversation
  filters) plus a chatbot-script form tweak and a `res.config.settings` page.
  UX is **backend operator tooling**, not a new public page.
- **Security:** **2 ACLs, 0 record rules, 0 new groups.** Both ACLs are
  read-only grants to the existing operator group `im_livechat_group_user`:
  read `website.visitor` and read `website.track` (so an operator can see a
  visitor's page-visit history). No new privilege boundary is introduced.

### Code-read: real cross-model side-effects (the point)

- **Chat-button injection into pages** — `website.page._post_process_response_from_cache`
  calls `request.website._get_livechat_channel_info()` on **every cached page
  response**; `website._get_livechat_channel_info` returns `channel_id.sudo().get_livechat_info()`
  (button text, channel name…). This is how the widget appears on website pages
  via the site's bound `im_livechat.channel`. (`models/website_page.py`,
  `models/website.py`)
- **Visitor ↔ session linkage (the core join)** — when a visitor starts a chat,
  `im_livechat.channel._get_livechat_discuss_channel_vals` looks up
  `website.visitor._get_visitor_from_request()` and stamps `livechat_visitor_id`
  onto the new session; conversely `website.visitor._compute_livechat_operator_id`
  / `_compute_session_count` read back through `discuss_channel_ids` so the
  backend shows "Speaking with X" and a chat count. (`models/im_livechat_channel.py`,
  `models/website_visitor.py`)
- **Operator-initiated chat request** — `website.visitor.action_send_chat_request`
  creates a `discuss.channel` flagged `is_pending_chat_request=True` (adding the
  operator to the channel's `user_ids`), creating a `mail.guest` for anonymous
  visitors. The visitor only receives it on their **next page navigation**:
  `webclient._process_request_for_all` (`init_livechat`) →
  `_link_visitor_to_livechat` finds the pending channel for that visitor and
  pushes it with `open_chat_window`. Starting a *visitor-initiated* chat cancels
  any stale pending operator request (`_close_livechat_session(cancel=True)`).
  (`models/website_visitor.py`, `controllers/webclient.py`, `models/im_livechat_channel.py`)
- **Visitor enrichment of the conversation** — `discuss.channel._to_store_defaults`
  ships visitor `country_id`, `page_visit_history`, `lang_id`, `partner_id` and
  a `requested_by_operator` flag to the operator's panel; `_get_visitor_history`
  surfaces the last 3 visited pages; `chatbot.script.step._chatbot_prepare_customer_values`
  back-fills the bot's collected email/phone/country **from the visitor record**
  when the chatbot doesn't already have them. (`models/discuss_channel.py`,
  `models/chatbot_script_step.py`)
- **Housekeeping & auto-config** — `discuss.channel.channel_pin` auto-`unlink`s
  an empty livechat channel (so an operator can re-request); `_merge_visitor`
  re-parents sessions on visitor merge; `message_post` bumps the visitor's
  last-visit timestamp. Creating a channel with context `create_from_website`
  binds it to `website.channel_id` + auto-attaches the welcome-bot rule.
  (`models/discuss_channel.py`, `models/website_visitor.py`, `models/im_livechat_channel.py`)

## Value-Configuration Classification

**Value model: `network` (Stabell & Fjeldstad value-network mediating
technology); activity_class: support/bridge** (it is *integration glue* over a
primary network engine). The mediation — connecting website visitors to
operators/chatbots in real time — is performed by the **parent** `im_livechat`
(the matching/routing engine, the bus channel, the widget). `website_livechat`
adds the **network's customer-identity and reach layer**: it attaches each
mediated session to a persistent `website.visitor` profile (page history, prior
sessions, operator-initiated outreach) and makes the chat reachable from every
website page. In network terms it strengthens the *network promotion / contract*
and *customer-identity* activities of an already-running infrastructure, rather
than transforming inputs (chain) or solving one client's bespoke problem (shop).
It is a **support/bridge module to a primary network activity** — consistent
with `auto_install=True` and zero own-models. (The architect baseline labelled
it `network`/`primary`; refined here to network-**bridge** given it owns no
mediation logic of its own — *inferred from code-read*.)

## How to Drive It

Use the **run-odoo** skill (`.claude/skills/run-odoo/`). With the server up and
a `-i website_livechat` database (website + im_livechat auto-pulled):

```python
# odoo shell — the visitor ↔ session join this module creates
visitors = env['website.visitor'].search([('session_count', '>', 0)])
print(visitors.mapped(lambda v: (v.display_name, v.session_count, v.livechat_operator_name)))

# the website's bound chat channel + what gets injected on every page
site = env['website'].get_current_website()
print(site.channel_id.name, site._get_livechat_channel_info())

# pending operator-initiated chat requests (await next visitor page-load)
env['discuss.channel'].search([
    ('channel_type', '=', 'livechat'),
    ('is_pending_chat_request', '=', True),
    ('livechat_end_dt', '=', False),
]).mapped(('name', 'livechat_visitor_id.display_name'))
```

- **Route to exercise:** the only own-route is operator-only:
  `curl -b <operator_session> 'http://localhost:8069/chatbot/<script_id>/test'`
  (auth=user) renders a sandbox chatbot conversation.
- Public visitor entry (get_session / message post) is served by the **parent**
  `im_livechat` controller — drive it there; this module only injects the
  visitor identity via the subclassed `_get_guest_name` ("Visitor #N").

## Open Questions

- **Cache-hook cost:** `website.page._post_process_response_from_cache` runs
  `_get_livechat_channel_info()` on *every* cached page render — verify it is
  cheap/cached and doesn't defeat full-page caching on high-traffic sites.
- **Guest re-linking race:** `_link_visitor_to_livechat` rewrites channel
  guest membership when a visitor's guest changes mid-flow — confirm the
  concurrent-tab / re-auth behaviour holds (the code itself flags a `TODO DBE`).
- **PII harvesting scope:** `_chatbot_prepare_customer_values` copies visitor
  email/phone/country into bot-collected values — verify consent/GDPR posture,
  as this silently enriches a contact from tracking data.
- **`uses_api_keys: true` provenance:** no endpoint, SDK, or HTTP call site
  exists in this module — confirm the flag is inherited from `website`/platform
  and that no key is required for live chat itself. *(inferred)*
