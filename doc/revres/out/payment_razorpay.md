# payment_razorpay — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Payment Provider: Razorpay** module (`payment_razorpay`, category
*Accounting/Payment Providers*, `application=False`, `auto_install=False`) is a
concrete **acquirer adapter** that plugs the generic Odoo `payment` engine into
**Razorpay**, the Indian PSP, to collect **card / UPI / netbanking / wallet**
payments. It owns **no models of its own** — three `_inherit` extensions
(`payment.provider`, `payment.transaction`, `payment.token`) graft Razorpay
credentials and 30-odd override methods onto the engine. Its entire reason to
exist is the external integration (metadata gap #7): server-to-server REST to
`api.razorpay.com`, a browser Razorpay Checkout SDK, OAuth self-onboarding through
an Odoo proxy, and a signature-verified settlement webhook.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `payment` | The provider/transaction/token state machine + `_send_api_request` HTTP plumbing — Razorpay only configures its hooks. |

**Adds on top:** a live Indian acquirer — card/UPI/netbanking/wallet collection via
Razorpay Orders + the client-side Checkout SDK, RBI-compliant eMandate tokenization
and recurring charges, full manual capture, partial+full refunds, merchant OAuth
self-onboarding, and automatic webhook registration.

## Data Model (the ERM)

| Model (`_inherit`) | #fields | Key relations |
|--------------------|--------:|---------------|
| `payment.provider` | +8 Char/Datetime | `code` selection_add `razorpay`; `razorpay_key_id` + `razorpay_key_secret` (Basic auth); `razorpay_webhook_secret`; OAuth `razorpay_account_id`/`refresh_token`/`public_token`/`access_token`/`access_token_expiry` |
| `payment.transaction` | +0 (16 methods) | `provider_id`, `token_id`; `provider_reference` == Razorpay Payment/Refund id; self→child refund tx |
| `payment.token` | +0 (1 method) | `provider_ref` == `'<customer_id>,<token_id>'` (eMandate) |

Secret/webhook/OAuth-token fields are all gated by `base.group_system`. No own
views (`xml_loc≈132` is form inheritance + QWeb templates + provider data); **0**
ACL/record-rules/groups — it leans entirely on payment's security.

## Behavior & Surfaces

- **Routes:** 3 — `/payment/razorpay/return` (public, csrf=False, save_session=False:
  HMAC-verifies `order_id|payment_id` with key_secret), `/payment/razorpay/webhook`
  (public, csrf=False: X-Razorpay-Signature HMAC of the raw body), and
  `/payment/razorpay/oauth/return` (auth=user: OAuth code→token exchange).
- **Frontend (static, gap #3):** 1 JS file, **0 OWL**, 0 registry adds — a single
  `PaymentForm.prototype` patch that opens the **Razorpay Checkout SDK** in the
  browser from `_get_specific_processing_values` (key_id/order_id/customer_id/
  public_token). Loaded into `web.assets_frontend`.

What metadata cannot show, established by reading the code:

- **`_get_specific_processing_values` / `_razorpay_create_customer` /
  `_razorpay_create_order`** — POST `customers` then `orders` to
  `api.razorpay.com/v1/` (amount in minor units, method code, optional eMandate
  `token` block), handing key_id/order_id/customer_id to the browser SDK. HTTP goes
  through `payment.provider._send_api_request`, pointed by `_build_request_url` and
  authenticated either HTTP **Basic** `(key_id, key_secret)` or, under OAuth, a
  **Bearer access-token** header that auto-refreshes when expired.
- **`_send_payment_request` (recurring) + capture/refund/void** — recurring token
  charges POST `payments/create/recurring` (guarded by a 36h RBI duplicate-charge
  window); `_send_capture_request` POSTs `payments/<id>/capture` (full-only);
  `_send_refund_request` POSTs `payments/<id>/refund` (partial OK, `notes.reference`
  for correlation); `_send_void_request` **raises UserError** — voids unsupported.
- **`RazorpayController._verify_signature`** — both inbound routes HMAC-SHA256 the
  payload (webhook: raw body × `razorpay_webhook_secret`; redirect: `order|payment`
  × `razorpay_key_secret`) and `hmac.compare_digest`; mismatch/missing → **HTTP 403
  Forbidden**. On success `_process` drives payment's `_set_pending/_authorized/
  _done/_error` state machine, mapping `const.PAYMENT_STATUS_MAPPING`.
- **OAuth self-onboarding** — `action_start_onboarding` redirects to Razorpay's
  authorize URL (with CSRF token); `/payment/razorpay/oauth/return` validates the
  CSRF token, POSTs `get_access_token` through the Odoo proxy
  `razorpay.api.odoo.com/api/razorpay/1`, stores the tokens, enables the provider,
  and auto-creates the webhook (`accounts/<id>/webhooks`, api v2).
- **Tokenization / eMandate** — `_extract_token_values` vaults a `payment.token`
  (`provider_ref='<customer_id>,<token_id>'`, card last4 / UPI vpa tail);
  `_razorpay_get_mandate_max_amount` caps the mandate (`const.MANDATE_MAX_AMOUNT`
  card 1,000,000 / upi 100,000 INR) for RBI recurring rules.
- **external integration (gap #7)** — `uses_api_keys=true`; two endpoints
  (`api.razorpay.com/{version}/`, `razorpay.api.odoo.com/api/razorpay/1`) plus the
  browser Checkout SDK. No `requests` import — all HTTP delegated to the parent
  engine. None of this is derivable from model/field metadata.

## Value-Configuration Classification

**Value model: Network (mediating-technology acquirer).** `payment_razorpay` is a
Stabell & Fjeldstad **value-network** component: it interconnects two parties who
would not otherwise transact — the cardholder/UPI payer and the merchant — by
linking the merchant into Razorpay's network. It shows all three mediating
activities: **network promotion & contract management** (OAuth onboarding, webhook
registration, key/token + eMandate management), **service provisioning** (creating
the Customer/Order, capturing/refunding per transaction), and **infrastructure
operation** (the api.razorpay.com link, the Checkout client channel, the
signed-webhook settlement loop). It inherits the parent `payment` engine's model
exactly. **activity_class = support** — payment acceptance is a finance/infra
support function (`application=False`, no end-user app). Classified
**network / support**, mirroring the sibling `payment_stripe`.

## How to Drive It

Use the `run-odoo` skill. With a `-i payment_razorpay` database (provider in test):

```python
# odoo shell — provider + feature flags
p = env['payment.provider'].search([('code','=','razorpay')], limit=1)
print(p.name, p.state, p.support_manual_capture, p.support_refund, p.support_tokenization)
# transactions + the Razorpay-specific override surface
tx = env['payment.transaction'].search([('provider_code','=','razorpay')], limit=1)
print(tx.reference, tx.state, tx.provider_reference)
print([m for m in dir(env['payment.transaction']) if m.startswith('_razorpay_')])
# webhook signature guard (expect HTTP 403 Forbidden on a missing/invalid header):
#   curl -X POST https://<host>/payment/razorpay/webhook -d '{}'   (no X-Razorpay-Signature)
# Razorpay test mode: UPI success@razorpay / test card 4111111111111111, future expiry, any CVC
```
