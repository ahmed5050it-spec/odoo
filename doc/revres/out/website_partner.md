# website_partner — Reverse-Engineering Brief

> *Generated by the revres workflow: explorer facts (`facts/website_partner.facts.json`
> + code-read of the module) → architect synthesis. DEEP record. Odoo 19.0.*

The **Website Partner** module (`website_partner`, category *Website/Website*,
`application=False`) is the thin, shared **base for publishing a partner's public
profile page** — the `/partners/<id>` detail page reused by resellers, customers
and events. It depends only on `website` and adds **no model of its own**: it
extends `res.partner` to make any contact publishable, defines the single public
detail route, and ships the reusable `partner_page` / `partner_detail` QWeb
skeleton that downstream channel/customer/event apps plug into.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `website` | Pulls the web platform: QWeb `website.layout`, the builder/snippet UX, `website.published.mixin`, `website.seo.metadata`, `ir.http._slug`. |

**Adds on top:** the publish toggle (`is_published`) + rich `website_description`
on contacts, the public `/partners/<id>` page, SEO/canonical-slug handling, and
the `left_column`/`right_column` extension slots consumed by `website_customer`,
`website_crm_partner_assign` and `event`.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`res.partner`** *(extension)* | Contact, now `_inherit` `website.seo.metadata` | +3 | gains `website.published.mixin` (`website_published` related `is_published`, computed `website_url`) |

New fields: `is_published` (Boolean, `tracking=True`), `website_description`
(Html, sanitized/translatable), `website_short_description` (Text, translatable).
No new tables, no security records, no `ir.rule` — visibility is enforced in
controller code, not in the ORM. The "data model" is really **two QWeb templates**
(`partner_page`, `partner_detail`) plus three columns on `res.partner`.

## Behavior & Surfaces

- **Route:** one — `GET /partners/<partner_id>` (`auth=public`, `http`,
  `website=True`). Deliberately **non-semantic** (raw string, not a model
  converter) because it `sudo()`-browses.
- **Views:** 1 form inherit (adds the `is_published` `website_redirect_button`)
  and **2 QWeb templates**. No backend list/kanban/graph — all UX is the
  parent's website builder.
- **Security:** 0 access rules, 0 record rules, 0 groups.

### Behavior metadata cannot show (code-read)

- **Publishing semantic:** flipping `is_published` makes a back-office contact a
  live profile; `_compute_website_url` points `website_url` at `/partners/<slug>`.
- **Access gate (the real security):** the controller renders only if
  `website_published` **OR** the caller has `website.group_website_restricted_editor`
  — else `request.not_found()`. Non-canonical slugs **redirect** to the canonical
  one (SEO de-dup).
- **Chatter side-effect:** `_track_subtype` posts `mt_partner_published` /
  `mt_partner_unpublished` subtypes on publish toggle; the data file
  force-publishes `base.main_partner`.
- **Extensible base page:** `partner_detail` exposes empty `left_column`/
  `right_column` slots + `oe_structure` drop-zones; `website_customer` and
  `website_crm_partner_assign` xpath-inherit and fill them (references, reseller
  grade, the `/partners` listing + faceted grade/country routes live downstream,
  not here).
- **No own frontend:** `extract_frontend` → `present=false` (0 JS, 0 OWL, 0
  bundles); all interactivity is borrowed from `website`.

## Value-Configuration Classification

**Value Network, support activity.** Like its parent `website`, this is a
**network** (Stabell & Fjeldstad mediating technology): it exposes `res.partner`
records as public profiles, mediating between visitors and partners, and its
worth grows with the number of published partners and consuming apps. But unlike
`website` (primary), `website_partner` is **support**: a thin `application=False`
base library — one inherited model, one detail route, no listing, no UX — that
**provisions** a shared publishing capability the truly customer-facing modules
(reseller directory, customer references, events) build their primary service on.

## How to Drive It

Use the `run-odoo` skill. With the server up and a `-i website_partner` database:

```python
# odoo shell
pub = env['res.partner'].search([('is_published', '=', True)])
print([(p.display_name, p.website_url) for p in pub])
p = env.ref('base.main_partner'); print(p.is_published, p.website_url)
```
```bash
curl -s http://localhost:8069/partners/1 | head           # rendered profile
curl -s -o /dev/null -w '%{http_code}\n' \
     http://localhost:8069/partners/999999                # expect 404 (unpublished/missing)
```
