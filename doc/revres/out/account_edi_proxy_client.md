# account_edi_proxy_client — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Proxy features for account_edi** module (`account_edi_proxy_client`,
category *Accounting/Accounting*, `application=False`) is the **EDI proxy /
access-point client** for e-invoicing. It registers a per-company identity on an
external access point (Odoo's IAP service / networks like **Peppol**), signs and
encrypts requests with an RSA key, and exchanges e-invoice documents over that
proxy. It depends only on `account` + `certificate` and ships **no concrete
network itself** — `proxy_type` and the proxy URLs are extension stubs that
localization modules (Peppol, `l10n_it_edi`, Nemhandel) subclass.

## Behaviour Beyond Metadata (code-reads)

1. **`_register_proxy_user` (enrolment)** — generates an RSA keypair via
   `certificate.key._generate_rsa_private_key`, POSTs
   `{dbuuid, company_id, edi_identification, public_key(PEM), proxy_type}` to
   `<server_url>/iap/account_edi/2/create_user`, and persists the returned
   `id_client` + `refresh_token` as a new user. `edi_identification` is the
   network address (the VAT for Peppol). Demo mode fakes credentials, no call.
2. **`_make_request` (signed JSON-RPC transport)** — wraps a JSON-RPC 2.0
   envelope, hard-blocks `edi_mode=='demo'`, `requests.post`s with a 30 s timeout
   and the `OdooEdiProxyAuth` signer. Handles `proxy_error`: `refresh_token_expired`
   → `_renew_token` + cursor commit + retry; `no_such_user` → `active=False`;
   `invalid_signature` → database-duplication warning.
3. **`OdooEdiProxyAuth` (cryptographic signature)** — signs the canonical message
   `timestamp|path|id_client|sorted-query|sorted-body` either with **HMAC-SHA256**
   keyed by the base64 `refresh_token` (default) or an **RSA** signature via
   `private_key._sign` (asymmetric fallback to resync after a DB copy/restore),
   emitting `odoo-edi-signature` / `-type` headers for message integrity.
4. **`_renew_token` + `_decrypt_data`** — token renew row-locks the user
   (`lock_for_update`), POSTs `/iap/account_edi/1/renew_token`; the 24h expiry
   stops two databases sharing credentials. Inbound payloads use envelope
   encryption: RSA-decrypt the symmetric key, then Fernet-decrypt the body.
5. **External integration (static, gap #7)** — 1 outbound HTTP call site via the
   `requests` SDK, no stored api-keys; egress is the signed proxy POST. Endpoints
   are not hard-coded here — URLs come from `_get_proxy_urls()` in localizations.

**Rationale:** e-invoicing transport and identity infrastructure extending the
accounting stack — it creates no accounting value of its own, only signs,
encrypts and carries the invoices that primary activities already produced. The
access point it connects to is itself a value *network* (mediating identity and
document interchange), but at the enterprise level this client is a **support**
function. Maps to the AR/AP e-invoicing-compliance facet of APQC 9.2.x / 9.5.x.

## Fit-to-Standard & Open Questions

**Standard out-of-box:** per-company proxy enrolment with RSA keypair; signed
JSON-RPC transport (HMAC-SHA256, RSA fallback); 24h token renewal with retry &
desync detection; RSA-wrapped-Fernet decryption; prod/test/demo modes; pluggable
`proxy_type`/URL hooks; credential security (token gated to system group).

**Common gaps:** no concrete network ships (empty `proxy_type`, `_get_proxy_urls`
returns `{}` — needs a localization); endpoints supplied by the extending module;
no inbound routing of decrypted docs to `account.move` here; no dedicated UI
beyond an admin form/list.

**Open questions:** which modules populate `proxy_type` and the IAP/Peppol host
URLs; the full `/iap/account_edi/*` contract and `proxy_error` catalogue; how
decrypted documents reach `account.move`; lifecycle of `is_token_out_of_sync` /
`token_sync_version`.
