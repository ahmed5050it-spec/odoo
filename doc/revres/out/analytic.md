# analytic — Reverse-Engineering Brief

> *Generated by the code-explorer + code-architect workflow: facts from
> `extract_module.py`/`extract_frontend.py` + behavioral reads of
> `models/{analytic_account,analytic_line,analytic_plan,analytic_distribution_model,analytic_mixin}.py`.*

The **Analytic Accounting** module (`analytic`, category *Accounting/Accounting*,
v1.2, `application=False`, `auto_install=False`) is the **cost/revenue
aggregation backbone** of an Odoo deployment. It owns no documents and no HTTP
routes; instead it provides a *dimensional ledger* — **`account.analytic.line`**
(the universal cost/revenue line) grouped on **`account.analytic.account`** (the
"value unit": a project, order, or cost centre) — onto which every other module
posts. It depends only on `base`, `mail`, and `uom`. Per
`PRIMARY_SUPPORT_INTEGRATION_AR.md`, this module is **THE join point** where
support-activity costs meet primary-activity value: HR labour (`hr_timesheet`),
purchasing, and expenses (`hr_expense`) post analytic *cost* lines onto the same
analytic account that sale revenue (`sale_timesheet`) *credits*, so
profit-per-value-unit becomes computable.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `base` | ORM, `res.company`/`res.partner`/`res.users`, `ir.model.fields` (for the dynamic plan columns). |
| `mail` | `account.analytic.account` `_inherit`s `mail.thread` — accounts are tracked/chattered. |
| `uom` | `account.analytic.line.product_uom_id` — quantity unit on the cost line. |

**Provides on top:** a multi-dimensional analytic chart (plans → accounts), the
analytic distribution mechanism (a percentage JSON split across accounts), an
auto-distribution rules engine, and balance/debit/credit roll-up per value unit.
Downstream consumers (`hr_timesheet`, `sale_timesheet`, `project`, `hr_expense`,
`purchase`, `account`) inherit `account.analytic.line` / `analytic.mixin` to feed
this vessel — none of which is visible from `analytic`'s own metadata.

**Central pair:** `account.analytic.line` (where value lands) and
`account.analytic.account` (where it aggregates). The two abstract mixins are the
reuse surface every other app grafts onto. The field mix is **relational +

allocation* layer, not a transactional document.

### Behavior beyond metadata (code-read)
- **`account.analytic.line` is the universal cost/revenue line.** Every cost and
  revenue line in Odoo lands here, grouped on `account.analytic.account`.
  `_compute_debit_credit_balance` aggregates line `amount` (≥0 credit / <0 debit)
  per plan column, currency-converted to the company currency, yielding
  `balance`/`debit`/`credit` on the account — the **support↔primary join** where
  posted costs net against posted revenue.
- **Dynamic plan columns (`_sync_plan_column` / `_column_name`).** Plans are not
  just a hierarchy: each *root* plan materialises a real `m2o` column on every
  `analytic.plan.fields.mixin` model. The project root plan uses the fixed
  `account_id`; every other root plan gets a generated `x_plan{id}_id`
  `ir.model.fields` column (created/renamed/dropped on plan create/write/unlink,
  with a partial btree index). `account.analytic.account.write` migrates line data
  across columns via raw SQL `UPDATE` when a plan changes. Pure runtime schema
  mutation.
- **Auto-distribution (`account.analytic.distribution.model._get_distribution`).**
  A rules engine that pre-fills `analytic_distribution` on documents:
  `_get_applicable_models` matches by `partner_id` / `partner_category_id` /
  `company_id` (each optional, `False` = wildcard) and merges matches, skipping any
  whose root plan is already applied. This is how an invoice/SO/expense inherits an
  analytic account from its partner without manual entry.
- **`analytic.mixin.analytic_distribution` (JSON split + GIN index).** The reusable
  carrier: a `Json` map of *comma-joined account ids → percentage*. A GIN index on
  the split JSON keys makes "which docs hit this account" searchable, and
  `_read_group_groupby` rewrites group-by-distribution into a per-account subquery.
  `_validate_distribution` enforces mandatory plans sum to 100%; `_merge_distribution`
  recombines partial (`__update__`) edits proportionally.

## Value-Configuration Classification

**Support backbone — value-model `support`, activity_class `support`.** Analytic
Accounting is the financial **cost-aggregation backbone** of the value system, not
a primary value-creating activity. It supplies the dimensional ledger onto which
other modules post; under Stabell & Fjeldstad / Porter it is firm-infrastructure
**support**. Critically, it is the concrete **support→primary integration vessel**
(per `PRIMARY_SUPPORT_INTEGRATION_AR.md`): `account.analytic.line` is **THE join**
where support costs (HR labour via `hr_timesheet`, purchasing, expenses via
`hr_expense`) meet primary-activity value (sale revenue via `sale_timesheet`,
project delivery) on the **same `account.analytic.account`** — so net value per
unit is computable. The dynamic plan columns and the distribution model exist
precisely to route every transaction into that shared vessel. It belongs to no
single primary value configuration; it is the *vessel that connects them all*.

## APQC PCF Hint

**9.0 Manage Financial Resources** — specifically **9.3 Perform cost accounting /
management accounting**: maintaining the analytic (cost) ledger and allocating
cost/revenue to value units. Consistent with `apqc_odoo_map.tsv`, which classes
the surrounding finance postings (`account.move` receivable/payable) as
**support** under 9.x; analytic is the dimensional substrate those postings tag.

## How to Drive It

Use the **run-odoo** skill (`odoo shell`):

- `env['account.analytic.account'].search([], limit=5).mapped(('display_name','plan_id.name','balance'))`
  — accounts (value units) with their plan and net balance.
- `env['account.analytic.line'].search([], limit=5).mapped(('name','amount','account_id.display_name'))`
  — the universal cost/revenue lines and where they post.
- `env['account.analytic.plan']._get_all_plans()` then `plan._column_name()`
  — the project plan + other root plans and the dynamic column each owns.
- `env['account.analytic.distribution.model']._get_distribution({'partner_id': <id>, 'company_id': <cid>})`
  — preview the analytic distribution auto-applied for a partner.
- No `curl` surface: the module exposes **0 routes**.
