# pos_self_order_razorpay — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from

> controller & self-order JS. Odoo 19.0.*

The **POS Self Order Razorpay** module (`pos_self_order_razorpay`, category
*Sales/Point Of Sale*, `application=False`, author *Odoo S.A.*, LGPL-3) is a
thin, **auto-installed** bridge that "allows customers to pay by Razorpay POS
Terminal" from the **self-order kiosk**. It sits between `pos_razorpay` (the
Razorpay P2P device integration) and `pos_self_order` (the customer-facing
kiosk/QR app) and adds **no new model and no new fields**: it overrides two
`pos.payment.method` methods, exposes **two public jsonrpc routes**
(poll status / cancel), and patches the kiosk OWL app. ~110 Python LOC, 0 XML,
3 JS files. The order and tender are recorded by the host `pos_self_order`
plumbing; this module only wires the **Razorpay handshake** into that flow.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `pos_self_order` | The kiosk self-order app. Provides `/kiosk/payment/<config>/kiosk`, the `_payment_request_from_kiosk` hook, `_load_pos_self_data_domain`, `pos.order._send_payment_result` (PAYMENT_STATUS bus), and the public OWL `PaymentPage`/`SelfOrder` it patches. |
| `pos_razorpay` | The Razorpay POS device. Provides `use_payment_terminal='razorpay'`, the device/credential fields, and `razorpay_make_payment_request` / `razorpay_fetch_payment_status` / `razorpay_cancel_payment_request` (`pay`/`status`/`cancel` against the Razorpay POS API; INR; `p2pRequestId`). |

**Adds on top:** kiosk self-payment via the Razorpay device — a `_payment_request_from_kiosk` override, a `_load_pos_self_data_domain` override exposing the terminal to the kiosk client, two poll/cancel routes, and a JS `Razorpay` polling handler with QUEUED re-queue logic.

## Behavior & Surfaces

- **Routes (2, public jsonrpc, `website=True`):**
  `/pos-self-order/razorpay-fetch-payment-status/` and
  `/pos-self-order/razorpay-cancel-transaction/`, subclassing
  `PosSelfOrderController`, gated by `_verify_pos_config(access_token)` and an
  order search by `(id, config_id)` (`Unauthorized` if missing).
- **The handshake (code-read):** the **trigger** is the host's
  `/kiosk/payment/<config>/kiosk`. The JS posts the serialized order; the host
  runs `process_order` (creates the `pos.order` in the open session) and calls
  `payment_method._payment_request_from_kiosk(order)`. This override (only when
  `use_payment_terminal == 'razorpay'`) sends `amount = order.amount_total`
  (**unscaled** — unlike the Pine Labs sibling), `referenceId =
  '<config>/Order/<id>/<uuid4>'`, and calls `razorpay_make_payment_request`
  (`pay` → `p2pRequestId`).
- **Settlement (code-read):** the client polls
  `razorpay-fetch-payment-status` → `razorpay_fetch_payment_status` (`status`;
  parent maps Razorpay messageCodes → AUTHORIZED / QUEUED / SENT / RECEIVED /
  FAILED). On **`"AUTHORIZED"`** the route writes a `pos.payment` via
  `order.add_payment({amount, transaction_id=txnId,
  payment_method_authcode=authCode, card_brand=paymentCardBrand,
  card_no=cardLastFourDigit, payment_ref_no=externalRefNumber,
  razorpay_reverse_ref_no=reverseReferenceNumber, …})`, then
  `action_pos_order_paid()` and, if `self_ordering_mode == 'kiosk'`,
  `call_bus_service(order, 'Success')` → `_send_payment_result('Success')`
  (`config._notify('PAYMENT_STATUS')` + receipt + kitchen order). On FAILED/empty
  → `call_bus_service(order, 'fail')`. Cancel → `razorpay_cancel_payment_request`
  (`cancel`) then `call_bus_service(order, 'fail')`.
- **Exposure (code-read):** `_load_pos_self_data_domain` OR-extends the public
  data domain so Razorpay methods reach the kiosk client **only** when
  `self_ordering_mode == 'kiosk'`.
- **Frontend (gap #3):** 3 JS files, **0 OWL components**, bundle
  `pos_self_order.assets`. A non-OWL `Razorpay` class (`razorpay.js`) +
  `PaymentPage.prototype` / `SelfOrder.prototype` patches. `Razorpay.startPayment`
  posts to `/kiosk/payment`, then `paymentPolling()` hits the status route every
  **10 s** (`REQUEST_TIMEOUT`), correlating on `p2pRequestId` in `localStorage`;
  a **`QUEUED`** status triggers a **cancel + restart**, and a **90 s** inactivity
  timer auto-fires the cancel route. Client logic, not in Python metadata.
- **Integrations (gap #7):** **0 direct call-sites here** — the HTTPS calls to the
  Razorpay POS API (`RazorpayPosRequest._call_razorpay`) live in `pos_razorpay`.

## Value-Configuration Classification

**Primary model: Value Chain (transform).** `pos_self_order_razorpay` is a thin
payment-terminal bridge inside the in-store self-service checkout: its only act
is collecting the customer's tender on the Razorpay device and completing a
`pos.payment` on the kiosk `pos.order`. It inherits the `point_of_sale →
pos_self_order` **chain / primary** sell classification. It has a **network**
overtone (mediating between the diner and the Razorpay device/API via public
poll/cancel routes), but the value logic it completes is the chain sell. *(The
host `pos_self_order` is itself classed `network` as the mediating self-order
channel; this child adds only a tender device to that channel's kiosk mode.)*

## Fit-to-Standard & How to Drive It

**Standard out-of-box:** kiosk order paid on a Razorpay device
(`use_payment_terminal='razorpay'`); order creation + device request in one
`/kiosk/payment` round-trip; 10 s status polling until `AUTHORIZED` →
auto `pos.payment` + order-paid; `QUEUED` auto cancel+restart and ~90 s
inactivity auto-cancel with a PAYMENT_STATUS `fail` signal; terminal auto-exposed
to the kiosk only in kiosk mode.

**Common gaps:** **INR-only** (parent constraint); completion depends on the
polling tab staying alive; refund/void live in `pos_razorpay` and aren't exposed
to the kiosk; a stuck `QUEUED` could loop cancel+restart without operator
visibility; depends on `pos_razorpay` reaching the Razorpay POS API.

```python
# Razorpay methods on kiosk configs
env['pos.payment.method'].search([('use_payment_terminal','=','razorpay')]) \
    .mapped(('name','razorpay_tid','razorpay_test_mode','config_ids.self_ordering_mode'))

# kiosk-sourced Razorpay tenders
env['pos.order'].search([('source','=','kiosk'),
    ('payment_ids.payment_method_id.use_payment_terminal','=','razorpay')], limit=5) \
    .mapped(('name','state','amount_total'))
```

Open a kiosk POS (`self_ordering_mode='kiosk'`) with a Razorpay method and place
an order to trigger `PaymentPage.startPayment → Razorpay.startPayment`.

## Open Questions

- Exact OWL reaction to the `PAYMENT_STATUS` bus message after the server already
  wrote the `pos.payment` on the poll.
- Robustness of the `QUEUED` cancel+restart loop when the device repeatedly queues.
- Race between the 90 s inactivity cancel and a late device `AUTHORIZED`.
- Idempotency of repeated `razorpay-fetch-payment-status` calls returning
  `AUTHORIZED` (double `add_payment` guarded only by `action_pos_order_paid`).
