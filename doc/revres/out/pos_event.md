# pos_event — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/`, narrative per
> `PROMPT.md`. Odoo 19.0.*

The **POS - Event** module (`pos_event`, category *Technical*,
`application=False`) is the **bridge** that lets a cashier sell event tickets at
the Point of Sale: a ticket is rung up as an ordinary `pos.order.line` and each
attendee becomes an `event.registration` linked to that line. It is
**auto_install=True** — it activates automatically when both `point_of_sale` and
`event_product` are present — and is a thin link module (713 Python LOC, 0 own
routes, 3 added fields). Its whole job is to splice the offline POS checkout
chain onto the event ticketing/seat-capacity network.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `point_of_sale` | Host app: the offline OWL till, `pos.order`/`pos.order.line`/`pos.session`/`pos.config` it extends. |
| `event_product` | Makes a ticket a sellable `product.product` (`service_tracking='event'`), so it can be a POS line. |

**Adds on top:** in-POS ticket/slot selection with live seats, per-attendee
registration capture, cross-till anti-oversell broadcast, and badge email /
ticket printing on payment.

## Data Model (the ERM)

| Model (`_name`) | Kind | #fields | Key relations |
|-----------------|------|--------:|---------------|
| **`event.registration`** | extension + `pos.load.mixin` | +2 | `pos_order_line_id→pos.order.line` (ondelete=cascade), `pos_order_id` (related) |
| `pos.order.line` | `_inherit` (extension) | +2 | `event_ticket_id→event.event.ticket`, `event_registration_ids→event.registration` |
| `pos.order` | `_inherit` (extension) | +1 | `attendee_count` (computed over `lines.event_registration_ids`) |
| `event.event` | extension + `pos.load.mixin` | +1 | `image_1024` (PoS image); ships event/ticket/slot catalogue to the till |
| `event.event.ticket` / `event.slot` / `event.question` (+answer/registration.answer) | extension + `pos.load.mixin` | +0 | loaded into the POS bootstrap payload, read-only at the till |

**No new transaction model** — the module's entire data contribution is two FKs
joining the `pos.order` chain to the `event.registration` network. Field types
are purely relational (`Many2one` 3, `One2many` 1, `Integer` 1, `Image` 1):
this is wiring, not a new entity. The `_inherit`-without-`_name` rows
(`pos.order`, `pos.order.line`, `pos.config`, `pos.session`) are extensions of
POS core.

## Behavior & Surfaces

- **Routes:** 0 — no own web/RPC surface. It rides the `point_of_sale` `/pos/ui`
  terminal app and the `pos.order` `sync_from_ui` RPC.
- **Views:** 0 list/form/kanban of its own beyond small inherited additions
  (registration/event/pos.order view tweaks); the real UI is OWL.
- **Security:** 3 access rules, **0 record rules**, **0 groups** —
  `point_of_sale.group_pos_user` gets create/read/write on `event.registration`
  and read-only on `event.event` / `event.event.ticket`.
- **Behavior beyond metadata (code-read):** selling is driven in the browser —
  `ProductScreen.prototype` is patched so `addProductToOrder` runs
  `EventSlotSelectionPopup → EventConfiguratorPopup → EventRegistrationPopup`,
  then `addLineToCurrentOrder({event_ticket_id})` and
  `pos.models['event.registration'].create({pos_order_line_id})` per attendee.
  Server-side, `event.registration.create/write → _update_available_seat →
  pos.config._update_events_seats → _notify('UPDATE_AVAILABLE_SEATS')`
  broadcasts remaining seats to **every open till** (anti-oversell), and
  `_compute_registration_status` slaves the registration to the order (cancel if
  order cancelled, `free` if total zero, else `sold`/`open`).
  `action_pos_order_paid → send_paid_order_mail → action_send_badge_email`; a
  refund in `_process_order` writes `state='cancel'` on the matching
  registrations. `pos.session._load_pos_data_models` ships the event/ticket/slot/
  question models into the POS bootstrap via `pos.load.mixin`.
- **Frontend (static):** 11 JS, 6 XML, 3 OWL components
  (`EventConfiguratorPopup`, `EventRegistrationPopup`, `EventSlotSelectionPopup`)
  in `point_of_sale._assets_pos`; **no new screens/services** — 8 prototype
  patches splice the flow in. No external HTTP/SDK/api-key usage (gap #7 empty).

## Value-Configuration Classification

**Primary model: Value Chain (transform), customer-facing.** `pos_event` is a
**chain** in Stabell & Fjeldstad terms: its originating, dominant operation is a
retail **sell** — a ticket is tendered as a normal POS line and paying for it
*also* creates the attendee registrations, exactly as `sale` confirmation spawns
downstream documents. The act it adds value to is the in-store sale (the
Market-and-Sell primary activity of `point_of_sale`/`sale`); the registrations
are a triggered side-effect, not a separate mediation business. It is the
**BRIDGE** point: `point_of_sale` (chain) ←→ `event` (network). The event side
it bridges *into* is a network (seat-capacity mediation), but this module's own
code centre of gravity — POS order line, `action_pos_order_paid`,
refund-to-cancel, badge email — sits on the chain/selling side, so **chain** is
the correct primary call over **network**. A **primary** activity, not support.

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — selling a ticket at the counter
is a sell motion realized as a till (the 3.5 manage-sales-orders family as a POS
line), consistent with the `sale` and `point_of_sale` records; downstream
attendance/communications belong to the `event` module, not here.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and a
`-i pos_event` database:

```python
# odoo shell
pol = env['pos.order.line'].search([('event_ticket_id','!=',False)], limit=5)
print(pol.mapped(('order_id.name','event_ticket_id.name','qty')))
regs = env['event.registration'].search([('pos_order_id','!=',False)], limit=5)
print(regs.mapped(('name','state','sale_status','pos_order_id.name')))
print(env['pos.order'].search([('attendee_count','>',0)], limit=5)
      .mapped(('name','state','attendee_count')))
# browse /pos/ui/<config_id>, add an event product to fire the slot/ticket popups
```
