# event_booth — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/`, narrative per
> `PROMPT.md`. Odoo 19.0.*

The **Events Booths** module (`event_booth`, category *Marketing/Events*,
`version 1.1`, `application=False`) adds sellable exhibitor booths/stands to an
event. It lets an organizer define a catalog of booth categories, attach a fixed
set of booths to each event (manually or seeded from an event type), and assign
each booth to a renting exhibitor — flipping the booth from *available* to
*unavailable* and logging a booked note on the event chatter. It is **not**
auto-installed and depends only on `event`. Its center of gravity is the
`event.booth` model, mixed in from the `event.type.booth` template plus
`mail.thread`/`mail.activity.mixin`. This is the backend side only; pricing,
checkout and the public storefront live in `event_booth_sale` /
`website_event_booth`.

adding `event_id`, the renter and contact fields, and the status.

## Behavior beyond metadata (code-read)

- **State + availability:** `state` is a 2-value Selection available/unavailable
  (default available, `group_expand`, tracked). `is_available` is a non-stored
  compute with a custom `_search_is_available` mapping `in`/`not in` onto the
  underlying `state`; every counter and kanban column hangs off this one field.
- **Booking = a state transition, not a document:** `action_confirm(additional_values)`
  merges `{'state':'unavailable'}` with extra vals and calls `write()`. `write()`
  snapshots still-available booths, and on transition to *unavailable* calls
  `_action_post_confirm` → `_post_confirmation_message`, which posts the
  `event_booth_booked_template` message on the **event** chatter under the
  `mt_event_booth_booked` subtype. `create()` of an already-unavailable booth
  posts the same note.
- **Renter capture:** `partner_id` (string "Renter", tracked) plus
  `contact_name/email/phone` — stored editable computes that default-fill from
  the partner only when empty, so the on-site contact can differ from the renter.
- **Booths from event-type templates:** `event.event._compute_event_booth_ids`
  (stored, `precompute`) emulates an onchange — when `event_type_id` changes it
  unlinks only still-available booths and recreates one booth per
  `event_type_booth_ids` line, copying the whitelisted `['name','booth_category_id']`.
  `_get_default_booth_category` auto-picks the sole category when only one exists.

## Security & Policies

9 access rules, **no** module-specific record rules or groups — it reuses the
inherited event groups: `group_event_registration_desk` (read), `group_event_user`
(manage booths), `group_event_manager` (manage booths + categories). Key policies:
the available→unavailable booking transition is enforced in the `write()` override
(not a workflow); the event-type re-sync protects already-booked booths by only
removing available ones; `booth_category_id` is `ondelete='restrict'`.

## Classification

| Field | Value |
|-------|-------|
| **value_model** | `network` (event value-network — booths are an exhibitor-facing offering mediated through the event) |
| **activity_class** | `primary` |
| **apqc_category** | `3.0 Market and Sell Products and Services` (event sponsorship / booth sales) |

The economic logic is capacity/availability mediation: a fixed set of booths per
event, each matched to an exhibitor, with availability rollups and chatter
promotion of bookings — mediating-technology (network) logic, not a transformation
chain or per-case shop. Selling/allocating exhibitor booth space is a sell motion;
the paid checkout itself sits in `event_booth_sale`.

## Fit-to-Standard

- **Standard:** booth categories (image/description/sequence), per-event booths
  with available/unavailable status + group_expand kanban, booth templating from
  event types, renter assignment with editable contact fields, booking that flips
  status and logs to the event chatter, plus available-booth counters and pivot/
  graph analysis.
- **Typical fits:** exhibitions/trade shows with a fixed set of sellable stands;
  sponsor/exhibitor management by category; reusing a booth layout across recurring
  events via event types.
- **Common gaps:** paid booth checkout/pricing (`event_booth_sale`), public website
  booth selection (`website_event_booth`), floor-plan/spatial layout, and any
  approval workflow beyond the binary status.
