# pos_safaricom — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from
> `extract_module.py` / `extract_frontend.py` + code-read of the models &
> controllers. Odoo 19.0.*

The **POS Safaricom** module (`pos_safaricom`, category *Sales/Point of Sale*,
`application=False`, author *Odoo S.A.*, LGPL-3) "integrate[s] your POS with the
Safaricom Payment Provider" — i.e. it adds **M-Pesa mobile-money tender at the
till** for the Kenyan market. It is a thin, single-dependency
(`depends=['point_of_sale']`) payment bridge: it turns a `pos.payment.method`
into a Safaricom/M-Pesa terminal, talks to the **Safaricom Daraja API**
(OAuth + STK push + C2B + QR), and completes the in-progress `pos.payment` when
the asynchronous customer confirmation arrives on a public callback. ~673 Python
LOC, 1 new model + 1 inherit, 3 public routes, a small OWL popup.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `point_of_sale` | The only dependency. Provides `pos.payment.method`, `pos.config`, `pos.payment`, `pos.session`, the bus `_notify`, and the OWL terminal it plugs a tender screen into. |

**Adds on top:** a `('safaricom','M-Pesa')` payment-terminal option, two M-Pesa
flows (M-PESA Express STK push and Lipa na M-PESA / C2B till), scan-to-pay QR,
per-method Daraja credentials, three public callback routes, and a
`MpesaTransactionPopup` on the payment screen.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Notes |
|-----------------|-------------|--------:|-------|
| **`pos.payment.method`** *(inherit)* | POS Payment Methods, extended | +6 | Adds `consumer_key`, `consumer_secret`, `business_short_code` ('shortcode-tillnumber'), `passkey`, `safaricom_test_mode`, `safaricom_payment_type` (`mpesa_express`/`lipa_na_mpesa`); 20 methods. |
| `transaction.lipa.na.mpesa` *(new)* | Transaction Lipa na M-PESA | 5 | C2B receipt buffer: `trans_id`, `name`, `amount`, `number`, `received_at`. No relations — matched to a tender by `trans_id`. |

No standalone views (an inherited `pos_payment_method_views.xml` adds the
credential fields to the payment-method form); 1 access rule, no record rules,
no groups.

## Behavior & Surfaces

- **Routes (3, all public http, csrf-disabled):** `/pos_safaricom/callback`
  (M-Pesa Express STK result), `/c2b/validation/callback` (C2B pre-charge
  validation), `/c2b/confirmation/callback` (C2B payment confirmation). Each
  recovers the `payment_method_id` from a `hash_sign`-signed `?payload`
  (`verify_hash_signed`, 6h expiry) before acting — the only auth on the routes.
- **Outbound STK push (code-read):** `mpesa_express_send_payment_request`
  first calls `_get_bearer_token` (HTTPBasicAuth GET to Daraja
  `oauth/v1/generate` with consumer key/secret → `access_token`), builds the
  base64 `_get_password = b64(shortcode+passkey+timestamp)`, formats the phone
  to `254XXXXXXXXX`, and POSTs the STK payload (Bearer token) to
  `stkpush/v1/processrequest`. On `ResponseCode '0'` it returns **`success=False`
  on purpose** — captures `CheckoutRequestID`/`MerchantRequestID` and waits.
- **Confirmation (code-read):** the STK callback runs `_notify_stk_callback`,
  which parses `stkCallback` (`ResultCode==0`), pulls `MpesaReceiptNumber`/phone
  from `CallbackMetadata`, finds every **open** `pos.session` on that method, and
  pushes a `SAFARICOM_LATEST_RESPONSE` bus notification so the OWL terminal
  completes the `pos.payment`. C2B confirmation calls `_create_payment_transaction`
  (dedupe on `trans_id`, create `transaction.lipa.na.mpesa`, fire
  `NEW_LIPA_NA_MPESA_TRANSACTION`); `mark_transaction_used` unlinks it when the
  cashier applies it.
- **Frontend (gap #3):** the cashier flow is OWL/JS — 3 JS / 1 XML adding
  `MpesaTransactionPopup`, a `payment_safaricom.js` payment-interface, and a
  `PosStore.prototype` patch into `point_of_sale._assets_pos` (+ a test tour).
  The screen logic / bus-notification handling is not in Python metadata.
- **Integrations (gap #7):** 4 `requests` call-sites to the Safaricom **Daraja**
  API over HTTPS using consumer key/secret + passkey held on the payment method —
  `oauth/v1/generate`, `stkpush/v1/processrequest`, `c2b/v2/registerurl`,
  `qrcode/v1/generate` — with `sandbox.safaricom.co.ke` vs `api.safaricom.co.ke`
  selected by `safaricom_test_mode`. Lipa na M-PESA auto-registers its callback
  URLs (`lipa_na_mpesa_register_urls`) on `create`.

## Value-Configuration Classification

**Primary model: Value Chain (transform).** `pos_safaricom` is a thin
payment-collection extension of `point_of_sale`, so it inherits the parent's
**chain / primary** classification: the act it adds — capturing the customer's
M-Pesa tender at the till and completing a `pos.payment` on the originating
`pos.order` — sits inside the retail **Sell/Deliver** checkout. Caveat: it has a
strong **network** overtone, being an outbound integration that mediates between
the buyer's phone and the Safaricom Daraja mobile-money infrastructure (OAuth +
STK push + asynchronous bus-driven confirmation) — but the value logic it
participates in is the chain sell transaction.

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — collecting payment to close the
in-store sale is part of selling/closing the counter transaction, mirroring the
`point_of_sale` parent rather than treasury/AR (APQC 9.0), which is realized
downstream by the base POS session closing entry.

## Fit-to-Standard & Open Questions

**Standard out-of-box:** register M-Pesa as a POS terminal; M-PESA Express STK
push to the customer's phone; Lipa na M-PESA C2B with auto-registered callbacks;
scan-to-pay QR; sandbox/live switch per method; async confirmation via signed
public callbacks + POS bus notifications.

**Common gaps:** hardening of the public csrf-disabled callbacks (replay/abuse
beyond the signed payload); no module-specific reconciliation/reporting of
`transaction.lipa.na.mpesa` beyond manual cashier matching; no B2B paybill /
reversal / refund flows; dependence on a reachable **https** `web.base.url`;
hard-coded Daraja endpoints (API/version changes need code edits).

**Open questions:** how the payment screen correlates a `CheckoutRequestID` with
the `SAFARICOM_LATEST_RESPONSE` notification to mark the right `pos.payment`
paid; how a C2B transaction is matched to an order line before being unlinked;
STK timeout/retry when the customer never confirms (tender stays
`success=False`); whether `MpesaReceiptNumber` is persisted on the `pos.payment`
for accounting traceability; the callbacks' security posture beyond the 6h
`hash_sign` payload.
