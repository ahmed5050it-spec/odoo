# sale_project — Reverse-Engineering Brief

> *Generated by the revres code-explorer + code-architect workflow: structural
> facts from `extract_module.py` / `extract_frontend.py` + behavioral facts read
> from `addons/sale_project/models/` + `controllers/portal.py`. Odoo 19.0.*

The **Sales - Project** module (`sale_project`, category *Sales/Sales*,
`application=False`, **`auto_install=['sale_management', 'project_account']`**)
is the bridge whose manifest summary is "Task Generation from Sales Orders". It
declares **no model of its own** — 16 `_inherit`-only classes, ~7.5k Python LOC
— and exists to wire `sale.*` to `project.*` so that **confirming a sale order
with a *service* product automatically provisions a `project.project` and/or
`project.task`**. It sits one layer above three modules: `sale_management` (the
order document), `sale_service` (the service/timesheet line semantics), and
`project_account` (project ↔ analytic accounting). Because it auto-installs when
its sale/project ancestors are both present, every deployment that has Sales and
Project gets quote-to-project provisioning for free.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `sale_management` | Owns the quotation/order + order-template document this module extends with `project_id`, project/task smart buttons, and the confirm-time generation hook. |
| `sale_service` | Provides the service-product/`qty_delivered`/timesheet line machinery; `sale_project` adds the `milestones` delivered-qty method and the `_timesheet_service_generation` engine on top. |
| `project_account` | Brings `project.project` already wired to `account.analytic.account`, so a generated project lands on the order's analytic account and feeds invoicing. |

**Capability added:** turns a confirmed `sale.order.line` whose product is
configured with a `service_tracking` into a live project and/or task, and keeps
the two sides linked (`sale_line_id`/`task_id`/`project_id`) so delivered work,
milestones, and invoicing flow back to the order.

**Load-bearing keys.** The whole bridge rides on **two forward keys** —
`sale.order.line.project_id` and `sale.order.line.task_id` (the *generated*
project/task) — and **two back-links** — `project.task.sale_line_id` and
`project.project.sale_line_id` (which order item billed this work). The
**central driver is not a model but the `product.template.service_tracking`
Selection**: its value decides which side-effect fires on confirmation.

**Field-type distribution** (`Many2one` 22, `Boolean` 14, `Integer` 8,
`Selection` 6, `Float` 3, `One2many`/`Many2many` 2 each, `Char` 1): heavily
**relational + flag/counter**, with almost no descriptive text — exactly the
shape of a wiring module. The `Many2one` count is the cross-model glue; the
`Boolean`/`Integer` are visibility flags (`show_create_project_button`,
`visible_project`) and smart-button counts (`tasks_count`, `project_count`).

### Code-read (the metadata gap)

- **Confirm → project/task is the core side-effect.** `sale.order._action_confirm`
  calls `order_line.sudo().with_company(...)._timesheet_service_generation()`
  **before** `super()`. That method, on `sale.order.line`, partitions service
  lines by `product_id.service_tracking`: `project_only`/`task_in_project` →
  create one `project.project` per order (from a template via
  `action_create_from_template`/`copy`, else a fresh project seeded with
  To Do/In Progress/Done/Cancelled stages); `task_in_project`/`task_global_project`
  → create a `project.task` in that (or a pre-configured global) project. It
  also stamps `sale.order.project_id`, posts "Task Created (…)" on the order, and
  records `reinvoiced_sale_order_id` on the project.
- **Idempotent + reactive.** Generation also runs from `sale.order.line.create`
  and `write`: it searches existing `project_id`/`task_id` so a draft→confirm→
  draft→confirm cycle does **not** spawn duplicates, and raising
  `product_uom_qty` from 0 lazily generates the task, then re-syncs
  `task.allocated_hours` to the ordered quantity on every quantity change.
- **Milestone billing.** For `service_policy == 'delivered_milestones'`,
  `_handle_milestones` links `project.milestone` records to the SO line; the
  line's `qty_delivered_method` becomes `'milestones'` and `_prepare_qty_delivered`
  sums reached-milestone `quantity_percentage × product_uom_qty` — milestones
  drive how much of the line is invoiceable.
- **Two-way SO ↔ task creation.** `project.task` can mint/confirm a `sale.order`
  the other direction: `_ensure_sale_order_linked` (called from task
  create/write) auto-confirms any draft order behind a newly linked
  `sale_line_id`, and `sale.order.create` honors `create_for_project_id` /
  `create_for_task_id` context to back-link and confirm. `project.task.sale_order_id`
  is a stored compute that only resolves when the task is billable and the
  partner is consistent with the order's partners.
- **Lifecycle hooks.** `post_init_hook _set_allow_billable_in_project` backfills
  `allow_billable=True` on existing partner-bearing projects/tasks at install;
  `uninstall_hook` neutralizes the embedded "open invoices / view SOs" project
  actions. Cancelling an order (`sale.order.write` state=`cancel`) clears
  `sale_line_id` off its projects.

## Value-Configuration Classification

**Value model: `shop` · activity_class: `primary` · APQC: 5.0 Deliver Services.**
By Stabell & Fjeldstad this is **value-shop / intensive technology**: the unit
of work is a *project/task to be solved*, and `sale_project` is what turns a sold
service into that problem-solving vehicle (project + task + milestones), then
loops delivered work and milestones back to invoicing. It depends on
`sale_service`/`project_account` (service+project), not on `stock`/`mrp`, and
adds **zero** physical-flow concepts — so it is **not** a value-chain bridge.

*(Refinement note: the auto-architect metamodel baseline tags it
`chain`/`primary`/`3.0 Market and Sell` purely from the `sale_*` dependency
names. The code-read overrides that — the module's actual job is provisioning
and billing **service delivery via projects**, which is value-shop, not the
order-to-cash goods chain. Marked inferred.)* Its role is **primary**: project/task
provisioning from an order is a core line activity in a services business, even
though the module owns no standalone business object.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). There are **no routes to
curl** (`route_count: 0`); drive it through `odoo shell` on the inherited models.
The trigger is a service product whose `service_tracking` is set, then confirming
its order:

```python
# odoo shell — products configured to spawn projects/tasks on sale
gen = env['product.template'].search([
    ('service_tracking', 'in', ['task_global_project', 'task_in_project', 'project_only']),
])
print(gen.mapped(('name', 'service_tracking', 'service_policy')))

# the orders that have generated projects/tasks and the links they created
so = env['sale.order'].search([('project_count', '>', 0)], limit=5)
for o in so:
    print(o.name, o.project_ids.mapped('name'),
          o.order_line.mapped(('product_id.name', 'project_id.name', 'task_id.name')))

# verify the confirm side-effect end to end: confirm a draft order whose line
# uses a service_tracking product, then read what got created
draft = env['sale.order'].search([('state', '=', 'draft')], limit=1)
draft.action_confirm()
print(draft.project_ids.mapped('name'), draft.tasks_ids.mapped('name'))
```
