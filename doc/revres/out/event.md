# event — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/`, narrative per
> `PROMPT.md`. Odoo 19.0.*

The **Events Organization** module (`event`, category *Marketing/Events*,
`application=False`) runs trainings, conferences, meetings and exhibitions: it
lets an organizer publish an event, offer tickets with limited seats, capture
attendee registrations, drip automated communications, and check people in by
barcode. It is **not** auto-installed and depends on `mail`, `portal`, `utm`,
`barcodes`, `phone_validation` and `base_setup`. Its center of gravity is the
`event.event` / `event.registration` pair, surrounded by ticketing
(`event.event.ticket`), scheduling (`event.slot`) and a time-based mailing
engine (`event.mail`).

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `mail` | Chatter/activities on events & registrations; mailing via `mail.template`/`mail.compose.message`. |
| `portal` | Public ticket/badge access (`/event/<id>/my_tickets`) and attendee self-service. |
| `utm` | Campaign/source/medium attribution on each registration. |
| `barcodes` | Unique per-registration barcode + scan kiosk check-in. |
| `phone_validation` | Formats/validates attendee phone numbers on create/onchange. |

**Adds on top:** event lifecycle (stages/kanban), capacity-limited ticketing,
multi-slot scheduling, registration questions, and an automated mailing
scheduler.

## Behavior & Surfaces

- **Routes:** 3 — `/event/<event>/ics` and `/event/<id>/my_tickets` (`public`,
  `http`: iCal + ticket-PDF download, hash-guarded) and
  `/event/init_barcode_interface` (`user`, `jsonrpc`: the scan kiosk). No public
  storefront here — that lives in `website_event`.
- **Views:** **list (20)**, form (14), kanban (4), plus pivot (2), graph (2),
  calendar (3), activity (1) — operational and analyst-friendly.
- **Security:** 37 access rules, **3 record rules** (all multi-company
  scoping), **3 groups** — `group_event_registration_desk` (Registration Desk),
  `group_event_user` (User), `group_event_manager` (Administrator), each implying
  the previous.
- **Behavior beyond metadata (code-read):**
  `event.registration.state` is a draft/open/done/cancel machine;
  `_compute_seats` aggregates registrations by state in raw SQL to derive
  reserved/used/available; an `@api.constrains` calls `_verify_seats_availability`
  to block overbooking; create/confirm fan out to `_update_mail_schedulers`; and
  the `event.mail` cron `schedule_communications` mass-mails attendees on a
  computed schedule. `register_attendee` flips a scanned ticket to *done*.
- **Frontend (static):** 13 JS, 3 OWL components (`EventScanView`,
  `EventRegistrationSummaryDialog`, `IconSelectionField`).
- **Integration (gap #7):** `res.partner` calls the Google Maps Static API
  (signed, via `requests`) for venue maps.

## Value-Configuration Classification

**Primary model: Value Network (mediation), customer-facing.** `event` is a
**network** in Stabell & Fjeldstad terms: its core activity is *mediating* —
connecting an organizer with an audience and operating the
registration/ticketing **platform** that lets attendees join. Its economic logic
is membership/seat **capacity** (`seats_max`/`seats_available`, sold-out) plus
network promotion (`event.mail`, `utm` attribution, portal ticket access) — not
the sequential input→output transformation of a **chain**, nor case-by-case
problem solving of a **shop**. It is a **primary** activity, not support. (Once
`event_sale`/`website_event_sale` add paid checkout, the same `event.event` also
feeds the chain/cash side, but core `event` itself is network mediation.)

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — registering an audience to a
marketed event is a market/sell motion; the scheduled communications lean toward
3.x demand generation rather than a fulfillment category.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i event` database:

```python
# odoo shell
evs = env['event.event'].search([], limit=5)
print(evs.mapped(('name','seats_available','seats_max')))
regs = env['event.registration'].search([], limit=5)
print(regs.mapped(('name','state','barcode')))
print(env['event.mail'].search([('interval_type','=','after_sub')])
      .mapped(('event_id','scheduled_date','mail_state')))
# curl jsonrpc /event/init_barcode_interface (auth=user) opens the scan kiosk
```
