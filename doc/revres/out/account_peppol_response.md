# account_peppol_response — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Peppol Business Response** module (`account_peppol_response`, category
*Accounting/Accounting*, `application=False`, **`auto_install=True`**) is a thin
compliance/interchange extension that sits on top of `account_peppol`. It
implements the OpenPeppol **Invoice Response / Message-Level Response (MLR)**
business message: the accept / reject / acknowledge status replies that flow back
across the Peppol e-invoicing network between a document's sender and receiver.
It does not create invoices — it exchanges *status signals about* them, both
outbound (responding to received vendor bills) and inbound (recording what a
counterparty did with an invoice we sent).

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `account_peppol` | The base Peppol access-point integration (proxy user, message UUIDs, send/receive). This module only adds the *response* layer. |

Transitively it rides on `account_edi_ubl_cii` (UBL serialization) and
`account_edi_proxy_client` (the IAP/access-point transport). `auto_install=True`
means it activates automatically once `account_peppol` is present.

**Adds on top:** a Business-Level-Response object, a reason/action clarification
catalog, a rejection wizard, and Peppol-state fields on `account.move`.

## Behavior & Surfaces

- **Routes:** none (0). Purely backend — driven by ORM actions and crons.
- **Views:** 1 form, 1 list, plus the rejection wizard view.
- **Security:** 3 access rules, 0 record rules, 0 groups.

Metadata cannot show the response workflow. Code reads establish:

- `account.move._post` overrides posting to auto-fire
  `action_peppol_send_approval_response` → `_peppol_send_response(moves, 'AP')`:
  posting a received Peppol bill emits an **Approval** Invoice-Response to its
  sender. Reception auto-sends an **Acknowledgement** (`AB`).
- `_peppol_send_response` transmits a UBL **ApplicationResponse**
  (`trns:invoice_response:3`) through the access point via `_call_peppol_proxy`
  on `'1/send_response'` with `reference_uuids`, `status` (AB/AP/RE) and
  `clarifications`; `RE` requires ≥1 `OPStatusReason` or it raises. Success
  creates `account.peppol.response` rows (`processing`) and logs chatter.
- `_peppol_process_new_messages` / `_peppol_extract_response_info` parse inbound
  `ApplicationResponse` XML (lxml) — `ResponseCode` + `Status`/`StatusReasonCode`
  (listIDs `OPStatusReason`/`OPStatusAction`) resolved against
  `account.peppol.clarification` — and create a response row on the origin move.
- `_compute_peppol_move_state` rolls up `done` responses to the move's
  `peppol_move_state`: any `RE`→Rejected, else `AP`/`PD`→Approved, else
  `AB`→Received.
- Rejection: `button_cancel` opens `account.peppol.rejection.wizard`; the user
  picks reason/action codes and `button_send` sends `RE` + clarifications.
- Status crons (`_peppol_get_documents_for_status` /
  `_peppol_process_messages_status`) reconcile delivery state with the proxy
  (error 702 skip, 207→`not_serviced`, else store/error);
  `_cron_peppol_auto_register_services` registers the Invoice Response service.

**Reason/status codes** (`response_code`): AB Acknowledgement, IP In Process,
UQ Under query, CA Conditionally accepted, RE Rejection, AP Approval, PD Paid —
only AB/AP/RE are actively driven (the mandatory Peppol BLR set); the rest stored.

## Value-Configuration Classification

**Value model: Support (support / support).** This is an e-invoicing
compliance/interchange extension on accounting; it creates no primary customer
value, it exchanges the **compliance status** of AR/AP documents on the Peppol
network. A Porter/Stabell support activity riding on the financial system of
record.
