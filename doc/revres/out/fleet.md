# fleet — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, code-read behavioral notes, and the `PROMPT.md`
> template. Asset-management support subsystem.*

The **Fleet** module (`fleet`, category *Human Resources/Fleet*,
`application=True`) manages an organisation's **vehicles as physical assets**
across their full lifecycle. It depends only on `base` and `mail`, ships no web
controllers, and centres on `fleet.vehicle` (62 fields, 40 methods) — a Vehicle
record that carries a state machine, a driver, a model/brand catalog, and three
satellite logs (contracts, services, odometer). It is a self-contained
**support** activity: it tracks and maintains assets consumed by the primary
business, with no customer-facing document of its own.

## 1. Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `base` | Core ORM, `res.partner` (drivers/vendors/insurers), `res.users` (managers), `res.company`. |
| `mail` | `fleet.vehicle`, contracts and services inherit `mail.thread` + `mail.activity.mixin` — chatter, tracking, and the renewal/hand-over **activities** that drive the workflow. |

**Adds on top:** a vehicle register with a brand/model/category catalog, driver
assignment with full history, leasing/insurance **contracts with renewal
alerts**, service & cost logging, odometer tracking, a mass-mail-drivers wizard,
and pivot/graph cost & mileage analytics. No `account`, `stock`, or `hr`
dependency — accounting and payroll bridges live in separate modules.

**Central model:** `fleet.vehicle` — the three logs, odometer, assignment
history, and both analysis reports all reference it. The model catalog
(`fleet.vehicle.model` / `.brand` / `.category`) is a reusable spec library;
`MODEL_FIELDS_TO_VEHICLE` copies model defaults (CO₂, power, fuel, seats…) onto
each vehicle via compute methods.

## 3. Behavior Beyond Metadata (code-read)

Metadata shows fields and relations; it cannot show side-effects. The key ones:

- **Driver assignment → history.** Setting/changing `driver_id` (in `create`
  and `write`) calls `create_driver_history()`, appending a
  `fleet.vehicle.assignation.log` row (`date_start=today`). On a driver swap it
  also schedules a `mail.mail_activity_data_todo` to-do (to `manager_id` or the
  current user) to set the previous driver's end date.
- **Hand-over signalling.** Assigning `future_driver_id` flags the partner's
  other same-type vehicles `plan_to_change_car`/`plan_to_change_bike`;
  `action_accept_driver_change()` then clears those flags, releases the old
  vehicles, and promotes the future driver to `driver_id`.
- **Contract renewal cron.** Daily `ir.cron`
  `ir_cron_contract_costs_generator` → `run_scheduler()` →
  `scheduler_manage_contract_expiration()` drives the contract state machine,
  schedules a `fleet.mail_act_fleet_contract_to_renew` activity for contracts
  expiring within `hr_fleet.delay_alert_contract` days (default 30), and sets
  the vehicle's `contract_renewal_due_soon` / `contract_renewal_overdue` flags.
- **Append-only odometer.** The vehicle `odometer` field is the *max* reading;
  its inverse and `log.services._set_odometer` create new
  `fleet.vehicle.odometer` rows rather than mutating, and `write` raises a
  `UserError` if a new reading is lower than the current (monotonic guard).

## 4. Frontend & Integrations

- **Frontend (gap #3, static):** 1 JS file, 0 OWL components, 0 patches, one
  registry add (`views:fleet_form`) on `web.assets_backend`. The UI is almost
  entirely server-rendered — 11 forms, 12 lists, 6 kanban, 9 search views, plus
  4 pivot / 5 graph / 3 activity views — with negligible custom client code.
- **Integrations (gap #7):** no outbound HTTP call sites, no SDK imports, no API
  keys. The only endpoint is the documentation URL `https://www.odoo.com/app/fleet`
  in `__manifest__.py`. Fuel-card/telematics feeds are out of scope for base fleet.

## 5. Business Architecture

- **Capabilities (inferred):** Manage Vehicle Fleet · Assign Vehicles to Drivers
  · Manage Vehicle Contracts (with renewal alerts) · Log Services & Costs · Track
  Odometer/Mileage · Fleet Cost & Odometer Analysis.
- **Value streams (inferred):** vehicle lifecycle (new request → in-service →
  driver assignment → contract & service upkeep → write-off) and contract
  renewal (open → near-expiry alert → renew/expire).
- **Organization (auto):** `fleet_group_user` (*Officer: Manage all vehicles*),
  `fleet_group_manager` (*Administrator*).
- **Policies (inferred):** 9 record rules (per-administrator full rights +
  multi-company scoping), the daily contract cron, and the odometer monotonicity
  guard.
- **Metrics (inferred):** `fleet.vehicle.cost.report`, `fleet.vehicle.odometer.report`.
- **Strategy:** `null` (human-supplied).

## 7. Fit-to-Standard

- **Standard out-of-box:** vehicle register + model catalog, driver assignment
  with history, leasing/insurance contracts with auto renewal alerts, service
  logging, odometer tracking, cost/odometer analytics, mass-email drivers wizard.
- **Common gaps (config/dev):** accounting integration of costs (separate
  `fleet_account` / `hr_fleet` bridges), fuel-card / telematics / GPS feeds,
  payroll benefit-in-kind valuation (`l10n_*_hr_payroll_fleet`), custom
  depreciation beyond `car_value` / `residual_value`.
- **Drive hints:** `env['fleet.vehicle'].search([], limit=5).mapped(('name','state_id.name','driver_id.name'))`
  · `env['fleet.vehicle.log.contract'].run_scheduler()` (exercise the renewal cron).
