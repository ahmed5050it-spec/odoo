# delivery — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, code-read behavioral notes, and the `PROMPT.md`
> template. Gap #7 external-integration example.*

The **Delivery Costs** module (`delivery`, category *Sales/Delivery*,
`application=False`) is the **carrier-connector abstraction** of Odoo: it defines
*how shipping is rated and which carrier ships an order*, then injects the
shipping charge onto the sales order. It is **not** auto-installed and depends
only on `sale` and `payment_custom`. Its center of gravity is `delivery.carrier`
(34 fields, 34 methods) — a Shipping Method that is either a built-in provider
(`fixed`, `base_on_rule`) or, via sub-modules, a connector to a real external
carrier API.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `sale` | The shipping charge is added to `sale.order` as a delivery `sale.order.line`; the carrier-selection wizard targets the order. |
| `payment_custom` | Enables Cash-on-Delivery as a custom payment mode, gated by the selected carrier (`allow_cash_on_delivery`). |

**Adds on top:** a carrier catalog with rate/availability matching, rule-based
pricing, a carrier-selection wizard, an eCommerce pickup-location selector, and
the **SPI extension point** for external carrier connectors. Notably it does
**not** depend on `stock` — physical shipment/tracking lives in `stock_delivery`.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`delivery.carrier`** | Shipping Methods | 34 | `product_id→product.product`, `company_id→res.company`, `price_rule_ids→delivery.price.rule` |
| `delivery.price.rule` | Delivery Price Rules | 10 | `carrier_id→delivery.carrier` |
| `delivery.zip.prefix` | Delivery Zip Prefix (service area) | 1 | — |
| `choose.delivery.carrier` | Carrier Selection Wizard | 13 | `order_id→sale.order`, `carrier_id→delivery.carrier` |
| `sale.order` *(extension)* | — | 7 | `carrier_id→delivery.carrier`, `shipping_weight` |

**Central model:** `delivery.carrier` — everything (price rules, the wizard,
sale.order, and downstream pickings in `stock_delivery`) references it. The
field set is feature-flag heavy (`Boolean` 15) over the carrier product and
pricing (`Float` 14, `Many2one` 12). `delivery_type` (a `Selection`) is the
polymorphism axis: external provider modules `selection_add` their own value.

## Behavior & Surfaces

- **Provider dispatch (code-read):** `rate_shipment(order)` reflectively calls
  `getattr(self, '<delivery_type>_rate_shipment')(order)`. Base ships `fixed`
  (carrier-product price) and `base_on_rule` (`safe_eval` over
  `delivery.price.rule`); it then applies margin/`fixed_margin` and zeroes the
  price under `free_over`. The connector SPI (`<type>_send_shipping`,
  `<type>_get_tracking_link`, `<type>_cancel_shipment`) is documented in the
  class docstring — base defines it, sub-modules implement it.
- **Shipping cost on the order (code-read):** `set_delivery_line` /
  `_create_delivery_line` write a `sale.order.line` with `is_delivery=True`,
  carrying the rated price into Quote-to-Cash invoicing.
- **External integrations (static, gap #7):** 0 HTTP call sites, 0 SDK imports,
  no API keys in this module — the real carrier API traffic (FedEx/UPS/DHL/
  Easypost/Sendcloud, …) lives in `delivery_*` sub-modules that extend
  `delivery.carrier`. This is an integration *boundary*, not a connector.
- **Routes:** 2, `auth='user'`, `jsonrpc` — the pickup-location selector
  (`/delivery/get_pickup_locations`, `/delivery/set_pickup_location`).
- **Frontend (gap #3):** 7 JS / 6 XML, OWL components `Location`, `LocationList`,
  `LocationSchedule`, `LocationSelectorDialog`, `Map`, `MapContainer`; patches
  `PaymentForm.prototype`; bundle `web.assets_frontend`.
- **Security:** 10 access rules, 1 record rule (multi-company carrier scoping),
  0 groups; plus tag/margin/insurance CHECK constraints.

## Value-Configuration Classification

**Value Chain — support activity.** `delivery` extends the **outbound-logistics
(shipping/carrier)** leg of the value chain, so its value model is **chain**. It
is a **support** activity, not primary: it *provisions* shipping capability —
abstracting carriers, rating shipments, and injecting cost — while the physical
outbound move and tracking are executed by `stock` / `stock_delivery`. It also
carries a noted **gap #7 external-integration** character: the module is the
connector SPI, and concrete external carrier APIs are realized in `delivery_*`
sub-modules rather than here.

## APQC PCF Hint

**4.4 Operate outbound transportation / ship** (Supply Chain). Rating and
carrier selection are the "ship" preparation; the Cash-on-Delivery hook touches
9.0 (Manage Financial Resources) at the payment boundary, and the order-line
cost touches 3.0 (Sell) where it rides the sales order.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i delivery` database:

```python
# odoo shell
carriers = env['delivery.carrier'].search([])
print(carriers.mapped('name'), carriers.mapped('delivery_type'))
so = env['sale.order'].search([], limit=1)
c = env['delivery.carrier'].search([('delivery_type', '=', 'fixed')], limit=1)
print(c.rate_shipment(so))  # {'success', 'price', 'carrier_price', ...}
# pickup-location surface:
#   curl .../delivery/get_pickup_locations  (auth=user, jsonrpc, zip_code+country)
```
