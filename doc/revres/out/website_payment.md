# website_payment — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +

The **Website Payment** module (`website_payment`, category *Website/Website*,
`application=False`, `auto_install=True`) is a thin **bridge** that exposes the
payment engine on the public website. It adds **no new models** — only four
inherit-only extensions (555 py LOC) — and its real weight is in **public
controllers** and **website snippets**: the `/donation` storefront, the
website-scoped "pay" / manage-payment-methods pages, and a supported-payment-
methods snippet. Its manifest summary is exactly that: *"Payment integration with
website"* / *"multi-website support for payment providers"*.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `website` | Public web channel, snippets, multi-website (`website_id`), website builder. |
| `account_payment` | The portal payment controllers + `account.payment` it bridges to. |

**Adds on top:** a `website_id` scope on `payment.provider`, an `is_donation`
flag on `payment.transaction`/`account.payment`, the public `/donation/pay` +
`/donation/transaction/<minimum_amount>` flow, a supported-methods snippet
endpoint, and a `PaymentForm` JS patch driving the free-amount donation UX.

The load-bearing relation is `payment.provider.website_id`: it lets a provider be
unscoped (all sites) or pinned to one website, which the controllers exploit for
multi-website isolation.

## Behavior Beyond Metadata (code-read)

- **`/donation/pay` + `/donation/transaction/<minimum_amount>`** — the public
  donation flow. `donation_pay` forces `is_donation`, defaults amount `25.0`, and
  mints an access token for anonymous visitors. `donation_transaction` builds a
  `payment.transaction` from the **visitor-typed free amount**, enforces
  `amount >= minimum_amount`, requires name/email/country for anonymous donors,
  and **re-issues the access token against the final amount** (the donor can
  change it on the page) — a tamper guard invisible to metadata.
- **Website-aware provider scoping** (`controllers/payment.py`) — `payment_pay`
  and `payment_method` (the `/my/payment_method` portal page) re-dispatch with
  `website_id`, flowing into `payment.provider._get_compatible_providers` to
  **filter providers to the current website** (others → `incompatible_website`).
- **Supported-methods snippet endpoint** — `get_supported_payment_methods`
  computes the website's compatible providers `with_user(website.user_id).sudo()`
  (editor previews what customers see), returns brand + brandless-primary methods
  as `{name, image_url}`, with a **7-day public cache** vs `no-cache` internally.
- **Settlement side-effects** (`_post_process`) — a done donation sends a **donor
  confirmation email** + logs **chatter** on the `account.payment`; a second
  `_send_donation_email` fires at creation as an internal recipient notification.
- **Frontend (static)** — `payment_form.js` **patches** `@payment`'s `PaymentForm`
  to bind free-amount inputs into `paymentContext.amount` and inject
  `partner_details`/`donation_comment`/`donation_recipient_email` into the RPC; a
  `DonationForm` public interaction handles snippet UX.

This bridge processes nothing itself; it **exposes** the payment value-network on
the public web channel — network promotion (donation + supported-methods
snippets advertising the means to transact), service provisioning
(`/donation/transaction` binding a free amount to a transaction), and
infrastructure operation (website-scoped provider routing). Unlike the back-office
`payment` engine (which we tagged *support* / 9.0 Manage Financial Resources),
this module is **customer-facing** (category Website/Website) and its function is
**online collection of money / donations from the public** — revenue-facing, so
`activity_class=primary` and **APQC 3.0** (Market and Sell) rather than 9.0; a 9.5
"process payments" reading would understate that this is the public **collection
front end**, not internal treasury.

## Fit-to-Standard

**Out-of-box:** public `/donation/pay` with prefilled + free amounts and minimum
enforcement; donor/recipient emails + chatter on settlement; per-website provider
scoping on pay and manage-methods pages; drag-drop Donation and Supported-Payment-
Methods snippets; anonymous donation via the website public partner.
**Typical fits:** non-profit one-off fundraising; multi-website groups routing
each site to its own acquirers; "accepted cards" trust snippet; portal customers
managing website-scoped saved cards.
**Common gaps:** no live acquirer ships here (needs a `payment_<provider>`);
recurring/pledged donations; tax receipts / gift-aid documents; bespoke donation
analytics; custom post-settlement document creation.
