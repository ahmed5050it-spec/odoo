# purchase_stock — Reverse-Engineering Brief

> *Generated by the revres code-explorer + code-architect workflow: structural
> facts from `extract_module.py` / `extract_frontend.py` + behavioral facts read
> from `addons/purchase_stock/models/` and `__init__.py`. Odoo 19.0.*

The **Purchase Stock** module (`purchase_stock`, category *Supply Chain/Purchase*,
version 1.2, `application=False`, **`auto_install=True`**) is the bridge whose
manifest summary is "Purchase Orders, Receipts, Vendor Bills for Stock". It owns
**one** real model — `vendor.delay.report`, a read-only SQL view — and otherwise
exists as **27 `_inherit`-only extensions** (~13.0k Python LOC) that wire
`purchase.*` to `stock.*`. It sits one layer above its two dependencies
(`purchase` + `stock_account`) and, because it is auto-installed, it materializes
the two halves of the procure-to-receive loop that neither parent can express
alone: **approving a PO creates a receipt** (`stock.picking` + `stock.move`), and
**a stock need pulls a PO into existence** (the `'buy'` route / `_run_buy`). It is
the procurement counterpart to `sale_stock`'s delivery bridge.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `purchase` | Owns the RFQ / purchase-order / vendor-bill document this module extends with receipt, picking-type and reception fields. |
| `stock_account` | Pulls in `stock` (pickings/moves/rules/warehouses/orderpoints) **plus** valuation, so received goods feed inventory *and* accounting (landed-cost-aware receipts, vendor-bill ↔ move matching). |

**Adds on top:** the **`buy`** stock-rule action and per-warehouse **Buy route**
(`buy_to_resupply` / `buy_pull_id`), so reordering rules, MTO moves and
manufacturing demand can replenish *by purchasing*; automatic receipt creation on
PO approval; `qty_received` derived from done moves; vendor on-time-delivery
analytics; and replenishment-info vendor selection. `auto_install=True` is the
glue-module tell — it activates the moment both `purchase` and `stock_account`
are present.

(receipt fulfillment) and **`stock.picking.purchase_id`** (related, read-only

### Code-read (the metadata gap — what the facts can't show)

- **Forward leg (approve → receipt).** `purchase.order.button_approve()` calls
  `super()` then **`_create_picking()`**: for any PO with a `consu` line it
  prepares a `stock.picking` (vendor→destination location, via
  `_prepare_picking`/`_get_destination_location`), creates `stock.move`s through
  `order_line._create_stock_moves()`, then `_action_confirm()` + `_action_assign()`
  and confirms forward (push-rule) pickings too. **Approving the PO is what
  spawns the receipt.** Conversely `button_cancel()` cancels not-yet-done
  pickings/moves and flips downstream MTO moves back to `make_to_stock`.
- **Backward leg (need → RFQ).** `stock.rule._run_buy(procurements)` is the
  reverse direction: it resolves a vendor (`_get_matching_supplier`), groups
  procurements by a PO domain (`_make_po_get_domain`, honoring the partner's
  RFQ-grouping policy day/week), then **finds-or-creates a `purchase.order` and
  its lines** (`_prepare_purchase_order` / `_prepare_purchase_order_line_from_procurement`).
  This is how a reordering rule, an MTO sale, or an MO shortage **auto-generates a
  draft RFQ**. `stock.rule.run()` also injects the warehouse `reception_route_id`
  whenever a `buy` route is involved.
- **Receipt feeds quantities & accounting.** `purchase.order.line._compute_qty_received_method`
  flips `consu` lines to **`'stock_moves'`**, so `_prepare_qty_received` sums done
  incoming/outgoing move quantities (handling returns/dropship edge cases) — i.e.
  *receiving stock advances `qty_received`*, which in turn gates billing.
  `stock.picking._action_done()` calls `purchase_id.action_acknowledge()`.
- **Live qty sync.** `purchase.order.line.create`/`write` call
  `_create_or_update_picking()` on confirmed orders: increasing a line qty extends
  or creates the receipt; decreasing below billed schedules a "ask for a refund"
  activity on the vendor bill; `unlink` cancels/`make_to_stock`s the related moves.
- **Buy route bootstrapping.** The `_create_buy_rules` **post_init hook** sets
  `buy_to_resupply=True` on every warehouse lacking a `buy_pull_id`, so existing
  warehouses gain the Buy route on install; `stock.warehouse._generate_global_route_rules_values`
  defines the `action='buy'` rule pointing at `route_warehouse0_buy`.
- **Vendor on-time analytics.** `vendor.delay.report` is a SQL view joining
  `stock_move → purchase_order_line`, scoring a move on-time when
  `pol.date_planned >= m.date`, exposed as a weighted `on_time_rate` graph/pivot.

## Value-Configuration Classification

**Value model: `chain` · activity_class: `primary` · (Stabell & Fjeldstad: long-linked / transformation technology).** This is a pure value-chain bridge
realizing **inbound logistics / procurement**: a demand signal is transformed
into a vendor purchase order, and the physical receipt of goods flows back to
advance received quantity and gate vendor-bill matching. It is classified
**primary** because supplier replenishment and goods receipt are core line
activities in the procure-to-pay chain — even though the module owns no
standalone business object (only the `vendor.delay.report` analytics view). It
inherits the *primary/chain* DNA of both parents (`purchase` document flow +
`stock` move flow). *(The auto-architect metamodel baseline tags it
`support`/`support` as a thin auto-install module; the code-read above refines
that to a primary inbound-logistics chain bridge — marked inferred.)*

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). There are **no routes to
curl** (`route_count = 0`) — drive it through `odoo shell` on the inherited
`purchase.*` / `stock.*` models:

```python
# odoo shell — approving a PO with a storable line creates a receipt
po = env['purchase.order'].search([('state', 'in', ('draft', 'sent'))], limit=1)
po.button_confirm()          # or button_approve() when double-validation is on
print(po.picking_ids.mapped(('name', 'state')))   # <- the stock.picking it spawned
print(po.receipt_status, po.effective_date)

# the reverse leg: orderpoints that replenish by buying, and the RFQs they made
ops = env['stock.warehouse.orderpoint'].search([('supplier_id', '!=', False)])
print(ops.mapped(('product_id.display_name', 'effective_vendor_id.name')))

# vendor on-time-delivery analytics (read-only SQL view)
env['vendor.delay.report'].search([], limit=3).read(
    ['partner_id', 'product_id', 'qty_total', 'qty_on_time', 'on_time_rate'])
```

To watch the backward leg, set a reordering rule below its minimum on a product
with a vendor and run the scheduler — `stock.rule._run_buy` should create a draft
`purchase.order`. To watch the forward leg, confirm a PO and read `picking_ids`.
