# mail_group — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, code-read behavior, and the `PROMPT.md` template.*

The **Mail Group** module (`mail_group`, no application category,
`application=False`, `auto_install=False`) turns Odoo into a classic
email-driven **mailing list / discussion group** manager. Its center of gravity
is `mail.group` (24 fields, 44 methods) — the list itself, owning an email alias
— surrounded by `mail.group.member` (subscribers), `mail.group.message` (list
posts wrapping a `mail.message`), and `mail.group.moderation` (per-email
allow/ban rules). Members email an alias to post or reply; accepted messages are
fanned out to every subscriber and archived on a public portal. It depends only
on `mail` (delivery + gateway + alias) and `portal` (public web surface).

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `mail` | Posts are stored as `mail.message`; delivery uses `mail.mail`/`ir.mail_server`; the inbound gateway + `mail.alias.mixin` route email to the list. |
| `portal` | Public, server-rendered web pages (`/groups`) for browsing archives and self-service subscribe/unsubscribe. |

**Adds on top:** list membership, three privacy modes, message moderation with
allow/ban lists, RFC-compliant list headers, and a threaded web archive — none
of which the bare `mail` chatter provides.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`mail.group`** | Mail Group | 24 | `member_ids→mail.group.member`, `mail_group_message_ids→mail.group.message`, `moderation_rule_ids→mail.group.moderation`, `moderator_ids→res.users`, `access_group_id→res.groups` |
| `mail.group.member` | Mailing List Member | 4 | `mail_group_id→mail.group`, `partner_id→res.partner` |
| `mail.group.message` | Mailing List Message | 15 | `mail_message_id→mail.message`, `mail_group_id→mail.group`, `group_message_parent_id→mail.group.message` |
| `mail.group.moderation` | Mailing List black/white list | 3 | `mail_group_id→mail.group` |
| `mail.group.message.reject` | Reject Group Message (wizard) | 6 | `mail_group_message_id→mail.group.message` |

**Central model:** `mail.group` — every other model points back to it.
`mail.group` is **not** a `mail.thread`; it inherits only `mail.alias.mixin`
(it owns an alias but reimplements posting). `mail.group.message` *wraps* rather
than inherits `mail.message` (via a `mail_message_id` Many2one with related
fields) to add threading and moderation without bloating the `mail.message`
cache. The field mix is relational/boolean-heavy (many flags: moderation,
access, closed), consistent with a configuration + routing model rather than a
data-entry document.

## Behavior & Surfaces

- **Routes:** 9, all `auth='public'` — `http` portal pages (`/groups`,
  `/groups/<group>`, `/groups/<group>/<message>`), `jsonrpc`
  `/group/subscribe` & `/group/unsubscribe`, and the confirm/one-click
  endpoints. The public surface is HMAC-token / `consteq` gated.
- **Custom posting (code-read):** `mail.group.message_post` builds a
  `mail.message` then a `mail.group.message`, sets `moderation_status`, and
  either calls `_notify_members` or queues for moderation. `message_new` /
  `message_update` are no-op stubs so the gateway uses this flow.
- **Fan-out (code-read):** `_notify_members` creates one `mail.mail` per member
  email (skipping the author), each with RFC-2369 list headers (`List-Id`,
  `List-Archive`, `List-Post`) and an RFC-8058 one-click `List-Unsubscribe`,
  batched at 500.
- **Moderation (code-read):** `action_moderate_accept/reject/allow/ban` gate
  pending messages; allow/ban persist a `mail.group.moderation` rule and cascade
  to all same-author pending messages; `_cron_notify_moderators` reminds
  moderators via Inbox/Email.
- **Gateway guards (code-read):** `_alias_get_error` enforces `access_mode`
  (members/groups) at the alias; `_routing_check_route` bounces email to a
  closed group.
- **Frontend (static):** 2 JS files as website `public.interactions`
  (`mail_group`, `mail_group_message`); no OWL, no patches; pages are QWeb.
- **Security:** 9 access rules, **10 record rules** (portal visibility scoping),
  0 module-defined groups in the extract (the `group_mail_group_manager`
  administrator group is declared in `data/res_groups.xml`).

## Value-Configuration Classification

**Primary model: Value Network (mediating), primary activity.** `mail_group`
is a network-style **mediating technology** (Stabell & Fjeldstad): the list is
the intermediary that links a community of subscribers to one another, and its
value grows with membership (network effect) rather than flowing along a
transformation chain. Its core service is **mediation / relationship-brokering**
— registering members (`mail.group.member`), routing each post to every other
member (`_notify_members` fan-out), and maintaining the shared archive — not
converting an input into an output (chain) or matching a problem to bespoke
expertise (shop). Moderation (`mail.group.moderation`) is the network's
admission / contract-management control. It is classed **primary** because
operating the discussion-group community is the module's own end-product, not a
back-office support function.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`) with an `-i mail_group`
database:

```python
# odoo shell
groups = env['mail.group'].search([])
print(groups.mapped(('name', 'access_mode', 'moderation', 'member_count')))
# auto-created alias for a new list:
g = env['mail.group'].create({'name': 'Test List'}); print(g.alias_id.alias_name)
# pending moderation backlog:
print(env['mail.group.message'].read_group(
    [('moderation_status', '=', 'pending_moderation')], ['__count'], ['mail_group_id']))
# public subscribe (jsonrpc): POST /group/subscribe {group_id, email}
#   -> 'added' | 'email_sent' | 'is_already_member'
# GET /groups  -> public portal index of lists
```
