# payment_demo — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Payment Provider: Demo** module (`payment_demo`, category
*Accounting/Accounting*, `application=False`) is a **fake payment acquirer
that simulates every possible payment flow in-process** — no external gateway,
no real money. It is the canonical test harness and developer reference for the
Odoo `payment` engine: it declares every optional feature the engine supports
(`support_express_checkout`, `support_manual_capture='partial'`,
`support_refund='partial'`, `support_tokenization=True`) while permanently
blocking itself from going live (`@api.constrains` raises `UserError` if
`state` is set to anything other than `'test'` or `'disabled'`).

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `payment` | Inherits the full provider / transaction / token / payment-method engine and all its hooks. |

`payment_demo` has **no own models** — it uses `_inherit` only. It extends
three existing models (`payment.provider`, `payment.transaction`,
`payment.token`) and adds one controller.

## Data Model

| Inherited model | New fields | Key behavior added |
|-----------------|-----------|-------------------|
| `payment.provider` | `code` (selection_add `'demo'`) | `_compute_feature_support_fields` enables all four feature flags; `_check_provider_state` blocks `state='enabled'`. |
| `payment.token` | `demo_simulated_state` (Selection: pending / done / cancel / error) | Per-token outcome selector for off-session recurring charges. |
| `payment.transaction` | `capture_manually` (Boolean, related) | Full simulation of `_send_payment_request`, `_send_capture_request`, `_send_void_request`, `_send_refund_request`, `_apply_updates`, `_extract_token_values`. |

The `demo_simulated_state` field on `payment.token` is the most distinctive
data element: it controls what happens when the engine calls
`_send_payment_request` for an off-session charge (subscription renewal,
auto-pay). A QA engineer configures it at token-creation time; every subsequent
charge against that token produces the pre-selected outcome without touching any
external API.

## Routes

| Path | Type | Auth | Purpose |
|------|------|------|---------|
| `/payment/demo/simulate_payment` | jsonrpc | public | Receives `{reference, payment_details, simulated_state}` from the browser and calls `payment.transaction.sudo()._process('demo', data)`. |

## Behavior (code-read)

### 1. Demo declares all features but can never go live

`payment_provider.py` `_compute_feature_support_fields` forces
`support_express_checkout=True`, `support_manual_capture='partial'`,
`support_refund='partial'`, `support_tokenization=True` for `code=='demo'`. An
`@api.constrains('state','code')` guard then raises `UserError` if state is set
to `'enabled'`. This makes Demo the only provider that exercises every engine
code path but can never accidentally charge a real customer.

### 2. `_apply_updates` — the simulation hub

The entire state-machine dispatch lives in `payment_transaction.py`
`_apply_updates`:

- Sets `provider_reference = f'demo-{self.reference}'`.
- If `self.tokenize`, calls `self._tokenize(payment_data)` **inline** (before
  the state transition) to vault the token with `demo_simulated_state`.
- Dispatches on `payment_data['simulated_state']`:
  - `'pending'` → `_set_pending()`
  - `'done'` + `capture_manually` True + no `manual_capture` flag → `_set_authorized()` (two-step path)
  - `'done'` otherwise → `_set_done()`; if `self.operation == 'refund'`,
    immediately fires `env.ref('payment.cron_post_process_payment_tx')._trigger()`
    so downstream accounting entries complete without waiting for the scheduler
  - `'cancel'` → `_set_canceled()`
  - anything else → `_set_error()`

None of the refund cron self-trigger, the two-step authorize path, or the inline
tokenization sequencing are visible from model/field metadata.

### 3. Off-session payment uses `token.demo_simulated_state`

`_send_payment_request` reads `simulated_state = self.token_id.demo_simulated_state`
and calls `self._process('demo', ...)` directly — zero HTTP. This is the
only way the engine's subscription / auto-renewal code path can be tested
deterministically without a live gateway.

### 4. JS frontend simulates checkout and Express Checkout

Three JS files ship in `web.assets_frontend`:

- **`payment_demo_mixin.js`** — shared module that reads `#customer_input` and
  `#simulated_payment_state` from the DOM and calls
  `rpc('/payment/demo/simulate_payment', {reference, payment_details, simulated_state})`,
  then redirects to `/payment/status`.
- **`payment_form.js`** — patches `PaymentForm.prototype`: `_prepareInlineForm`
  forces `'direct'` flow (bypassing redirect) and `_processDirectFlow` delegates
  to the mixin.
- **`express_checkout.js`** — patches `ExpressCheckout.prototype.initiateExpressPayment`
  to additionally collect a shipping address from a Bootstrap modal form, call the
  `shippingAddressUpdateRoute` RPC, pick the first available delivery method via
  `/shop/set_delivery_method`, and then call the mixin — exercising the full
  Express Checkout (Apple/Google Pay-equivalent) flow in software.

The QWeb `payment_demo_templates.xml` provides the inline form with a free-text
`customer_input` field and a `simulated_payment_state` `<select>` (done /
pending / cancel / error), the token warning template (showing what outcome to
expect from a saved Demo token), and the Express Checkout modal.

### 5. Tokenization: double-tokenization guard

`_extract_token_values` returns `{'payment_details': ..., 'provider_ref': 'fake
provider reference', 'demo_simulated_state': state}` so the customer's typed
input becomes the token display name and the chosen outcome becomes permanent on
the token. A guard `if self.state in ('done', 'authorized'): return {}` prevents
double-tokenization because `_apply_updates` already called `_tokenize()` inline
in the done/authorized branch. This coordination between two methods is invisible
without reading both together.

## Value-Configuration Classification

**Value model: network** (Stabell & Fjeldstad mediating-technology). Demo
inherits the payment engine's network position — its structural role is to
mediate between payer and merchant — but makes no real external connections; all
simulation is in-process. **Activity class: support** (APQC 9.0 Manage
Financial Resources — payment testing infrastructure, `application=False`).
