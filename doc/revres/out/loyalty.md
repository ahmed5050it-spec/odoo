# loyalty — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Coupons & Loyalty** module (`loyalty`, category *Sales*,
`application=False`) is Odoo's cross-cutting **promotions & rewards engine**. It
is **not** auto-installed and sits deliberately upstream of the sell activities:
it depends only on `product`, `portal` and `account`, yet is consumed by `sale`,
`point_of_sale` and `website_sale` to discount carts, accrue/redeem points and
place reward lines. Its center of gravity is the `loyalty.program` →
`loyalty.rule` / `loyalty.reward` configuration tree plus the issued
`loyalty.card` that carries a points balance. Crucially, this module defines the
*rules* of a promotion but stores **no orders** and confirms **no transactions**.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `product` | Rules/rewards target `product.product`/`category`/`tag`; each reward auto-creates a backing service product. |
| `portal` | Customer self-service view of the loyalty card + point history (`/my/loyalty_card/*`). |
| `account` | Currency, pricelist and discount-product plumbing so rewards become invoiceable order lines. |

**Adds on top:** a program designer covering 8 program types, point-accrual
rules, a discount/free-product reward catalog, coupon/card issuance with history,
and program communication (creation + milestone emails).

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`loyalty.program`** | Loyalty Program | 29 | `rule_ids→loyalty.rule`, `reward_ids→loyalty.reward`, `communication_plan_ids→loyalty.mail`, `coupon_ids→loyalty.card`, `pricelist_ids→product.pricelist` |
| **`loyalty.rule`** | Loyalty Rule (earning) | 19 | `program_id→loyalty.program`, `product_ids→product.product`, `product_category_id`, `product_tag_id` |
| **`loyalty.reward`** | Loyalty Reward | 29 | `program_id→loyalty.program`, `discount_line_product_id→product.product`, `reward_product_id→product.product` |
| `loyalty.card` | Loyalty Coupon / card / gift card / eWallet | 13 | `program_id→loyalty.program`, `partner_id→res.partner`, `history_ids→loyalty.history` |
| `loyalty.history` | Card points ledger | 7 | `card_id→loyalty.card`, polymorphic `order_id`/`order_model` |
| `loyalty.mail` | Loyalty Communication | 5 | `program_id→loyalty.program`, `mail_template_id→mail.template` |

**Central model:** `loyalty.program` — everything hangs off it. The field profile
is `Many2one`-heavy (28) with many `Boolean` (17) and `Selection` (15) flags,
reflecting a configuration engine where `program_type` toggles whole sub-records.
The module also `_inherit`-extends `product.product/template`, `product.pricelist`
and `res.partner` (adding `loyalty_card_count`).

## Behavior & Surfaces

- **Routes:** 2 — a customer **portal** card view (`/my/loyalty_card/<id>/history`,
  http) and its data feed (`/my/loyalty_card/<id>/values`, jsonrpc), both
  `auth='user'`. No storefront/admin web API here (the channels supply that).
- **Views:** form (6), list (4), kanban (2), search (2). No pivot/graph — this is
  a setup module, not an analytics one.
- **Security:** 8 access rules, **5 record rules**, **0 groups** — light, multi-
  company-scoped; it piggybacks on the host channel's groups rather than defining
  its own.

The metadata cannot show what a *program* actually does. Reads of the code
establish:

- `loyalty.program.program_type` is one of **8** values (coupons, gift_card,
  loyalty, promotion, ewallet, promo_code, buy_x_get_y, next_order_coupons).
  `_compute_from_program_type` **clears and rebuilds** `rule_ids`/`reward_ids`/
  `communication_plan_ids` from `_program_type_default_values()` when the type
  changes; `is_payment_program` is True for gift_card/ewallet. `program.write()`
  cascades `active` onto child rules, rewards and their discount products.
- `loyalty.rule` declares **when** points accrue: `reward_point_mode` (per order /
  per money / per unit), `mode` auto vs `with_code` (unique code enforced against
  other rules *and* cards), `minimum_qty`/`minimum_amount`, and
  `_get_valid_product_domain()` for eligibility. It holds no order data — matching
  is done by the consumer module.
- `loyalty.reward.create()` calls `_create_missing_discount_line_products()`,
  which **creates a `product.product`** (service, `sale_ok=False`, price 0) per
  reward to carry the discount/free product on the order; `write()` keeps that
  product's name in sync and (un)archives it with the reward.
- `loyalty.card` holds the **points balance** (`tracking=True`). `create()` fires
  the "At Creation" email; `write()` snapshots points and fires the "When
  Reaching" milestone email on increases. Balance edits (update-balance wizard,
  generate-coupons wizard) write `loyalty.history` issued/used rows. The
  order-driven debit/credit of points lives in `sale`/`pos`.

## Value-Configuration Classification

**Value model: Support (cross-cutting promotions/rewards engine).** Unlike
`sale` (a primary value-chain activity), `loyalty` does not convert demand into a
confirmed order — it **supplies the pricing/reward rules** that the primary sell
activities apply. Installed alone it changes nothing; only when `sale`,
`point_of_sale` or `website_sale` consume its `loyalty.program` do carts get
discounted, points move and reward lines appear. It is therefore firm
infrastructure for marketing & sales — a Porter **support** activity, classified
**support / support**. (One could argue `network` because gift cards/eWallets/
points create switching-cost ties to a customer base, but the code shows a rule
*engine* consumed by other modules, not a network operator — so support is the
better fit.)

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — specifically the pricing &
promotions process group (**3.2 Develop pricing strategy / manage promotions**),
not the 3.5 order-management groups that `sale` owns. The reward → discount-
product mechanism nudges the boundary of 9.0 (the discount eventually lands on an
`account.move` line), but the module's own subject matter is promotion design.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i loyalty` database:

```python
# odoo shell
progs = env['loyalty.program'].search([])
print(progs.mapped(('name', 'program_type')))
p = env['loyalty.program'].create({'name': 'Demo', 'program_type': 'promotion'})
print(p.rule_ids.read(['reward_point_mode', 'minimum_amount']))
print(p.reward_ids.read(['reward_type', 'discount', 'discount_line_product_id']))
cards = env['loyalty.card'].search([], limit=5)
print(cards.mapped(('code', 'points', 'program_type')))
# portal surface:  curl .../my/loyalty_card/<id>/values  (auth=user, jsonrpc)
```

## Open Questions (verify in code)

- The actual rule-matching and point debit/credit algorithm lives in the
  consuming modules (`sale`/`pos`/`website_sale`) — `loyalty` itself never applies
  a program to an order.
- How the clear-then-recreate of `rule_ids`/`reward_ids` in
  `_compute_from_program_type` plays against the "must have one reward" constraint
  (the `loyalty_skip_reward_check` guard in `write`).
- Lifecycle of the auto-created `discount_line_product_id` products (cleanup,
  reuse, reporting) over a reward's life.
- Whether eWallet/gift-card balances expire vs. only loyalty cards being barred
  from having an `expiration_date`.
