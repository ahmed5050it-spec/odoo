# stock_dropshipping — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + code-read of `models/`, against the `PROMPT.md`
> template. Odoo 19.0.*

The **Drop Shipping** module (`stock_dropshipping`, category *Supply
Chain/Inventory*, `application=False`) lets a vendor ship goods **directly to the
end customer** without passing through the retailer's warehouse — "no internal
transfer document is needed". Structurally it is unusual: it owns **0 `_name`
models** (11 inherit-only extensions, ~1987 Python LOC, 0 routes, 0 views beyond
3 backend form extensions). Its real artifact is a single **procurement route +
buy-rule**: it is a logistics **bridge** that wires `purchase` ⟷ `sale` ⟷
`stock` so a customer order is fulfilled by a vendor purchase in one direct move.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `sale_purchase_stock` | The tri-module glue (sale + purchase + stock). Dropshipping only makes sense once all three exist; this module splices them together. |

**Adds on top:** a pre-configured *Dropship* operation type (`stock.picking.type`
`code='dropship'`), a *Dropship* procurement route (`route_drop_shipping`), and a
per-company `stock.rule` (`action='buy'`, Suppliers → Customers) that short-
circuits Procure→Deliver into one vendor-direct shipment. Plus dropship smart-
buttons on the sale and purchase order forms.

## Data Model (the ERM)

| Model (`_inherit`) | Adds | Key relations / role |
|--------------------|------|----------------------|
| **`stock.rule`** | (methods) | The buy-rule Suppliers→Customers; `_get_partner_id` returns False on the dropship route so the move isn't re-pointed at the vendor. |
| **`stock.picking.type`** | `code` (`+dropship`) | Default src = Suppliers, dest = Customers, no warehouse. |
| `stock.picking` | `is_dropship` (computed) | True when src=supplier/transit and dest=customer/transit. |
| `sale.order` / `sale.order.line` | `dropship_picking_count` | MTO chaining + injects customer ship-to + dropship type into the auto-PO. |
| `purchase.order` / `purchase.order.line` | `dropship_picking_count` | `_is_dropshipped()`; back-links PO → originating `sale.order` (`sale_ids`). |
| `res.company` | (methods) | Auto-creates the dropship sequence, picking type and rule per company. |
| `stock.lot`, `product.product`, `stock.replenish.mixin` | (methods) | Lot partner = customer ship-to; dropship picking description; replenish UI. |

**No new entity.** There is no `dropship.order` table — the route record
(`stock.route` data) plus the company-built `stock.rule` *are* the model. The
field footprint is tiny: 2 Integer + 1 Boolean + 1 Selection across the whole
module.

## Behavior & Surfaces

Five **code-read** side-effects metadata cannot show (the point of this pass):

- **The buy-rule is dropshipping.** `res.company._create_dropship_rule()` builds
  a `stock.rule` with `action='buy'`, `location_src_id=Suppliers`,
  `location_dest_id=Customers`, `procure_method='make_to_stock'`, on a `dropship`
  picking type. Demand on the sale order is satisfied by a purchase whose
  *receipt is the delivery to the customer*, bypassing the warehouse.
- **PO is redirected to the customer.** `sale.order.line.
  _purchase_service_prepare_order_values` sets `dest_address_id =
  partner_shipping_id` and `picking_type_id = dropship` on the generated PO.
- **MTO chaining.** `sale.order.line._compute_is_mto` forces `is_mto=True` when a
  product/category route's pull rule goes supplier→customer, linking customer
  demand straight to vendor procurement.
- **Single move, counted once.** `is_dropship` reclassifies one picking;
  `sale.order` and `purchase.order` *subtract* it from `delivery_count` /
  `incoming_picking_count` and surface it as `dropship_picking_count` — so it
  isn't double-counted as both a receipt and a delivery.
- **Traceability.** A dropshipped PO links back to its `sale.order`
  (`_prepare_reference_vals`) and `_get_qty_procurement` reads PO-line quantities
  back to compute delivered qty on the sale (handling kits).

**Surfaces:** 0 web routes; **no frontend** (`extract_frontend.py`:
`present=false`, 0 JS/OWL/registry/patches); 0 external integrations; 0 security
groups/rules. Provisioning is per-company via `_create_per_company_*` hooks with
an `uninstall_hook` teardown.

## Value-Configuration Classification

**Value model: chain — activity class: support.** `stock_dropshipping` is a
**procurement/logistics route bridge** of the value chain, not a primary activity
of its own. It owns no business entity and adds a single buy-rule that splices
the **Procure** (inbound) and **Deliver** (outbound) activities into one direct
move. It is the **BRIDGE** wiring `purchase` ⟷ `sale` ⟷ `stock` for dropship
fulfillment: a vendor purchase fulfils a customer sale directly, with no
warehouse step. The chain value model is inherited from the procure-and-deliver
flow it short-circuits; it is classed **support** because it is an inbound-
logistics fulfillment *policy* layered on the `sale` (3.0) and `purchase` (4.2)
activities rather than a primary value-creating step.

## APQC PCF Hint

**4.0 Deliver Physical Products** — straddling **4.2 Procure
Materials/Services** (the vendor purchase) and **4.4 Deliver Product** (ship to
customer), collapsed into a single dropship move. It is a routing/fulfillment
configuration over those activity groups, not a new process.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i stock_dropshipping` database:

```python
# odoo shell
route = env.ref('stock_dropshipping.route_drop_shipping')          # the Dropship route
rule = env['stock.rule'].search([('route_id','=',route.id),('action','=','buy')])
print(rule.read(['location_src_id','location_dest_id','picking_type_id']))  # Suppliers -> Customers
print(env['stock.picking.type'].search([('code','=','dropship')]).mapped('name'))
# dropship pickings link both a sale and a purchase:
print(env['stock.picking'].search([('is_dropship','=',True)], limit=5).mapped(('name','sale_id','purchase_id')))
```
