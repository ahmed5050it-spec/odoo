# payment — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavioral notes from code-read, classification by
> code-architect. Odoo 19.0.*

The **Payment Engine** module (`payment`, category *Hidden*, `application=False`)
is the provider-agnostic core that lets any Odoo document collect money online.
It is **not** auto-installed and sits low in the graph: it depends only on
`onboarding` and `portal`, yet is the foundation every `payment_<provider>`
module (Stripe, PayPal, Mercado Pago, …) and every collect-cash flow
(`account_payment`, `sale`, subscriptions, eCommerce) builds on. Its center of
gravity is the `payment.transaction` model (32 fields, 53 methods) — the record
that ties a payer, an amount, a provider, a method and an optional saved token to
a guarded state machine.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `portal` | Self-service surfaces: `/my/payment_method`, saved-token management, public checkout pages. |
| `onboarding` | Guided setup of payment providers (`res.config.settings` onboarding step). |

**Adds on top:** a provider/method/token registry, a transaction state machine,
authorize/capture/void/refund, tokenization (vaulting), payment links, express
checkout, and the outbound HTTP plumbing to reach external acquirers.

high-volume operational document by itself.

## Behavior & Surfaces

- **State machine (code-read):** `_set_pending/_set_authorized/_set_done/`
  `_set_canceled/_set_error` all funnel through `_update_state`, which declares
  **allowed source states** per target (e.g. `done` only from
  draft/pending/authorized/error). Illegal transitions are refused with a
  warning; `done`/`cancel` roll child capture/void amounts up to the parent via
  `_update_source_transaction_state`. None of this is in metadata.
- **Webhook flow (code-read):** `_process(provider_code, payment_data)` finds the
  tx via `_search_by_reference`, validates the amount, applies provider updates,
  and — if `tokenize` and state ∈ {authorized, done} — calls `_tokenize` to mint
  a `payment.token`. Async settlement is retried by a cron (`_cron_post_process`)
  for up to 4 days; downstream modules override `_post_process` to create the
  `account.payment` / confirm the order.
- **External acquirer link (static, gap #7):** `payment_provider.py` imports
  `requests` and centralizes outbound HTTP in `_send_api_request` (URL/headers/
  **api-key auth** via override hooks, 10s timeout, `ValidationError` on failure).
  This is the canonical metadata-gap-#7 example — acquirer communication is
  invisible to model/field metadata.
- **Routes:** 7. Public checkout/webhook surface (`/payment/pay`,
  `/payment/transaction`, `/payment/status[/poll]`, `/payment/confirmation`) plus
  authenticated self-service (`/my/payment_method`, `/payment/archive_token`).
- **Frontend (gap #3):** 5 JS files, no OWL components — instead 4 public
  **interactions** (`payment_form`, `payment_button`, `express_checkout`,
  `payment_post_processing`) plus one backend copy-link widget.
- **Security:** 12 access rules, **5 record rules**, 0 module-owned groups —
  partner-scoped visibility of own tokens/transactions for portal self-service.

## Value-Configuration Classification

**Value model: Network (mediating technology).** `payment` interconnects two
parties who would not otherwise transact directly — the payer and the
merchant/acquirer — by provisioning a mediation service: network promotion &
contract management (provider/method onboarding, tokenization), service
provisioning (the transaction), and infrastructure operation (the `requests`
acquirer link + webhook settlement). It does **not** transform inputs to outputs
(chain) nor solve a bespoke problem (shop); it brokers a financial exchange. We
chose **network over support** deliberately: although it is an infrastructure
"Hidden" engine that, from the enterprise value-chain view, lives in the
**support** `activity_class` under finance, its own internal logic is mediation —
hence `value_model=network`, `activity_class=support`.

## APQC PCF Hint

**9.0 Manage Financial Resources** — specifically **9.5 Process payments /
collect cash** (online collection, tokenized charges, capture/refund). The
onboarding and link wizards touch the configuration boundary of 9.x.

## How to Drive It

```python
# odoo shell
env['payment.provider'].search([]).mapped(('name', 'code', 'state'))
txs = env['payment.transaction'].search([], limit=5)
print(txs.mapped('reference'), txs.mapped('state'), txs.mapped('amount'))

# initiate via http jsonrpc: curl .../payment/transaction (auth=public)
```
