# sale_timesheet — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from code-read, narrative per `PROMPT.md`.*

The **Sales Timesheet** module (`sale_timesheet`, category *Sales/Sales*,
`application=False`, **`auto_install=True`**) is the **billing bridge of the
value-shop**: it makes logged effort sellable. It depends on just two modules —
`sale_project` and `hr_timesheet` — and exists only as the connective tissue
between them. It owns a single new model and otherwise *extends* 15 existing
ones (≈7,800 LOC Python, 4,140 XML). Its center of gravity is the link
`account.analytic.line.so_line → sale.order.line`: the field that routes every
timesheet hour to the billable sales line it should feed.

## Role & Dependencies

| Depends on | Why (from manifest + code) |
|------------|----------------------------|
| `sale_project` | Gives projects/tasks a `sale.order` link (`sale_line_id`); this module builds billing on top of it. |
| `hr_timesheet` | Supplies `account.analytic.line` as timesheets (logged effort); this module makes those hours billable. |

**Adds on top:** delivered-timesheet service policy, three pricing modes
(task / project / employee rate), invoice-on-delivered-hours, project
profitability, a timesheet-revenue analysis report, and a master *Service on
Timesheets* product.

**Central join:** `account.analytic.line` (the timesheet) — it gains `so_line`,
`order_id`, and `timesheet_invoice_id`, the three edges that turn an hour into
revenue. Only **one** model is genuinely new; the value is in the extensions.

## Behavior & Surfaces (the metadata gap)

The interesting logic is invisible to metadata — it lives in compute methods:

- **Hours → delivered qty.** For a `service_type='timesheet'` product,
  `sale.order.line._compute_qty_delivered_method` sets the method to
  `'timesheet'` and `_prepare_qty_delivered` computes `qty_delivered` by summing
  logged hours (`_get_delivered_quantity_by_analytic`), **not** from stock. This
  is the monetization step.
- **Hour → right billable line.** `account.analytic.line._compute_so_line` /
  `_timesheet_determine_sale_line` resolve `so_line` from the project's
  `pricing_type`: *task_rate*→task SOL, *fixed_rate*→project SOL,
  *employee_rate*→the employee map entry (with fallbacks). This routes each hour
  to the correct unit price.
- **Deliver → invoice.** `account.move._link_timesheets_to_invoice` stamps
  `timesheet_invoice_id` on the period's hours; `_recompute_qty_to_invoice`
  bills only not-yet-invoiced hours; posting an `out_refund` clears the stamp so
  hours become re-billable.
- **Routes:** 1 portal route — `/my/tasks/<task_id>/orders/invoices`
  (`auth='user'`, `type='http'`). **Frontend:** 1 OWL component, `SoLineField`
  (`fields:so_line_field`, also in the `project.webclient` bundle) for picking
  the sales item on timesheet grids. **Integrations:** none (no HTTP/SDK).
- **Security:** 2 access + **2 record rules**, 0 new groups — the rules narrow
  `account.analytic.line` rules to `project_id=False` so `hr_timesheet`'s
  own-timesheet rules govern project lines; permissions are reused.

## Value-Configuration Classification

**Value Shop (problem-solving) — the monetization bridge. `primary`.** Per
Stabell & Fjeldstad, the value-shop solves a unique customer problem through
cyclical logged effort; value is *known by delivered effort*. `sale_timesheet`
is the seam that realizes that value as revenue: it joins the **shop** side
(`project` + `hr_timesheet`, where the work happens) to the **chain/cash** side
(`sale`, `account`). It turns delivered effort into
`sale.order.line.qty_delivered`, prices each hour via the pricing-type/employee
map, and invoices on delivered hours. The product master it ships —
*Service on Timesheets* (`type=service`, `service_policy=delivered_timesheet`,
UoM hour) — is exactly the value-shop product definition. It is **primary** (on
the revenue-producing service-delivery path), not support.

## How to Drive It

Use the `run-odoo` skill. With the server up and an `-i sale_timesheet` database:

```python
# odoo shell
env.ref('sale_timesheet.time_product').read(['name','service_policy','type','list_price'])
sols = env['sale.order.line'].search([('qty_delivered_method','=','timesheet')], limit=5)
print([(l.product_id.name, l.qty_delivered, l.remaining_hours) for l in sols])
print(env['project.project'].search([('allow_billable','=',True)], limit=5).mapped(('name','pricing_type')))
```
