# event_booth_sale — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/` + `wizard/`, narrative
> per `PROMPT.md`. Odoo 19.0.*

The **Events Booths Sales** module (`event_booth_sale`, category
*Marketing/Events*, `version 1.2`, `application=False`) is the **auto-installed
bridge** that makes exhibitor booths sellable: it joins `event_booth` (the booth
catalog + available/unavailable assignment) to `event_sale`/`sale` (quotations,
pricing, invoicing). A booth category gets a linked product and a price; a booth
is chosen on a sale order line through a configurator wizard; confirming the
order books the booth (flips it to *unavailable*, stamps the partner/contact);
paying the invoice flags the booth paid. The module adds only two new models —
`event.booth.registration` and the transient `event.booth.configurator` — and
extends eight existing ones. Public/online booth checkout is **not** here; it
lives in `website_event_booth`.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `event_booth` | Provides `event.booth`, `event.booth.category`, `event.type.booth` and the available/unavailable state this module prices and sells. |
| `event_sale` | Brings the `sale`/`product`/`account` chain (sale.order(.line), product service_tracking, invoicing) the booth is bolted onto. |

**Adds on top:** product-driven booth pricing, a sale-order booth configurator,
a multi-bidder reservation buffer, order-confirmation booking, and paid-on-invoice.

`auto_install=True` — installs automatically once both `event_booth` and
`event_sale` are present.

## Behavior beyond metadata (code-read)

- **Category pricing via a linked product:** a booth category requires a
  `product_id` (domain `service_tracking='event_booth'`, default
  `product_product_event_booth`). `price` is a stored editable compute seeded
  from `product_id.list_price + price_extra`; `price_incl` runs `taxes_id.compute_all`;
  `price_reduce`/`price_reduce_taxinc` apply the contextual pricelist discount
  (`@api.depends_context(*PRICE_CONTEXT_KEYS)`). `event.type.booth` re-exposes
  product/price/currency as `related` so templates carry pricing.
- **Confirming the order books the booth:** `sale.order.action_confirm` super-confirms,
  then for each `event_booth` line raises unless `event_booth_pending_ids` is set,
  then `_update_event_booths` re-checks availability and calls
  `event.booth.registration.action_confirm` → `event.booth.action_confirm(values)`,
  which flips `state='unavailable'` **and** writes the SO line / partner /
  contact onto the booth, then cancels every rival registration and `_action_cancel`s
  their orders.
- **Multi-bidder reservation buffer:** `event.booth.registration` (O2m on both the
  SO line and the booth) lets several draft orders hold the same booth; the
  pending-ids inverse creates/unlinks one registration per selected booth. A
  `unique(sale_order_line_id, event_booth_id)` constraint and a one-event check
  guard it.
- **The event-booth product type:** `service_tracking='event_booth'` (selection_add)
  forces `invoice_policy='order'`, is excluded from the catalog domain, and is
  locked once a product is bound to a category. `sale.order.line._get_display_price`
  sums `booth_category_id.price_reduce` over pending booths instead of the bare
  product price.
- **Paid on invoice:** `account.move._invoice_paid_hook` walks `sale_line_ids`
  and calls `_update_event_booths(set_paid=True)` → `event.booth.action_set_paid`
  (`is_paid=True`); booths linked to an SO can't be deleted.

## Frontend (gap #3, static)

Thin backend-only JS: **2 js files, 0 OWL components, 0 XML templates**, one
registry add (`views:event_booth_configurator_form`) and one patch
(`SaleOrderLineProductField.prototype`) that intercepts selecting an event-booth
product on a sale order line and opens the booth configurator. Bundle:
`web.assets_backend` only — no storefront bundle (that is `website_event_booth`).

## Integrations (gap #7, static)

None: 0 HTTP call sites, no SDK imports, no API keys, no endpoints. All
pricing/tax/discount runs through Odoo's in-process product, pricelist and
account engines.

## Classification

- **Value model:** `network` (primary). The booth value-network — a fixed
  capacity of stands matched to exhibitors, reserved by multiple bidders and
  allocated *available→unavailable* on the winning order — bridged to the sales
  chain so the booking carries a price, an invoice and a paid flag. Matching to
  shared capacity, not sequential transformation.
- **APQC:** **3.0 Market and Sell Products and Services** — event booth /
  sponsorship sales: price the offering, configure it on a quotation, confirm
  the order, recognise payment.

## Fit-to-Standard & Open Questions

**Standard:** sellable booth categories with derived/tax/discounted prices,
booth configurator on the order line, multi-bidder reservation resolved at
confirmation, auto-booking + rival-order cancellation, order-policy invoicing,
paid-on-invoice flag. **Typical fits:** trade shows selling priced stands,
sponsorship packages, event-type templating. **Common gaps:** public/online
booth checkout (`website_event_booth`), deposit/partial-payment invoicing,
floor-plan stand picker, approval/waitlist workflow.

**Open questions:** whether partial payments should set `is_paid`; how
`website_event_booth` selection interacts with the reservation buffer; whether
multi-company scoping is expected given no record rules are added.
