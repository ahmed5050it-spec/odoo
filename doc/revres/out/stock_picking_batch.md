# stock_picking_batch — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` + key-model
> code-reads, narrated per the `PROMPT.md` template. DEEP upgrade of the baseline.*

The **Warehouse Management: Batch Transfer** module (`stock_picking_batch`,
category *Supply Chain/Inventory*, `application=False`, v1.0, LGPL-3) is a thin,
high-leverage add-on on top of `stock`. It introduces **batch** and **wave**
picking: grouping many `stock.picking` transfers into a single
`stock.picking.batch` that one worker processes together. It owns just **3 new
models** (~3.9k Python LOC, ~1k XML LOC), defines **no routes**, and adds only a
single field widget on the frontend — almost all of its value is server-side
ORM orchestration that re-uses the parent's move ledger rather than extending it.

## Role & Dependencies

Depends only on **`stock`** — the transfers being grouped
(`stock.picking`/`stock.move`/`stock.move.line`, picking types, reservation,
backorders). **Adds on top:** `stock.picking.batch` (batch *and* wave, via
`is_wave`), two wizards (`stock.picking.to.batch`, `stock.add.to.wave`), a
`batch_id` link on `stock.picking`/`stock.move.line`, and a block of auto-batch /
wave-grouping / capacity config fields on `stock.picking.type`.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`stock.picking.batch`** | Batch Transfer (`mail.thread`) | 20 | `picking_ids→stock.picking` (via `batch_id`), `picking_type_id`, `user_id→res.users`, `move_ids`/`move_line_ids` (computed) |
| `stock.add.to.wave` | Wave Transfer Lines (wizard) | 5 | `wave_id→stock.picking.batch`, `line_ids→stock.move.line` |
| `stock.picking.to.batch` | Batch Transfer Lines (wizard) | 5 | `batch_id→stock.picking.batch`, `user_id→res.users` |
| `stock.picking.type` *(inherited)* | +`auto_batch`, `batch_max_lines/pickings`, wave/batch group-by | 16 | `wave_category_ids→product.category`, `wave_location_ids→stock.location` |
| `stock.picking` / `stock.move.line` *(inherited)* | +`batch_id` link / wave split | 2 / 1 | `batch_id→stock.picking.batch` |

**Central model:** `stock.picking.batch` (34 methods) is an *orchestrator*, not a
new ledger — its `move_ids`/`move_line_ids` are computed off `picking_ids`. The
field profile is flag-heavy (`Boolean` on the picking-type config) reflecting an
options surface, not a new transactional object.

## Behavior & Surfaces

- **The batch state machine is a thin facade over member pickings.**
  `action_confirm` propagates `picking_ids.action_confirm()` and sets
  `in_progress`; `action_done` runs a *batch-wide* `_sanity_check`, detaches
  empty pickings, then `button_validate()`s all members at once (suppressing
  per-picking validation). `state` is a **stored compute** that auto-flips to
  `done`/`cancel` from member states (code-read).
- **Wave picking splits at the move-line level.** `_add_to_wave` links a whole
  picking if every line is taken, else `copy_data`-clones the picking and
  `move._split(qty)`s the taken quantity into a new move; `_auto_wave` buckets
  reservable lines by `wave_group_by_product / _category / _location` (code-read).
- **Assigning a batch re-owns its transfers.** Writing `user_id` cascades via
  `assign_batch_user` onto every member `stock.picking.user_id` with a chatter
  note (code-read).
- **Auto-batching is scheduler-like with capacity caps.** On reaching
  `assigned`, `_find_auto_batch` finds/creates a compatible batch only if
  `_is_picking_auto_mergeable` passes `batch_max_lines` / `batch_max_pickings`;
  a constraint forces ≥1 group-by when `auto_batch` is on (code-read).
- **Routes:** none. **Frontend:** 1 JS file, 0 OWL, one `fields:stock_picking_many2many`
  widget (static). **Views:** form (1), list (2), kanban (1), calendar (1).
- **Security:** 3 access rules, 1 record rule, **0 own groups** — everything
  reuses `stock.group_stock_user`.

## Value-Configuration Classification

**Value Chain, *support* activity.** The module lives in the same value-chain
logistics flow as `stock` (warehouse fulfillment, the *deliver* chain), so
`value_model = chain`. But unlike `stock` — a *primary* activity through which
goods physically pass — this is an **efficiency layer**: it groups existing
transfers and routes a worker's effort; it does not create stock moves or own a
transfer's state machine. It optimizes *how* picking is executed (fewer walks),
hence `activity_class = support`.

## APQC PCF Hint

**4.0 Deliver Physical Products** — specifically the 4.x **warehousing / order
picking** operations (operate warehousing, pick & stage product for shipment).
Per `apqc_odoo_map.tsv`, the configured surface anchors to **4.4.1.4**
develop/maintain delivery service policy (`stock.picking.type`) and **4.4.x**
operate outbound transportation (the grouped `stock.picking.button_validate`).

## How to Drive It

Use the `run-odoo` skill with an `-i stock_picking_batch` database:

```python
# odoo shell
pt = env['stock.picking.type'].search([('code','=','outgoing')], limit=1)
pt.write({'auto_batch': True, 'batch_group_by_dest_loc': True, 'batch_max_pickings': 5})
ids = env['stock.picking'].search([('state','=','assigned'),('picking_type_id','=',pt.id)], limit=3).ids
b = env['stock.picking.batch'].create({'picking_type_id': pt.id, 'picking_ids':[(6,0,ids)]})
b.action_confirm(); print(b.state)   # -> in_progress;  b.action_done() validates all members
ml = env['stock.move.line'].search([('picking_id.state','=','assigned')], limit=2)
# ml._add_to_wave()                  # split lines into a new wave transfer
```
