# project_todo — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads of `models/project_task.py`, `models/res_users.py`,
> `wizard/mail_activity_todo_create.py`, `security/project_todo_security.xml`,
> and `__init__.py` (post_init hook).*

The **To-Do** module (`project_todo`, category *Productivity/To-Do*,
version 1.0, `application=True`, `auto_install=True`) turns the Project task
engine into a **personal memo / to-do list** app. It is unusual among the
documented subsystems in that it adds almost **no data model of its own**: it
defines exactly one (transient) model and otherwise *re-purposes* the existing
`project.task` through a security record rule, two model extensions, and a
custom OWL view layer. It depends on a single module — `project` — and is
auto-installed alongside it, so every Project deployment gets a To-Do app for
free. Its center of gravity is not a table but a **definition**: a "to-do" is a
private, project-less, top-level `project.task` owned by one user.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `project` | The whole point — it reuses `project.task` as its storage and engine. To-Dos *are* tasks with no `project_id`; the staged-task lifecycle, chatter, activities, and views all come from `project`. |

**Adds on top:** a security record rule that carves "private tasks" out of the
shared task pool, auto-naming a task from the first line of its note, a
convert-to-task promotion, a systray that splits To-Do vs Task activity counts,
an onboarding welcome memo, a "schedule activity + to-do together" wizard, and a
dedicated OWL/JS view set (form, list, kanban, calendar, activity) — see
`__manifest__.py` `assets`.

## Data Model (the ERM)

| Model (`_name` / `_inherit`) | Kind | Description | #fields | Key relations |
|------------------------------|------|-------------|--------:|---------------|
| **`mail.activity.todo.create`** | `TransientModel` (wizard) | Create activity and todo at the same time | 4 | `user_id→res.users` |
| `project.task` | **extension** (`_inherit`, no `_name`) | — | 0 new | reuses `project.task` as-is |
| `res.users` | **extension** (`_inherit`, no `_name`) | — | 0 new | patches the activity systray |

**Central "model":** there isn't a new one — the central entity is the
inherited **`project.task`**, used in its project-less form. The only concrete
model, `mail.activity.todo.create`, is a throwaway wizard. Field-type
distribution is the tell: the *entire* module declares **4 fields** (`Char` 1,
`Date` 1, `Many2one` 1, `Html` 1), all on that wizard; the two extensions add
**zero** fields. This is the inverse of a relational data module — `project_todo`
is **behavior- and UI-heavy, schema-empty** (589 Python LOC, 663 XML LOC, but a
1-model footprint).

## Behavior & Surfaces

Read from code (the metadata gap — the static facts only show this module is
"thin"):

- **A "to-do" is a private, project-less task.** The sole record rule
  `task_edition_rule_internal` scopes `base.group_user` to
  `[('project_id','=',False), ('user_ids','in',user.id), ('parent_id','=',False)]`.
  That domain *is* the definition of a to-do: a top-level task, no project, owned
  by the current user. The same `project_task` table backs both Project tasks and
  To-Dos; the discriminator everywhere is `BOOL(project_id)`.
- **Auto-naming from the memo.** `ProjectTask.create` override: when a record has
  no `name`, no `project_id`, and no `parent_id`, it derives the title from the
  first line of the HTML `description` (`html2plaintext`, stripped of `*`,
  truncated to ~100 chars) — or falls back to `"Untitled to-do"`. Type a note;
  the title writes itself.
- **Convert-to-task is a one-field promotion.** `action_convert_to_task` stamps
  `company_id` from the chosen project and re-opens the *same* record in the
  standard task form — a to-do becomes a real task simply by gaining a
  `project_id`. No data migration; same row.
- **Systray splits To-Do vs Task.** `res.users._get_activity_groups` removes the
  merged `project.task` activity group and runs a raw SQL query grouping by
  `BOOL(project_id)` to emit two systray buckets — "To-Do" (`is_todo=True`) and
  "Task" — each with today/overdue/planned counts. (The JS side patches
  `ActivityMenu.prototype` to render them.)
- **Onboarding seeds a welcome to-do.** The `post_init_hook` `_todo_post_init`
  and `_onboard_users_into_project` call `_generate_onboarding_todo`, which
  renders the `project_todo.todo_user_onboarding` QWeb template per non-share user
  and creates a welcome memo as `SUPERUSER_ID` with `mail_auto_subscribe_no_notify`.
- **Wizard creates task + activity together.** `mail.activity.todo.create
  .create_todo_activity` creates a `project.task` *and* a linked `mail.activity`
  on it in one transaction, then returns a `display_notification` ("added to your
  pipeline").

**Surfaces:**
- **Routes:** **0** — no web/RPC controller of its own (`integrations`: 0 HTTP
  call sites, no SDKs, no API keys). All client interaction goes through the
  generic web client acting on `project.task`.
- **Views:** form (3: todo form, conversion form, activity wizard), list (1),
  kanban (1), search (1), calendar (1), activity (1) — a full single-model app
  surface registered via `get_todo_views_id()`. **Frontend is the real weight:**
  14 JS files, 1 OWL component (`TodoChatterPanel`), 6 registry adds (field
  `todo_done_checkmark`, view-widget `todo_chatter_panel`, views
  `todo_form/todo_list/todo_conversion_form/todo_activity_wizard`), and the
  `ActivityMenu.prototype` patch, across `web.assets_backend` (+ test bundles).
- **Security:** 4 ACLs (`project.task`, `project.task.type`, `project.tags`,
  the wizard), **1 record rule** (the privacy rule above), **0 new groups** — it
  reuses `base.group_user`.

## Value-Configuration Classification

**Structurally `shop`-derived; functionally a `support` / personal-productivity
overlay.** Because it reuses `project.task`, `project_todo` inherits the
**value-shop** DNA of `project` (Stabell & Fjeldstad intensive technology: a
task lifecycle for solving discrete pieces of work). But the to-do variant is
deliberately *de-projected* — private, project-less, single-owner — so its real
job is **individual work organization**, not customer-facing service delivery.
That makes its activity role **support / cross-cutting personal effectiveness**
(everyone's memos and next actions), rather than a *primary* value activity.
*(The auto-architect metamodel baseline tags it `shop`/`primary` by inheritance
from `project`; the code-read above refines that to a personal-productivity
support overlay — marked inferred.)*

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). There are **no routes to
curl** — drive it through `odoo shell` on the `project.task` model:

```python
# odoo shell — the to-dos are project-less, top-level, owned tasks
todos = env['project.task'].search([
    ('project_id', '=', False),
    ('parent_id', '=', False),
])
print(todos.mapped(('name', 'user_ids.name', 'date_deadline')))

# the view ids the To-Do app loads (kanban/list/form/calendar/activity)
print(env['project.task'].get_todo_views_id())

# the "schedule activity + to-do" wizard model
print(env['mail.activity.todo.create'].fields_get(
    ['summary', 'date_deadline', 'user_id', 'note']).keys())
```

The privacy record rule means a non-admin user only ever sees their *own*
project-less tasks — verify by searching the same domain as a regular user.
