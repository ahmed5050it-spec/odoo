# stock_delivery — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, code-read behavioral notes, and the `PROMPT.md`
> template. The bridge that wires the `delivery` carrier abstraction into
> `stock` picking execution.*

The **Delivery - Stock** module (`stock_delivery`, category *Shipping
Connectors*, `application=False`, **`auto_install=True`**) is **THE BRIDGE** that
the base `delivery` module deliberately deferred. `delivery` defines *how a
shipment is rated and which carrier ships it* but has **no `stock` dependency and
no `stock.picking` model**; `stock` performs the physical transfer but knows
nothing of carriers. This module is where the two meet: it puts `carrier_id` on
`stock.picking` and, at `button_validate`, **actually executes the ship** —
`send_to_shipper → delivery.carrier.send_shipping('<type>_send_shipping')` —
captures the tracking number, and feeds the real cost back into Quote-to-Cash. It
declares **0 own `_name` models**; it is a pure extension of **13 inherit-only**
models. Its center of gravity is the `stock.picking` extension (12 fields, 21
methods).

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `delivery` | Supplies the `delivery.carrier` abstraction (rate/ship/track/cancel SPI) that this module *invokes* from the picking. |
| `sale_stock` | Joins `sale.order` ↔ `stock.picking`, so the carrier set on the order reaches the transfer and the real cost rides back to the order line. |

**Adds on top:** carrier-aware transfers — send-to-shipper on validate, tracking
capture, shipment cancellation, packing weight/carrier-package codes, real-cost
delivery invoicing, and carrier propagation through pick-pack-ship. It is
`auto_install`, so installing both `delivery` and `sale_stock` silently
activates the bridge.

## Behavior & Surfaces

- **Send-to-shipper at validate (code-read):** `button_validate →
  _send_confirmation_email` calls `send_to_shipper()` when
  `carrier_id.integration_level == 'rate_and_ship'` (non-incoming, no existing
  ref, `print_label`). `send_to_shipper` calls `carrier_id.send_shipping(self)`
  (reflective `<type>_send_shipping`), applies `free_over`/margins to
  `carrier_price`, writes `tracking_number` into `carrier_tracking_ref` across
  related up/down-stream pickings, posts chatter, and calls
  `_add_delivery_cost_to_so`. A carrier `UserError` *after* one picking already
  shipped is downgraded to a warning activity, not a batch rollback.
- **Tracking & cancel (code-read):** `carrier_tracking_url` is computed via
  `carrier_id.get_tracking_link(picking)`; `open_website_url` opens the courier
  page or posts multi-tracker links. `cancel_shipment` calls
  `carrier_id.cancel_shipment` (`<type>_cancel_shipment`), clears the ref, posts
  chatter.
- **Real-cost invoicing (code-read):** when `invoice_policy == 'real'`,
  `_add_delivery_cost_to_so` rewrites the zero-priced delivery `sale.order.line`
  with the actual `carrier_price` (under `allow_delivery_cost_update`).
- **Carrier propagation (code-read):** `propagate_carrier` rules copy
  `carrier_id`/`carrier_tracking_ref` onto new and next transfers
  (`_get_new_picking_values`, `_key_assign_picking`, post-validate), keeping the
  carrier consistent across multi-step routes.
- **Packing (code-read):** the `stock.put.in.pack` wizard computes
  `shipping_weight`, warns past `max_weight`, and forbids mixing carriers in one
  package; `stock.package.type` maps `shipper_package_code` from the carrier.
- **External integrations (static, gap #7):** 0 HTTP call sites, 0 SDK imports;
  it *dispatches* to the SPI but makes no external call — the built-in
  `fixed`/`base_on_rule` providers return stubs (`tracking_number=False`, cancel
  `NotImplementedError`). Real carrier APIs live in `delivery_*` connectors.
- **Frontend (gap #3):** none — `present=false`, 0 JS/XML, server-side only.
- **Security:** 7 access rules cross-granting `delivery.carrier` /
  `delivery.price.rule` / `delivery.zip.prefix` / `choose.delivery.carrier` to
  `stock.group_stock_user` (read) and `stock.group_stock_manager` (write); 0
  record rules, 0 routes.

## Value-Configuration Classification

**Value Chain — support activity.** `stock_delivery` realizes the
**outbound-logistics carrier-execution** leg of the value chain, so its value
model is **chain**. It is THE BRIDGE `delivery` ↔ `stock` that the base
`delivery` module deferred — the place where carrier abstraction and physical
transfer connect and the ship-to-shipper integration actually fires. It is a
**support** activity, not primary: it *operates/provisions* shipping for the
chain (SPI dispatch, packing, tracking, invoicing) rather than being the primary
order-fulfilment act, and the concrete external carrier API is still delegated to
`delivery_*` connectors (gap #7).

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i stock_delivery` database:

```python
# odoo shell
p = env['stock.picking'].search([('carrier_id','!=',False),('state','=','done')], limit=1)
print(p.read(['carrier_id','carrier_tracking_ref','carrier_price','carrier_tracking_url']))
c = env['delivery.carrier'].search([('delivery_type','=','fixed')], limit=1)
print(hasattr(c, 'fixed_send_shipping'))           # SPI dispatch surface
pick = env['stock.picking'].search(
    [('carrier_id.integration_level','=','rate_and_ship'),('state','=','assigned')], limit=1)
# pick.sudo().send_to_shipper()                    # exercises the bridge end-to-end
```
