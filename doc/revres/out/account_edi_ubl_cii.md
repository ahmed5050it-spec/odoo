# account_edi_ubl_cii — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Import/Export electronic invoices with UBL/CII** module
(`account_edi_ubl_cii`, category *Accounting/Accounting*, `application=False`,
**`auto_install=True`**) is the **e-invoicing serialization engine** that sits on
top of Accounting. It carries no business documents of its own: it teaches
`account.move` how to **serialize** a posted invoice into a legally-mandated
structured XML (UBL 2.0/2.1, Peppol BIS 3, Factur-X/CII, XRechnung, NLCIUS,
E-FFF, A-NZ, SG) and how to **parse** an inbound XML or Factur-X PDF back into a
draft invoice or vendor bill. Because it auto-installs with `account`, every
Accounting database silently gains UBL/CII import-export. Its center of gravity
is a tower of abstract format models (`account.edi.common` →
`account.edi.ubl`/`account.edi.xml.ubl_20` → `account.edi.xml.ubl_bis3` and the
country CIUS layers; `account.edi.xml.cii` for Factur-X) plus a thin
`account.move` extension that holds the generated XML attachment.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `account` | The whole point: it extends `account.move`, `account.move.send`, `account.tax` to attach an EDI layer to the invoice/bill lifecycle. |

**Adds on top:** a hierarchy of abstract XML builder/parser models, three new
fields on `account.move` (`ubl_cii_xml_id`, `ubl_cii_xml_file`,
`ubl_cii_xml_filename`), UBL/CII tax-category & exemption-reason codes on
`account.tax`, and Peppol endpoint / invoice-format selection on `res.partner`.
It is **auto-installed**, so it is best read as a built-in capability of
Accounting rather than an optional app. 14397 lines of Python and 13693 of XML
(the CII/QWeb templates) implement the format mappings.

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`account.edi.common`** | Common EDI functions (data gen, constraints) | 0 | abstract base |
| **`account.edi.ubl`** | Base helpers for UBL | 0 | `_inherit→account.edi.common` |
| `account.edi.xml.ubl_20` | UBL 2.0 builder/parser | 0 | `_inherit→account.edi.ubl` |
| `account.edi.xml.cii` | Factur-X / XRechnung CII 2.2.0 | 0 | `_inherit→account.edi.common` |
| `account.edi.xml.ubl_bis3` | UBL BIS Billing 3.0.12 (Peppol) | 0 | `_inherit→account.edi.xml.ubl_21 + account.edi.ubl_pint_eu` |
| **`account.move`** (ext) | invoice carrying the UBL/CII XML | 3 | `ubl_cii_xml_id→ir.attachment` |
| `account.move.send` (ext) | embeds XML into the sent PDF/email | 0 | — |
| `account.tax` (ext) | UBL/CII tax category + exemption codes | 3 | — |
| `res.partner` (ext) | invoice EDI format + Peppol EAS/endpoint | 6 | — |

**Central model:** there is no new business entity — the engine orbits the
existing **`account.move`**. Of the 14 models, 6 are pure `_inherit` extensions
and the rest are **abstract** format models with **zero stored fields**: they are
pure behavior (the UBL family has 223 methods on `account.edi.ubl` alone, 88 on
`ubl_20`). The only persisted state is the XML attachment on the move and a
handful of Selection/code fields on tax and partner. This is why the metadata
field census is tiny while the Python LOC is large.

## Behavior & Surfaces

- **Routes:** 0. The module exposes **no controllers** of its own; it is driven
  from the existing Accounting UI (invoice Send/Print, journal Advanced
  Settings, partner & tax forms).
- **Frontend:** **none** — 0 JS files, 0 OWL components, 0 registry adds, no
  patches; the sole asset is one backend SCSS bundle entry. A headless engine.
- **Integrations:** **0 outbound HTTP call sites, no SDK imports, no API keys.**
  It only *builds and parses* XML; actual Peppol network transmission lives in a
  separate module.
- **Views:** 0 dedicated view files counted; it injects fields into existing
  `account.tax`, `account.move` and `res.partner` forms via 3 static XML views.
- **Security:** 0 access rules, 0 record rules, 0 groups — it inherits the
  Accounting security model wholesale.

The metadata cannot show what **serialize / parse** mean. Reads of the code
establish:

- `account.move._get_import_file_type` / `_get_edi_decoder` — **inbound
  routing**: sniffs the XML root tag, `UBLVersionID` and `CustomizationID` to
  pick the format model (CII→`account.edi.xml.cii`; `xrechnung`→`ubl_de`;
  en16931/peppol billing:3.0→`ubl_bis3`), then dispatches that model's
  `_import_invoice_ubl_cii` as the decoder (priority 20).
- `account.edi.xml.ubl_20._export_invoice` — **outbound pipeline**: validates
  taxes, builds a structured `document_node` dict (header, supplier party, lines,
  `LegalMonetaryTotal`, tax subtotals), runs `_export_invoice_constraints`
  (EN16931 business rules like BR-08/BR-09/BR-CO-26), renders bytes via
  `dict_to_xml`, and returns a `(xml_bytes, errors_set)` tuple so invalid
  invoices are reported rather than shipped. (CII does the same via a QWeb
  template render.)
- `account.edi.common._import_invoice_ubl_cii` — **parse-to-record**: refuses a
  move that already has lines, derives `move_type` + `qty_factor` (credit-note
  sign flip), retrieves-or-creates the partner (`_import_partner`, matched on
  VAT / Peppol EAS+endpoint), fills currency/bank/lines, then
  `_correct_invoice_tax_amount` overrides Odoo-computed tax when it is <0.05 off
  the XML, stamps the source XML onto `ubl_cii_xml_file`, and extracts embedded
  `AdditionalDocumentReference` PDFs as attachments.
- `account.move.send._hook_invoice_document_after_pdf_report_render` — **PDF↔XML
  round-trip**: after the PDF renders, for facturx/zugferd it **always silently
  embeds a Factur-X XML inside the PDF (PDF/A-3)** so the receiver can recover the
  structured data from the PDF alone; the XML is also added as a mail attachment.
- `res.partner._get_edi_builder` — **format→builder strategy table**: the
  recipient's `invoice_edi_format` selects the concrete builder
  (facturx/zugferd share `account.edi.xml.cii`), and `_need_ubl_cii_xml` gates
  export to sale documents / self-billing whose partner uses a real UBL/CII
  format.

## Value-Configuration Classification

**Value model: Support (Stabell & Fjeldstad / Porter support activity).**
`account_edi_ubl_cii` creates no primary-chain value of its own — it is a
**compliance / infrastructure enabler** that serializes and parses invoices
to/from legally mandated formats around `account.move` and **feeds the
accounting back-office**. It has no models, routes, UI or data of its own beyond
the Accounting layer it extends. Classified **support / support**.

## APQC PCF Hint

**9.0 Manage Financial Resources.** The engine is the format/transport adapter on
the document-exchange edge of accounting: it dresses **9.2.x Process accounts
receivable** (export a posted customer invoice as compliant UBL/CII) and **9.5.x
Process accounts payable** (import an inbound XML/Factur-X into a vendor bill).
It does not itself post ledger entries — it shapes the documents that `account`
posts and receives — so it sits squarely in the statutory/regulatory-compliance
corner of 9.0.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i account_edi_ubl_cii` database:

```python
# odoo shell — export a posted invoice and inspect the constraint errors
inv = env['account.move'].search(
    [('move_type','=','out_invoice'),('state','=','posted')], limit=1)
builder = env['res.partner']._get_edi_builder('ubl_bis3')
xml, errs = builder._export_invoice(inv)
print(errs)            # set() if EN16931-compliant
print(xml[:400])       # UBL Bis 3 header

# Factur-X / CII variant (shared by France & Germany):
xml2, errs2 = env['account.edi.xml.cii']._export_invoice(inv)
print(xml2[:400])
```

In the UI: open a posted customer invoice → **Print / Send** — the UBL/CII XML is
generated and embedded in the PDF (PDF/A-3 Factur-X); or use **Export XML** on
the print menu (`account.move.action_invoice_download_ubl`). Inbound: drop an
e-invoice XML or Factur-X PDF on a purchase journal alias and the decoder builds
the vendor bill.
