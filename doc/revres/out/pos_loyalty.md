# pos_loyalty — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from
> `extract_module.py` / `extract_frontend.py` + code-read of the models AND the
> static OWL/JS engine. Odoo 19.0.*

The **Point of Sale - Coupons & Loyalty** module (`pos_loyalty`, category
*Sales/Point Of Sale*, `application=False`) is the **promotions & rewards layer of
the Point of Sale**. It is **auto-installed** as the bridge between `loyalty` (the
program/reward engine) and `point_of_sale` (the till), and it lets a cashier apply
coupons, promo codes, automatic promotions, gift cards, eWallets and points-based
loyalty inside a POS order. Its center of gravity is **not** Python: ~13 JS / 6 XML
files of OWL patched into the offline terminal carry the entire redemption engine,
over a slim backend of 14 `_inherit` extensions (5084 Python / 484 XML LOC) — there
are **no new `_name` models and no HTTP routes of its own**.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `loyalty` | The program/rule/reward/card engine — 8 program types, point accrual, discount/free-product rewards, the issued `loyalty.card` balance and `loyalty.history` ledger. `pos_loyalty` consumes and redeems these at the till. |
| `point_of_sale` | The base terminal — the offline OWL SPA, `pos.order`/`pos.session`/`pos.config`, data-load + `sync_from_ui`, hardware/printing. `pos_loyalty` injects loyalty screens and reward lines into it. |

**Adds on top:** till-side application of coupons/promo codes, points earn &
redeem on POS orders, gift-card sale + redemption (printed + e-mailed), eWallet
top-up/pay/refund, and the server write-back that commits points after checkout.

## Data Model (the ERM)

| Model (`_name`) | Role | +fields | Key relations |
|-----------------|------|--------:|---------------|
| `loyalty.card` *(ext)* | POS-sourced coupon / card | +2 | `source_pos_order_id→pos.order`, `source_pos_order_partner_id→res.partner` |
| `loyalty.program` *(ext)* | POS-enabled program | +4 | `pos_config_ids→pos.config`, `pos_ok`, `pos_order_count`, `pos_report_print_id→ir.actions.report` |
| `loyalty.rule` *(ext)* | POS-filtered earning rule | +3 | `valid_product_ids→product.product`, `any_product`, `promo_barcode` |
| `pos.order.line` *(ext)* | reward / payment line | +5 | `reward_id→loyalty.reward`, `coupon_id→loyalty.card`, `is_reward_line`, `reward_identifier_code`, `points_cost` |
| `pos.order` / `pos.config` / `pos.session` *(ext)* | redemption methods | 0 | validate/confirm coupon programs; `_get_program_ids`; `_load_pos_data_models` |
| `res.partner` / `loyalty.mail` / `barcode.rule` *(ext)* | counters & wiring | +1 each | `loyalty_card_count`; `pos_report_print_id`; gift-card barcode type |

**Central model:** there is no new aggregate — the module *grafts* onto
`pos.order.line` (now reward-aware) and `loyalty.card` (now POS-sourced). **All 14
model entries are pure `_inherit` extensions**; 4 also add `pos.load.mixin` so the
program catalog ships into the offline client. The field mix is thin and join-y
(reward/coupon links, POS-scoping flags), reflecting a bridge, not a data owner.

## Behavior & Surfaces

- **Routes:** **none** (route_count 0). The module exposes no HTTP/JSON-RPC; it
  rides `point_of_sale`'s `/pos/ui` app and calls model RPC methods on the POS
  data layer — `pos.config.use_coupon_code`, `pos.order.validate_coupon_programs`,
  `pos.order.confirm_coupon_programs`, `loyalty.card.get_gift_card_status` /
  `get_loyalty_card_partner_by_code`.
- **Frontend (gap #3 — the headline):** **13 JS / 6 XML**, 1 OWL component
  (`ManageGiftCardPopup`) and **13 prototype patches**. The redemption **engine**
  is a ~1450-line patch on `PosOrder` (`pointsForPrograms`, `getClaimableRewards`,
  `_applyReward`, `_getRewardLineValues{Discount,Product}`, `computeFreeQuantity`
  for buy-X-get-Y) plus a ~880-line patch on `PosStore` (`updateRewards` /
  `updatePrograms` mutex-guarded re-eval, `activateCode`, `postProcessLoyalty`).
  Points are earned and reward `pos.order.line`s built **entirely offline**;
  `couponPointChanges{}` on `uiState` is the local ledger; new coupons get negative
  placeholder ids remapped to real db ids post-sync. None of this is in metadata.
- **Views:** **none of its own** (0 form/list/kanban) — it injects fields into the
  loyalty/partner back-office views; the operational UX lives in the SPA.
- **Security:** **13 access rules, 0 record rules, 0 new groups** — it reuses the
  inherited `point_of_sale.group_pos_user` / `group_pos_manager`.
- **Integrations (gap #7):** none — no outbound HTTP/SDK, no api-keys, no endpoints.

The metadata cannot show how a reward is applied. Code-reads establish the
server's three jobs around the client engine: (1) **load** —
`pos.session._load_pos_data_models` ships `loyalty.program/rule/reward/card` into
the terminal, scoped by `pos.config._get_program_ids()` (pos_ok, dates, this config
or all, pricelist, currency, usage cap), with rules pre-resolving `valid_product_ids`
and rewards rewriting `ilike→in` for the JS domain engine; (2) **validate at
checkout** — `pos.config.use_coupon_code` vets a scanned coupon/gift card and
`pos.order.validate_coupon_programs` re-checks balances at payment (returning
`removed_coupons` / live points), backstopping the optimistic client math against
concurrent use; (3) **write back** — `pos.order.confirm_coupon_programs` (sudo)
creates the awarded cards, debits/credits points, writes the `loyalty.history`
issued/used ledger, fires the creation e-mail and renders the gift-card PDF.
`loyalty.program._compute_pos_order_count` counts POS redemptions via raw SQL over
`pos_order_line.reward_id`, so usage caps & reports include the till; balances
commit **per order**, not at session close.

## Value-Configuration Classification

**Value model: Value Chain (transform), `activity_class=primary`.** `pos_loyalty`
is the promotions layer of `point_of_sale`, itself a chain **primary** activity:
the originating act is the retail **sell/checkout** producing a paid `pos.order`,
which drives the chain's outbound delivery (`stock.picking`) and revenue/cash
recognition (`account.move` at session close). Because coupons, points, discounts
and gift cards are applied *inside* that primary Sell act — discounting the cart,
adding reward lines to the live order and moving card balances at payment — it
inherits **chain / primary**, unlike the standalone `loyalty` engine (classified
*support*, since alone it confirms no transaction). Like its parent it has a strong
**network/frontend** character — nearly all logic ships as OWL screens in the
offline, IndexedDB-backed terminal with no server routes — but the value logic is
chain.

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — the POS redemption is the retail
manage-promotions / sell-to-customer flow (**3.2 manage promotions** realized at
the **3.5 point-of-sale order**). Triggered side-effects still reach **4.0 Deliver
Physical Products** (stock) and **9.0 Manage Financial Resources** (AR + cash at
session close), but those are downstream of the sale, inherited from the POS, not
this module's mission.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`) on a DB with `-i pos_loyalty`:

```python
# odoo shell
cfg = env['pos.config'].search([], limit=1)
print(cfg._get_program_ids().mapped(('name', 'program_type', 'pos_ok')))
print(env['loyalty.program'].search([('pos_ok', '=', True)])
        .mapped(('name', 'program_type', 'pos_order_count', 'total_order_count')))
print(env['loyalty.card'].search([('source_pos_order_id', '!=', False)], limit=5)
        .mapped(('code', 'points', 'program_id')))
print(env['pos.order.line'].search([('is_reward_line', '=', True)], limit=5)
        .mapped(('order_id', 'reward_id', 'coupon_id', 'points_cost')))
# launch UI: browse /pos/ui/<config_id>, add a product, open Rewards / Enter Code
```

## Open Questions (verify in code)

- The exact **offline point-earning/reward algorithm** (`pointsForPrograms` /
  `getClaimableRewards` / `_computeUnclaimedFreeProductQty`) lives in `static/src`
  JS — per-program split, round-half-up money mode and free-quantity correction are
  reverse-engineerable only from that code, not Python.
- **Concurrency:** how the optimistic client balance is reconciled
  (`validate_coupon_programs` / `confirm_coupon_programs`) when the same nominative
  card is used on two terminals or in `sale`/`website_sale` at once.
- **Negative-placeholder coupon id remapping** (`couponByLineUuidCache` /
  `rewardProductByLineUuidCache`) on order sync — re-sync edge cases and the
  `_remove_duplicate_coupon_data` guard.
- Lifecycle of POS-issued **gift cards vs eWallet expiration** (`program.date_to`
  applied on confirm; loyalty cards barred from expiration upstream).
