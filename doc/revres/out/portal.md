# portal — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py` + code-read, narrative per the `PROMPT.md` template.*

The **Customer Portal** module (`portal`, category *Hidden*, `application=False`)
is the base layer that gives external customers a self-service web surface — the
`/my/*` pages — onto the organisation's documents and conversations. It ships no
storefront and almost no persistent data of its own: it is deliberately
**route-heavy and model-light** (4 own models vs **18 routes**), a mediating
access surface that business addons (sale, account, project, …) extend by mixing
`portal.mixin` into their documents and registering `/my/<app>` sub-routes.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `web` | The web framework / controller + asset machinery the `/my` pages run on. |
| `http_routing` | Public/multilang URL routing for the frontend `/my` and `/portal` routes. |
| `mail` | Powers the **portal chatter** (re-hosted on the public surface) and share notifications. |
| `auth_signup` | The grant-access flow prepares signup tokens and sends the set-password invitation. |
| `html_editor` | Rich-text editing inside the portal chatter composer. |

**Adds on top:** signed-token document sharing, a grant/revoke **portal access
wizard**, customer account/address/security self-management, and a public
chatter.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`portal.mixin`** | Portal Mixin (abstract) | 3 | `access_url`, `access_token`, `access_warning` — mixed into business docs |
| `portal.share` | Portal Sharing (wizard) | 7 | `partner_ids→res.partner`, `resource_ref` (Reference) |
| `portal.wizard` | Grant Portal Access (wizard) | 3 | `partner_ids→res.partner`, `user_ids→portal.wizard.user` |
| `portal.wizard.user` | Portal User Config (wizard) | 8 | `partner_id→res.partner`, `user_id→res.users`, `wizard_id→portal.wizard` |

Plus **8 inherit-only extensions** — `ir.http`, `ir.qweb`, `ir.ui.view`,
`mail.message`, `mail.thread` (adds `website_message_ids`), `res.config.settings`
(`portal_allow_api_keys`), `res.partner`, `res.users.apikeys.description`. The
heart is the **abstract `portal.mixin`**: it stores no rows itself but injects
`access_url` + a signed `access_token` into whatever document mixes it in.

## Behavior & Surfaces

- **Routes:** 18 — the `/my/*` self-service set (`/my`, `/my/account`,
  `/my/addresses`, `/my/address/*`, `/my/security`, `/my/deactivate_account`) is
  `auth='user'`; the document/chatter set (`/portal/attachment/remove`,
  `/portal/chatter_init`, `/mail/chatter_fetch`) is **`auth='public'`**, gated by
  the signed `access_token` instead of a session.
- **Frontend (gap #3):** 27 JS files, **2 OWL components** (`PortalChatter`,
  `SignatureForm`), 11 registry adds (mostly `public.interactions`) and **7
  patches** of core web/mail prototypes (`Chatter`, `Composer`, `Message`,
  `Thread`, `AttachmentUploadService`, …). Dedicated `portal.assets_chatter*`
  bundles re-host the backend chatter on the public surface.
- **Integrations (gap #7):** no outbound HTTP/SDK calls; `uses_api_keys=true`
  (a config flag lets portal users mint API keys).
- **Security:** **3 access rules**, **0 record rules**, **0 own groups** — it
  reuses `base.group_portal` / `base.group_public` / `base.group_partner_manager`.
  Access control is enforced in code via signed tokens, not `ir.rule`.
- **Behavioral (code-read):** `_portal_ensure_token` lazily mints a uuid4 token
  (sudo write) and `get_portal_url`/`_get_share_url` append it to bypass
  recipient ACLs; `_document_check_access` falls back to a `consteq` token
  compare when `check_access('read')` fails; `_sign_token` HMACs `(dbname, token,
  pid)` with `database.secret` so an emailed recipient posts in chatter as an
  identified author; `portal.wizard.user.action_grant_access` creates a
  `res.users`, swaps `group_public→group_portal`, and sends the signup email.

## Value-Configuration Classification

**Primary model: Value Network (mediating), support activity.** `portal` is a
**network** value configuration — its job is to *connect* parties (external
customers ↔ the org's documents/conversations) over a shared infrastructure,
producing nothing of its own. It is the network/portal-access **enabler**, so as
an activity it is **support** (it provisions and secures the channel), not a
primary value-creating step. The mediation is concrete: `portal.mixin`'s signed
access tokens, the `portal.wizard` user-provisioning flow, and the shared portal
chatter are the "network promotion / contract management / infrastructure
operation" layers in Stabell & Fjeldstad terms.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up:

```python
# odoo shell
# inspect computed portal-user states in the access wizard:
w = env['portal.wizard'].create({})
print(w.user_ids.mapped(('email', 'is_portal', 'is_internal', 'email_state')))
# mint & read a signed share URL on any portal.mixin document:
so = env['sale.order'].search([], limit=1)
print(so.get_portal_url())          # .../my/orders/<id>?access_token=<uuid>
```
```bash
# unauthenticated /my redirects to login; with a portal session it renders:
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' "<base>/my"
# jsonrpc badge counts (needs a portal user session):  POST /my/counters
```

## Open Questions (verify in code)

- The full set of documents that mix in `portal.mixin` lives **downstream**
  (sale/account/project/…), not in `portal` itself — each overrides
  `_compute_access_url` and adds its own `/my/<app>` routes.
- No live row counts: the wizards are `TransientModel`s and `portal.mixin` is
  abstract, so the module owns no persistent table to sample.
- Exact interaction of `consteq` token check + HMAC `pid/hash` signature when a
  public visitor both views a document and posts in its chatter.
