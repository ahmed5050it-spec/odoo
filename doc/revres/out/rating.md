# rating — Reverse-Engineering Brief

> *Generated by the code-explorer + code-architect workflow: facts from
> `extract_module.py`/`extract_frontend.py` + behavioral reads of
> `models/{rating.py,rating_mixin.py,rating_parent_mixin.py,mail_thread.py,rating_data.py}`
> and `controllers/main.py`.*

The **Customer Rating** module (`rating`, category *Productivity*, v1.1,
`application=False`, `auto_install=False`) is the **customer-satisfaction
backbone** of an Odoo deployment. Like `mail.thread`, it is consumed rather than
used directly: it ships two abstract mixins — **`rating.mixin`** (a rated record)
and **`rating.parent.mixin`** (a parent that aggregates its children's ratings) —
plus one concrete, **polymorphic fact model `rating.rating`** whose
`res_model`/`res_id` reference points at *any* record in the system. It depends
only on `mail`. Primary modules graft these mixins on to instrument their own
deliverables: **project** (task/project satisfaction), **im_livechat**
(conversation rating), **website_slides** (course rating), **website_sale**
(product) — and, by the same pattern, helpdesk/event. None of those consumers is
visible from `rating`'s own metadata; the module's value is the reusable
instrument, not a document of its own.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `mail` | `rating.mixin` `_inherit`s `mail.thread`; a rating is rendered as a chatter `mail.message`, and the apply/send logic lives on the `mail.thread` extension. |

**Provides on top:** a tokenized email rating request (`rating_send_request`), a
public no-login survey (`/rate/<token>`), storage of the satisfaction fact with a
star/smiley image inside the chatter, and satisfaction analytics (avg, count, %
satisfaction, grade repartition) both per-record (`rating.mixin`) and rolled up to
a parent (`rating.parent.mixin`). Consumers inherit the mixins and override
`_rating_get_parent_field_name` / `_rating_get_operator` to wire the rating to
their own model — invisible from `rating`'s metadata.

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`rating.rating`** | Rating (the satisfaction fact) | 24 | `res_model_id→ir.model`, `parent_res_model_id→ir.model`, `partner_id→res.partner` (customer), `rated_partner_id→res.partner` (operator), `message_id→mail.message` |
| `rating.mixin` *(abstract)* | Rating Mixin (rated record) | 8 | `_inherit→mail.thread`, `rating_ids→rating.rating` (on `res_id`) |
| `rating.parent.mixin` *(abstract)* | Rating Parent Mixin (aggregate) | 5 | `rating_ids→rating.rating` (on `parent_res_id`) |

**Central record:** `rating.rating` carries a `Float` `rating` value (constrained
**0–5** by the `_rating_range` SQL check), a generic `Many2oneReference`
(`res_model`/`res_id`) to *any* rated record, a uuid `access_token` for the email
flow, a `consumed` flag (sent-but-unanswered vs filled), and an optional
`message_id` so the rating shows in the chatter. The two abstract mixins are the
reuse surface; the field mix is **reference + small-scalar** (satisfaction
measurement), not a transactional document.

## Behavior & Surfaces

- **Routes:** two **public** (`auth='public'`, `website=True`) HTTP routes —
  `/rate/<token>/<rate>` (render the survey) and `/rate/<token>/submit_feedback`
  (POST the answer). This is the only public surface.
- **Views:** form (2), list (1), kanban (2), search (1), **pivot (1) / graph (1)**
  — analytics-oriented, fitting a "slice satisfaction by rating/period" workflow.
- **Security:** **4 access rules**, **0 record rules**, **0 groups of its own**.
  `base.group_user` may read/write/create (not unlink); portal/public have **no**
  ORM access — the public flow runs as **sudo** after a token + partner check;
  `base.group_system` has full access.
- **Frontend (static):** 3 JS files, 0 OWL components, 0 registry adds, **1 patch
  (`Message.prototype`** via `core/common/message_model_patch.js`) plus a
  notification-item patch; bundles include `mail.assets_public` and
  `portal.assets_chatter`, so the rating renders **inside discuss/portal chatter**,
  not a standalone app. **Integrations:** none (no outbound HTTP, no SDK, no API
  keys).

### Behavior beyond metadata (code-read)
- **`rating.rating` is a polymorphic satisfaction fact.** The `Float` value is
  bounded 0–5 by `_rating_range` and mapped to grades **great/okay/bad** (≥4 / ≥3
  / <3) and text top/ok/ko in `rating_data`. `create()`/`write()` auto-stamp
  `rated_on` and resolve `parent_res_model`/`parent_res_id` via `_find_parent_data`
  (calling the rated record's `_rating_get_parent_field_name`). The `consumed` flag
  separates a request that was *sent* from one that was *answered*.
- **The mixin loop: `rating_send_request` → `/rate` → `rating_apply`.** On the
  `mail.thread` extension, `rating_send_request(template)` posts a `mail.template`
  (subtype `mt_note`) to the customer carrying a `/rate/<token>` link minted by
  `_rating_get_access_token` (reuses an unconsumed rating or creates one as sudo).
  `rating_apply(rate, token=…)` writes `rating`+`feedback`+`consumed=True`, and —
  if the record is a `mail.thread` — posts/updates a chatter `mail.message`
  embedding the rating image; `notify_delay_send` schedules the mail **+2 h** so
  the rater can still edit. Closed loop survey→store→chatter, none of it in
  metadata.
- **Public controller security (`controllers/main.py`).** `_get_rating_and_record`
  resolves the rating by `access_token` **as sudo** (404 if absent); a logged-in
  non-public user whose commercial partner ≠ `rating.partner_id` is rejected
  (`rating_external_page_invalid_partner`). `submit_feedback` validates `rate ∈
  {1,3,5}` (UNHAPPY/NEUTRAL/HAPPY) then calls `record_sudo.rating_apply`. The
  token+partner check *gating* the sudo escalation is the security boundary.
- **Satisfaction compute (`_compute_rating_stats` / `_compute_rating_satisfaction`
  / parent roll-up).** `rating_avg` and `rating_count` are computed together in one
  `_read_group` over **consumed** ratings with `rating>=1`;
  `rating_percentage_satisfaction = great*100/total` (−1 when none), 'great' =
  rating≥4. `rating_last_value` uses raw-SQL `array_agg` ordered by `write_date`.
  `rating.parent.mixin._compute_rating_percentage_satisfaction` rolls the same % up
  to a parent over `parent_res_id`, optionally windowed by
  `_rating_satisfaction_days`.

## Value-Configuration Classification

**Support backbone — value-model `support`, activity_class `support`.** Customer
Rating is firm-infrastructure **support**, not a primary value-creating activity.
It creates no order, delivery, or invoice; it **instruments** other modules.
Exactly like `mail.thread`, it provides reusable abstract mixins
(`rating.mixin`, `rating.parent.mixin`) plus a generic polymorphic fact
(`rating.rating`, `res_model`/`res_id` → *any* record) that **many primary
modules graft onto** — project, helpdesk, website_slides, event, im_livechat,
website_sale — to measure the satisfaction of *their* deliverables. Under Stabell
& Fjeldstad / Porter it belongs to no single primary value configuration; it is
the shared *measurement instrument* that cuts across them. The mixin design and
the polymorphic reference exist precisely so any value chain/shop/network module
can plug satisfaction measurement in without `rating` knowing about it.

## APQC PCF Hint

**6.0 Manage Customer Service** — specifically the **measure-and-evaluate-customer-
satisfaction** activity: capturing post-interaction satisfaction and rolling it
into KPIs (avg, % satisfaction, repartition). This is consistent with
`apqc_odoo_map.tsv`, which classes the surrounding chatter / customer-inquiry
handling (`mail.message` on a document) as **support** (`3.5.4.8 Handle sales
order inquiries`); rating is the satisfaction-measurement layer those service
interactions feed.

## How to Drive It

Use the **run-odoo** skill (`odoo shell`):

- `env['rating.rating'].search([], limit=5).mapped(('res_model','rating','rating_text','consumed'))`
  — recent ratings: what was rated, the value/grade, and whether answered.
- `rec = env['project.task'].search([], limit=1); rec._rating_get_access_token()`
  — mint (or reuse) a `/rate` token for a consumer record via the mixin.
- `rec.rating_apply(5, rating=env['rating.rating'].browse(<id>))`
  — apply a rating in code and watch the chatter message appear.
- `rec.mapped(('rating_avg','rating_count','rating_percentage_satisfaction'))`
  — the satisfaction KPIs computed by `rating.mixin`.
- `curl` public flow: `GET /rate/<token>/5` then `POST /rate/<token>/submit_feedback`
  (`rate=5`, `feedback=…`) — the no-login survey.
