# account_check_printing — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> code-reads of the `models/` + `wizard/` files, per `PROMPT.md`. Odoo 19.0.*

The **Check Printing Base** module (`account_check_printing`, category
*Accounting/Accounting*, `application=False`) adds a **"Checks" outbound payment
method** to the accounting engine: it lets a company pay vendor bills by printing
checks, with per-journal number sequencing and a configurable check layout. It
is **not** auto-installed and depends only on `account`. The manifest is explicit
that it "must be used as a dependency for modules that provide country-specific
check templates" — so this module is the *base* (logic + data structures), while
the actual paper layout arrives from downstream localizations.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `account` | Extends `account.payment`, `account.journal`, `account.payment.method`, `res.company`; the check is a payment document. |

**Adds on top:** a `check_printing` payment method, per-journal check `ir.sequence`
numbering, an "Amount in Words" field, check-layout / margin / stub company
settings, a **Print Checks** server action, and a **Print Pre-numbered Checks**
wizard. **No** QWeb check template ships here (see classification).

## Data Model (the ERM)

| Model (`_name`) | Kind | #fields | Key relations |
|-----------------|------|--------:|---------------|
| `account.payment` *(extension)* | check fields | 6 | `payment_method_line_id`, `journal_id` (check_number, check_amount_in_words, check_manual_sequencing) |
| `account.journal` *(extension)* | numbering cfg | 4 | `check_sequence_id→ir.sequence`, `bank_check_printing_layout` |
| `account.payment.method` *(extension)* | method reg | 0 | adds `check_printing` to `_get_payment_method_information` |
| `res.company` *(extension)* | layout cfg | 6 | `account_check_printing_layout` (= report xmlID), margins, stub flags |
| `print.prenumbered.checks` | transient wizard | 1 | captures first printed check number |

**Center of gravity:** the `account.payment` extension. The model set is config-
and flag-heavy (Boolean 8, Float 6, Char 4) — it decorates an existing document
rather than introducing a new business object. Only **1 own model** (`_name`) is
new; the other five are inherits.

## Behavior & Surfaces

- **Routes:** 0 — pure backend, no web/JSON-RPC surface.
- **Frontend:** none (0 JS, 0 OWL, 0 XML templates, no asset bundles). UI is
  server-rendered views: a `Print Check` button on the payment form and a
  `Print Checks` `ir.actions.server` bound to the `account.payment` list/kanban.
- **Views:** the facts report 0 typed views for this module; it injects fields
  into inherited `account.journal` / `account.payment` / settings forms.
- **Security:** 1 access rule (the wizard, gated to `account.group_account_user`),
  0 record rules, 0 own groups. Re-uses the accounting user group.
- **Numbering (code-read):** `account.journal.create` and the
  `create_check_sequence_on_bank_journals` **post_init_hook** auto-create a
  per-journal `no_gap` `ir.sequence`. `action_post` consumes it for manual
  sequencing; a raw-SQL `@api.constrains` enforces **check-number uniqueness per
  journal** across posted payments; numbers must be digits-only and may not
  decrease (bank rejection) or exceed int32.
- **Printing (code-read):** `print_checks` → optional `print.prenumbered.checks`
  wizard → `do_print_checks` resolves the layout, sets `is_sent=True`, and
  returns `report_action.report_action(self)`. `_check_make_stub_pages` builds the
  paid-invoice stub (9 lines/stub, VOID overflow pages).

## Value-Configuration Classification

**Support activity — Value Chain support function.** `account_check_printing`
adds nothing to the primary value chain; it operationalizes the **disbursement**
tail of accounts payable as a payment-method extension of accounting. It has no
routes, no frontend, no product/revenue logic — back-office plumbing around the
`account.payment` document. `value_model = support`, `activity_class = support`.

## APQC PCF Hint

**9.0 Manage Financial Resources** — specifically **9.5 Process payments**
(accounts payable / "pay", `9.5.x`), realized on `account.payment` with method
code `check_printing` (per `apqc_odoo_map.tsv`). It touches the AP disbursement
step only, not invoicing (9.2) or reconciliation.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i account_check_printing` database:

```python
# odoo shell
env.ref('account_check_printing.account_payment_method_check').read(['name','code','payment_type'])
env['account.journal'].search([('type','=','bank')]).mapped(('name','check_manual_sequencing','check_next_number'))
# expect ONLY [('disabled','None')] until a layout module is installed:
env['res.company']._fields['account_check_printing_layout'].selection
```
