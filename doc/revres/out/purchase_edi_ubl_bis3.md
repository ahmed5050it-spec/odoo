The **Import/Export electronic orders with UBL** module (`purchase_edi_ubl_bis3`,
category *Supply Chain/Purchase*, `application=False`, **`auto_install=True`**)
is the purchase-side twin of `account_edi_ubl_cii`: where that module serializes
invoices to UBL/CII, this one serializes a **purchase order** to and from
**Peppol BIS Ordering 3** UBL XML. It owns a single `AbstractModel` —
`purchase.edi.xml.ubl_bis3` (~30 methods, no stored fields) — that *inherits the
e-invoice builder* `account.edi.xml.ubl_bis3` and re-points its party/line/tax/
monetary node helpers at an `Order` document instead of an `Invoice`. Two small
`_inherit` extensions on `purchase.order` and `account.move` wire it into the
existing Purchase flow. ~645 Python LOC, no routes, no views of its own.

## Behavior & Surfaces (the metadata gap)

- **Outbound (`_export_order`):** `_get_purchase_order_node` assembles a UBL
  `Order` document — header with `CustomizationID
  urn:fdc:peppol.eu:poacc:trns:order:3`, `ProfileID …:bis:ordering:3`,
  `OrderTypeCode 105`, `QuotationDocumentReference`=`partner_ref` — then
  BuyerCustomerParty (own company), SellerSupplierParty (vendor), Delivery,
  PaymentTerms, `cac:OrderLine`, and `cac:AnticipatedMonetaryTotal` (the order
  analogue of the invoice's LegalMonetaryTotal). `_setup_base_lines` attaches each
  line's `product.supplierinfo` so the vendor's `product_code` / `product_name`
  land in `SellersItemIdentification` / `Item/Name`. Rendered with `dict_to_xml`
  using the `Order` template from `account_edi_ubl_cii.tools`.
- **Inbound (`_retrieve_order_vals`):** retrieves-or-creates the vendor via
  `_import_partner('SellerSupplier')` → `partner_id`, the delivery party →
  `dest_address_id`, sets `partner_ref` and `origin`, parses
  `./{*}OrderLine/{*}LineItem` via `_import_lines(document_type='order',
  tax_type='purchase')` + `_import_document_allowance_charges`, and writes them as
  `order_line` `Command.create(...)`. `_retrieve_line_vals` renames the base
  `quantity` key to `product_qty` to fit `purchase.order.line`.
- **Dispatch:** on `purchase.order`, `_get_edi_builders` appends the builder so
  the PO PDF report **embeds the Order XML inside the PDF**; `_get_import_file_type`
  sniffs the inbound `CustomizationID`, and `_get_edi_decoder` returns
  `_import_order_ubl` (priority 20). `_import_order_ubl` (in `account_edi_ubl_cii`)
  writes the vals, posts a *"Format used to import"* message, and on partial data
  schedules a `mail.mail_activity_data_todo` activity.
- **Integrity guard:** `account.move._check_move_for_group_ungroup_lines_by_tax`
  raises a `UserError` for any bill line with a `purchase_order_id`, so PO-backed
  vendor-bill lines can't be (un)grouped and the matching/valuation link stays
  intact.
- **Routes / Views / Security:** none — 0 routes, 0 view records, 0 access rules.
- **Frontend (static):** none — no JS, OWL, registry adds or asset bundles
  (gap #3 empty). **Integrations (gap #7):** no outbound HTTP/SDK/api-key usage;
  it only *builds and parses* XML — Peppol network transport is out of scope.

## Fit-to-Standard

**Out-of-box:** export a PO as Peppol BIS Ordering 3 UBL Order; embed the XML in
the PO PDF; detect inbound order format from `CustomizationID` and import into
`purchase.order`; retrieve-or-create vendor & delivery party; carry vendor
`product_code`/`product_name` into the UBL Item; reuse the shared builder's
EN16931/PINT tax & monetary computation. **Typical gaps:** actual Peppol Access
Point transmission (separate module), Order-Response / Order-Change profiles,
country-specific CIUS/extensions on the order, bespoke product/UoM/tax mappings.
**Drive (live):** in `odoo shell`, `env['purchase.edi.xml.ubl_bis3']._export_order(po)`
and read the BIS Order XML head, or inspect `_get_purchase_order_node(...)`.
