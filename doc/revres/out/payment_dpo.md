# payment_dpo — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Payment Provider: DPO** module (`payment_dpo`, category
*Accounting/Payment Providers*, `application=False`) integrates **DPO Group**
(Direct Pay Online) — an African payment processor covering Kenya, Nigeria,
South Africa, Ghana, Uganda, and other markets — into the Odoo `payment` engine
via a **two-stage XML redirect flow**: the server creates a transaction token via
the DPO API, redirects the browser to the DPO hosted payment page, and then
re-validates the outcome server-side on return before updating the Odoo
transaction state. There is no client-side JavaScript, no webhook/IPN, and no
Python SDK; all API communication uses stdlib `xml.etree.ElementTree` over the
parent engine's `_send_api_request`.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `payment` | Inherits the full provider / transaction engine and `_send_api_request`; overrides four hooks to plug in the DPO XML API adapter. |

`payment_dpo` has **no own models** — `_inherit` only. It extends two models
(`payment.provider`, `payment.transaction`) and adds one controller.

## Data Model

| Inherited model | New fields | Key behavior added |
|-----------------|-----------|-------------------|
| `payment.provider` | `code` (selection_add `'dpo'`), `dpo_service_ref` (Char), `dpo_company_token` (Char, `groups=base.group_system`) | API URL builder, XML headers, XML response parser. |
| `payment.transaction` | *(none)* | `_get_specific_rendering_values`, `_dpo_create_token`, `_extract_reference`, `_extract_amount_data`, `_apply_updates`. |

`dpo_company_token` is the DPO account secret — it travels in the XML request
body (never in HTTP headers or the URL) and is restricted to `base.group_system`.
`dpo_service_ref` is the merchant's DPO Service ID, required for every token
creation.

## Behavior (code-read)

### 1. XML API adapter: one endpoint, XML body, stdlib ET parsing

`payment_provider.py` overrides three parent engine hooks:

- `_build_request_url` — ignores the `endpoint` argument and always returns
  `'https://secure.3gdirectpay.com/API/v6/'` (DPO has a single API URL for all
  XML operations).
- `_build_request_headers` — returns `{'Content-Type': 'application/xml; charset=utf-8'}`.
- `_parse_response_content` — decodes `response.content`, parses it with
  `ET.fromstring()`, and flattens all child elements into a plain
  `{element.tag: element.text}` dict.

The parent engine's `_send_api_request` then transparently POSTs XML and
returns a Python dict — all callers in `payment_transaction.py` work with keys
like `'TransToken'`, `'Result'`, `'TransID'`, `'ResultExplanation'` directly.

### 2. `_dpo_create_token` — server-side createToken XML call

`_get_specific_rendering_values` calls `_dpo_create_token()`, which builds a
hand-crafted XML payload via Python f-strings:

```xml
<API3G>
  <CompanyToken>{dpo_company_token}</CompanyToken>
  <Request>createToken</Request>
  <Transaction>
    <PaymentAmount>{self.amount}</PaymentAmount>
    <PaymentCurrency>{self.currency_id.name}</PaymentCurrency>
    <CompanyRef>{self.reference}</CompanyRef>
    <RedirectURL>/payment/dpo/return</RedirectURL>
    <BackURL>/payment/dpo/return</BackURL>
    <customerEmail>{self.partner_email}</customerEmail>
    <customerFirstName>…</customerFirstName>
    <customerLastName>…</customerLastName>
    <customerCity>…</customerCity>
    <customerCountry>{country.code}</customerCountry>
    <customerZip>…</customerZip>
  </Transaction>
  <Services>
    <Service>
      <ServiceType>{dpo_service_ref}</ServiceType>
      <ServiceDescription>{reference}</ServiceDescription>
      <ServiceDate>{create_date %Y/%m/%d %H:%M}</ServiceDate>
    </Service>
  </Services>
</API3G>
```

On success it extracts `transaction_data.get('TransToken')` and returns
`{'api_url': f'https://secure.3gdirectpay.com/payv2.php?ID={TransToken}'}`.
The QWeb redirect template (`payment_dpo_templates.xml`) auto-submits a GET to
that URL, redirecting the browser to the DPO hosted payment page. On
`ValidationError` from the API, `_set_error` is called and `None` is returned.

### 3. Return route: verify-before-process pattern

`DPOController.dpo_return_from_checkout` handles the GET from DPO after the
customer completes (or abandons) payment. The return URL carries `CompanyRef`
(the Odoo reference) and `TransID` (DPO transaction ID) as query parameters.

`_verify_and_process`:

1. Looks up the transaction via `_search_by_reference('dpo', data)`, which calls
   `_extract_reference` → `data.get('CompanyRef')`.
2. POSTs a **second XML request** to the API with `<Request>verifyToken</Request>`
   and `<TransactionToken>{data.get('TransID')}</TransactionToken>`.
3. Merges the XML response dict into `data` via `data.update(verified_data)`.
4. Calls `tx_sudo._process('dpo', data)`.

The return URL query string is **never trusted** for the payment outcome — the
server always re-validates against the DPO API. This prevents replay or
tampered-redirect attacks. If `_send_api_request` raises `ValidationError` the
error is logged and `_process` is not called, leaving the transaction in its
current state.

### 4. `_apply_updates` — DPO Result code mapping

`_apply_updates` sets `self.provider_reference = payment_data.get('TransID')`
then dispatches on `payment_data.get('Result')` against `const.PAYMENT_STATUS_MAPPING`:

| Result codes | Odoo state |
|-------------|-----------|
| `'003'`, `'007'` | `_set_pending()` |
| `'001'`, `'005'` (authorized) or `'000'`, `'002'` (done) | `_set_done()` |
| `'900'`–`'904'`, `'950'` | `_set_canceled()` |
| `'801'`–`'804'` | `_set_error(code + ResultExplanation)` |
| unknown | `_set_error('Unknown status code')` + warning log |

Both authorized codes (`001`, `005`) and done codes (`000`, `002`) collapse to
`_set_done()` — there is no two-step authorize-then-capture. `_extract_amount_data`
returns `{'amount': float(TransactionAmount), 'currency_code': TransactionCurrency}`
for the engine's cross-check. The full code table is documented in `const.py`
with a pointer to the DPO API reference.

## Value-Configuration Classification

**Value model: network** (Stabell & Fjeldstad mediating-technology). `payment_dpo`
connects payers in African markets to the merchant via the DPO Group payment
network: it creates a token (network provisioning), redirects to the hosted page
(network service delivery), and verifies the outcome (network settlement). It
inherits the parent `payment` engine's network position exactly. **Activity class:
support** (APQC 9.0 Manage Financial Resources — 9.5 process payments / collect
cash; `application=False`).
