# account_edi — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Import/Export Invoices From XML/PDF** module (`account_edi`, category
*Accounting/Accounting*, `application=False`) is the **Electronic Data
Interchange (EDI) framework** for invoices. It generates, sends, receives and
tracks structured e-invoice documents for posted accounting moves through
*pluggable formats*. It depends only on `account` and ships **no concrete
format itself** — it is the plumbing that country localization modules (`l10n_*`)
subclass to implement UBL, Factur-X, FatturaPA, and government-clearance flows.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `account` | Operates on `account.move` (invoices/bills) and `account.journal`; extends posting, cancel and send flows. |

**Adds on top:** a per-(move, format) electronic-document lifecycle, an abstract
`account.edi.format` strategy object, synchronous + asynchronous (cron/web-service)
transmission, EDI cancellation workflow, and XML attachment onto invoices and mail.

## Behaviour Beyond Metadata (code-reads)

1. **`account.move._post` (override)** — on posting, for every format on the
   journal whose `_get_move_applicability(move)` is truthy, creates/resets an
   `account.edi.document` in `to_send` (after `_check_move_configuration`, which
   raises `UserError` on bad data), runs synchronous formats immediately, and
   triggers the `ir_cron_edi_network` cron for web-service formats.
2. **`account.edi.format` pluggable hooks** — the model is a near-empty abstract
   base; `_get_move_applicability` (returns `post`/`cancel`/`*_batching`/
   `edi_content` callables), `_needs_web_services`, `_is_compatible_with_journal`,
   `_check_move_configuration`, `_prepare_invoice_report` are all *TO OVERRIDE*.
   The actual move→XML generation and ack parsing live in `l10n_*` subclasses.
3. **`_process_documents_web_services` + `_cron_process_documents_web_services`** —
   state machine `to_send→sent` (post) and `to_cancel→cancelled` (cancel),
   `blocking_level` gating retries. `_prepare_jobs` batches by
   (format, state, company, key); `_process_job` calls the format callable,
   attaches the returned EDI XML to the move, then flips state. The cron locks
   rows, commits between jobs, and re-triggers while jobs remain.
4. **Cancel/draft gating** — once an EDI is `sent` via web service, `button_draft`
   raises (user must *Request EDI Cancellation*); `button_cancel` flips sent docs
   to `to_cancel`; `_is_ready_to_be_sent` blocks the customer email until the EDI
   leaves `to_send`. Legal-immutability coupling not expressible in metadata.
5. **Frontend (static)** — no OWL/JS: 0 JS files, 0 components, 0 registry adds.
   UI surfaces only through inherited `account.move` views.

## IT Architecture

- **Application:** `account_edi` — EDI framework component extending `account`.
- **Software services:** none (no HTTP/JSON routes).
- **Data objects:** `account.edi.document`, `account.edi.format`, plus inherited
  `account.journal`, `account.move`, `account.move.send`, `ir.actions.report`,
  `ir.attachment`.
- **Information flows:** `_post` → spawns documents → cron/web-service transmits →
  XML attached to move; cancel flow can draft+cancel the underlying move.
- **Integrations:** none in the base framework (0 HTTP call sites, no SDKs, no
  API keys) — connectivity is localization-specific.

## Fit-to-Standard & Open Questions

**Standard out-of-box:** per-(move,format) lifecycle; auto document creation on
posting; sync + async transmission with batching; pluggable `account.edi.format`
strategy; XML attached to invoice and Send & Print mail; error/retry/cancel flow.

**Common gaps:** no concrete format ships in the base (needs an `l10n_*`); no
inbound parsing pipeline here; clearance-platform connectivity is localization-
specific; no dedicated frontend/dashboard.

**Open questions:** which `l10n_*` subclass the format and their endpoints; real
batching-key semantics; inbound vendor-bill parsing; relation to the newer
`account.move.send` / `account_edi_ubl_cii` stack.
