# sale_loyalty — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> `extract_frontend.py`, behavior from reading `models/` + `wizard/`, narrative
> per `PROMPT.md`. Odoo 19.0.*

The **Sale Loyalty** module (`sale_loyalty`, category *Sales/Sales*,
`application=False`, **`auto_install=True`**) is **THE BRIDGE** that applies the
loyalty engine to back-office sales orders. It depends only on `sale` and
`loyalty`, and is auto-installed whenever both are present. It defines almost no
business entity of its own — instead it grafts coupons, promo codes, promotions,
gift cards and eWallets onto `sale.order` / `sale.order.line`: it resolves a
typed code to a program or card, generates reward/discount order lines, and
debits/credits `loyalty.card` points (writing a `loyalty.history` ledger) when
the order is confirmed. The program/rule/reward definitions live in `loyalty`;
this module is the **sale-side consumer** that turns them into money off a real
order.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `sale` | The quotation/sales-order app whose `sale.order` / `sale.order.line` it extends, prices and confirms. |
| `loyalty` | Brings `loyalty.program` / `loyalty.rule` / `loyalty.reward` / `loyalty.card` — the program engine this module applies. |

**Adds on top:** an Apply-Coupon wizard and a Reward-Selection wizard, a per-order
coupon-points ledger (`sale.order.coupon.points`), reward/discount order lines,
point settlement + `loyalty.history` writes at confirmation, follow-on coupon
issuance with email, and a `loyalty_data` summary widget on the order form.

## Data Model (the ERM)

| Model (`_name`) | Role | #fields | Key relations |
|-----------------|------|--------:|---------------|
| **`sale.order.coupon.points`** | per-order × coupon points ledger | 3 | `order_id→sale.order`, `coupon_id→loyalty.card` (UNIQUE pair) |
| `sale.loyalty.coupon.wizard` | apply a promo/coupon code | 2 | `order_id→sale.order` |
| `sale.loyalty.reward.wizard` | pick & claim a reward | 6 | `order_id→sale.order`, `selected_reward_id→loyalty.reward`, `selected_product_id→product.product` |
| `sale.order` *(ext)* | order carrying promotions | +6 | `applied_coupon_ids→loyalty.card`, `code_enabled_rule_ids→loyalty.rule`, `coupon_point_ids` |
| `sale.order.line` *(ext)* | the reward / discount / free-product line | +5 | `reward_id→loyalty.reward`, `coupon_id→loyalty.card` (`is_reward_line`, `points_cost`) |
| `loyalty.card` *(ext)* | issued card w/ source order | +2 | `order_id→sale.order` |
| `loyalty.program` *(ext)* | program w/ SO rollup | +2 | `order_count`, `sale_ok` |
| `loyalty.reward` *(ext)* | reward w/ SO-tuned product | 0 | discount-product `invoice_policy='order'`, archive-on-use |
| `loyalty.history` *(ext)* | history row | 0 | SO portal URL resolver |
| `account.move.line` *(ext)* | invoice line | 0 | flags discount-reward lines as discount lines |

**Center of gravity:** the `sale.order` ↔ `loyalty.card` pair mediated by
`sale.order.coupon.points` and the reward `sale.order.line`. Only three models
are standalone (two transient wizards + the points ledger); the rest are
`_inherit`-only extensions, so the module is mostly glue between two existing
stacks — field mix is `Many2one`-heavy, matching a bridge subsystem.

## Behavior & Surfaces

- **Routes:** **none** — interaction is backend ORM + the two wizards + the
  order form (no storefront; that is `website_sale_loyalty`).
- **Views:** the facts report 0 own view *types*; the module ships SO form
  extensions and the coupon/reward wizard views.
- **Security:** 17 access rules, **0 record rules**, 0 groups — multi-company
  scoping is inherited from `sale` / `loyalty`.
- **Behavior beyond metadata (code-read):**
  - `_try_apply_code` resolves a typed code to a `loyalty.rule` (`mode='with_code'`)
    or, failing that, a `loyalty.card`; rejects re-use and `loyalty`/`ewallet`
    types, and **locks the `loyalty_program` row** (`SELECT … FOR UPDATE NOWAIT`)
    to serialize concurrent applications.
  - `_update_programs_and_rewards` auto-loads the partner's eWallet/loyalty
    cards, evaluates automatic programs, then **regenerates reward order lines** —
    `_get_reward_values_discount` (one line per tax bucket on the reward's
    `discount_line_product_id`, capped at `discount_max_amount`/order total) or
    `_get_reward_values_product` (a free-product line covered by points).
  - `action_confirm` guards against negative points, writes `loyalty.history`
    (issued/used), and **debits/credits `loyalty.card.points`** so balances move
    only at confirmation; `_action_cancel` reverses it; `_send_reward_coupon_mail`
    emails future-order coupons.
  - the **reward wizard** (`action_apply`) claims `_get_claimable_rewards` via
    `_apply_program_reward`, re-runs the engine and prunes unused coupons.
- **Frontend (static):** 1 JS, 1 XML, **1 OWL component** `LoyaltyDataField`
  (field widget `loyalty_data_field`, `web.assets_backend`) rendering the
  read-only `loyalty_data` points/rewards summary on the order form; 0 patches.
- **Integration (gap #7):** none — `http_call_sites=0`, no SDK/API keys, no
  endpoints.

## Value-Configuration Classification

**Primary model: Value Chain, promotions layer — THE BRIDGE.** `sale_loyalty` is
classified **chain**: it is the discounts/rewards leg of the Quote-to-Cash sales
value chain, operating directly on the confirmed `sale.order` — generating
reward/discount lines that change what the customer pays and settling loyalty
points at confirmation. Unlike the `loyalty` engine itself (classified
**support**, a cross-cutting program/rule/reward *definition* store), this module
participates in the **primary** sell motion and is auto-installed precisely to
graft that pricing behavior onto `sale`'s chain. Hence **chain / primary**.
*(Support was considered, by analogy to the parent `loyalty` record, but rejected:
loyalty merely defines programs and stores no orders, whereas sale_loyalty acts
on a real order's price and points — primary chain activity at order time.)*

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`). With the server up and an
`-i sale_loyalty` database:

- `so = env['sale.order'].search([], limit=1); w = env['sale.loyalty.coupon.wizard'].create({'order_id': so.id, 'coupon_code': 'PROMO'}); w.action_apply()`
- `so._update_programs_and_rewards(); so.order_line.filtered('is_reward_line').read(['name','reward_id','coupon_id','points_cost','price_unit'])`
- `so.action_confirm(); env['loyalty.history'].search([('order_id','=',so.id),('order_model','=','sale.order')]).read(['card_id','issued','used'])`
- `env['loyalty.program'].search([('program_type','=','promotion')]).read(['name','order_count','sale_ok'])`

## Open Questions

- Precedence when several automatic programs and a coded program compete for the
  same lines (ordering inside `_update_programs_and_rewards` STEP 2).
- Concurrency behavior of the `FOR UPDATE NOWAIT` program lock under high-volume
  promo-code application (retry storms).
- Lifecycle of reward `sale.order.line` rows across order copy/amendment after
  confirmation (`copy()` drops them; partial re-confirmation paths).
