# payment_stripe — Reverse-Engineering Brief

> *Generated by the revres workflow: facts from `extract_module.py` +
> behavioral code-reads + the `PROMPT.md` template.*

The **Payment Provider: Stripe** module (`payment_stripe`, category
*Accounting/Payment Providers*, `application=False`) is the **Stripe acquirer
adapter** for Odoo's payment engine. It depends on exactly one module —
**`payment`** — and exists only to make Stripe a usable, live payment provider:
it teaches `payment.provider`/`payment.transaction`/`payment.token` how to talk
to Stripe over HTTP, how to confirm charges in the browser with Stripe.js, and
how to ingest Stripe's signed webhooks. It owns **no models and no views** — three
`_inherit` extensions graft Stripe credentials, intent/refund flows, and saved-
card fields onto the engine. This is a textbook **metadata gap #7**: a real
external integration whose endpoints, API-key auth, and webhook trust live in code,
not in field metadata.

## Role & Dependencies

| Depends on | Why |
|------------|-----|
| `payment` | The provider/transaction/token engine + the centralized outbound HTTP helper `payment.provider._send_api_request` and the guarded transaction state machine this module plugs Stripe into. |

**Adds on top:** Stripe credentials (publishable / secret / webhook-signing keys),
the direct **PaymentIntent** card flow with client-side Stripe.js confirmation,
**tokenization** (Stripe Customer + PaymentMethod, with eMandate support), manual
capture / void / full + partial refunds, **express checkout** (Apple Pay / Google
Pay), and **Stripe Connect** self-onboarding with one-click webhook registration.

## Data Model (the ERM)

| Model (`_name`) | Kind | #fields | Key relations |
|-----------------|------|--------:|---------------|
| `payment.provider` | _inherit | +4 | `code` (+'stripe'), `stripe_publishable_key`, `stripe_secret_key` (group_system), `stripe_webhook_secret` (group_system) |
| `payment.transaction` | _inherit | +0 | 14 methods overriding request/notification hooks; maps a tx ↔ a Stripe PaymentIntent / SetupIntent / Refund (`provider_reference` = Stripe object id) |
| `payment.token` | _inherit | +2 | `stripe_payment_method` (PaymentMethod id), `stripe_mandate` (eMandate); `provider_ref` = Stripe Customer id |

**No own model, no own views** — `xml_loc≈134` is view *inheritance* (Stripe keys +
*Generate Webhook* / *Verify Apple Pay domain* buttons on the provider form), QWeb
inline-form + SDK-loader templates, and provider seed data. The cross-system keys
(`provider_reference`, `provider_ref`, `stripe_payment_method`) are the real
center of gravity — they bind Odoo records to Stripe objects.

## Behavior & Surfaces

- **Routes:** 5, all HTTP. `/payment/stripe/return` (public redirect-return),
  `/payment/stripe/webhook` (public, **csrf=False**, signed async notifications),
  `/.well-known/apple-developer-merchantid-domain-association` (Apple Pay proof),
  and two `auth=user` Connect-onboarding routes
  (`/payment/stripe/onboarding/return|refresh`).
- **Views:** **0 own views** — all UX is inheritance into the provider form +
  payment QWeb templates; `payment_templates.xml` loads the Stripe.js `<script>`
  only on pages with a payment form.
- **Frontend (static):** 3 JS files, **no OWL**, 0 registry adds — it **patches**
  `PaymentForm.prototype` (Stripe.js Payment Element) and
  `ExpressCheckout.prototype` (Apple/Google Pay button); assets in
  `web.assets_frontend`.
- **Security:** **0 own ACL/record rules/groups** — leans on `payment`; secret &
  webhook keys are restricted to `base.group_system`.

What metadata cannot show, established by reading the code:

- **`_stripe_create_intent` / `_send_payment_request`** — outbound **POST to
  `https://api.stripe.com/v1/`** (`payment_intents` or `setup_intents`),
  authenticated `AUTHORIZATION: Bearer <stripe_secret_key>` + `Stripe-Version:
  2019-05-16`, amount in minor units, idempotency key, `expand[]=payment_method`.
  The browser then confirms the intent via Stripe.js using the `client_secret`.
  (Per README the legacy **Checkout-Session redirect** flow was replaced by the
  **deferred Payment Intents API** in v16.4 — this module creates **PaymentIntents,
  not Checkout Sessions**.)
- **`StripeController.stripe_webhook`** — `/payment/stripe/webhook` parses the
  event, finds the tx by `_search_by_reference`, then **`_verify_signature`** runs
  Stripe's manual scheme: read `Stripe-Signature`, reject events >10 min old or
  missing `v1`, **HMAC-SHA256** `"<ts>.<raw-body>"` with `stripe_webhook_secret`,
  **constant-time compare** (`hmac.compare_digest`) — mismatch → HTTP **403
  Forbidden**. On success it enriches the event (fetch PaymentMethod; paginate
  `refunds` for `charge.refunded`) and `_process('stripe', …)` drives the state
  machine. `/payment/stripe/return` instead **GETs** the intent to confirm state.
- **Stripe Connect onboarding** — `action_start_onboarding` gates on
  `SUPPORTED_COUNTRIES`, then POSTs `accounts` / `account_links` through Odoo's
  **proxy `https://stripe.api.odoo.com/api/stripe/`**; the Stripe-hosted URL is an
  `act_url` redirect; merchant returns to `…/onboarding/return|refresh`. Two
  `@api.constrains` forbid Test-mode on a connected account and Enabled-while-
  onboarding. `action_stripe_create_webhook` auto-registers the webhook and stores
  the signing secret.
- **Tokenization** — on a successful intent with `tx.tokenize`, `_extract_token_values`
  vaults a `payment.token`: `provider_ref`=Stripe **Customer** id (created up-front
  by `_stripe_create_customer`), `stripe_payment_method`=**PaymentMethod** id,
  last4, + `stripe_mandate` for Indian eMandates. Off-session charges POST a
  PaymentIntent with `confirm=True, off_session=True, customer, payment_method,
  mandate`; pre-SCA tokens are lazily migrated.

## Value-Configuration Classification

**Value model: Network (mediating-technology acquirer integration).** `payment_stripe`
interconnects two parties who would not otherwise transact directly — the
**cardholder/payer** and the **merchant** — by linking the merchant into Stripe's
card network. It shows all three mediating-technology activities: **network
promotion & contract management** (Connect onboarding, webhook & key management,
Apple Pay domain verification), **service provisioning** (creating & confirming the
PaymentIntent/SetupIntent per transaction), and **infrastructure operation** (the
`api.stripe.com` server link, the Stripe.js client channel, the signed-webhook
settlement loop). It is **not** transformation (chain) or bespoke problem-solving
(shop). It inherits the parent `payment` engine's classification — the engine is
the generic mediator, this module its **Stripe realization (gap #7)**. Classified
**network / support** (mirrors `payment.metamodel.json`; contrasts with
`account_payment` = support/support, whose own logic is ledger record-keeping).

## How to Drive It

Use the `run-odoo` skill. With a `-i payment_stripe` database and a Stripe provider
in test state:

```python
# odoo shell — provider + feature flags
p = env['payment.provider'].search([('code','=','stripe')], limit=1)
print(p.name, p.state, p.support_express_checkout, p.support_manual_capture, p.support_refund, p.support_tokenization)
# Stripe-specific override surface + a transaction <-> Stripe object link
print([m for m in dir(env['payment.transaction']) if m.startswith('_stripe_')])
tx = env['payment.transaction'].search([('provider_code','=','stripe')], limit=1)
print(tx.reference, tx.state, tx.provider_reference)  # provider_reference == Stripe intent id
```

```bash
# webhook signature gate: a missing/invalid Stripe-Signature -> HTTP 403 Forbidden
curl -X POST https://<host>/payment/stripe/webhook -H 'Content-Type: application/json' -d '{}'
# Stripe test card: 4111111111111111, any future expiry, any CVC (README)
```
