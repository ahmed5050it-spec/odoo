# sale_stock — Reverse-Engineering Brief

> *Generated by the revres code-explorer + code-architect workflow: structural

> from `addons/sale_stock/models/`. Odoo 19.0.*

The **Sales and Warehouse Management** module (`sale_stock`, category
*Sales/Sales*, `application=False`, **`auto_install=True`**) is the bridge that
"makes the link between the sales and warehouses management applications" (its
own manifest). It declares **no model of its own** — 24 `_inherit`-only classes,
~8.9k Python LOC — and exists solely to wire `sale.*` to `stock.*`. It is THE
BRIDGE that turns the chain's abstract `sale.order.action_confirm → stock.picking`
side-effect (documented across the catalog) into concrete procurement code.

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `sale` | Owns the quotation/order document this module extends with delivery fields. |
| `stock_account` | Pulls in `stock` (pickings/moves/rules) + valuation so delivery feeds accounting. |

`auto_install=True` means it activates automatically whenever both `sale` and
`stock_account` are present — the hallmark of a glue module, not a standalone
capability.

directly for speed).

## Behavior & Surfaces (the metadata gap)

- **Forward (confirm → delivery):** `sale.order._action_confirm` calls
  `order_line._action_launch_stock_rule()` **before** `super()`, which assembles
  `Procurement` tuples per `consu` line and runs `stock.rule.run(procurements)`.
  The pull rule creates `stock.move` → `stock.picking`, then
  `pickings_to_confirm.action_confirm()` triggers the scheduler. Re-running on
  `create`/`write` of confirmed lines keeps deliveries in sync with ordered qty.
- **Backward (delivery → progress):** `delivery_status` is computed from
  `picking_ids.state` (pending/started/partial/full); `qty_delivered_method`
  flips to `'stock_move'` so `qty_delivered` sums done outgoing/incoming move
  quantities; `effective_date` = first done customer picking. This back-flow
  gates `invoice_status` for delivery-policy products.
- **Routes:** 2, both `auth='public'` HTTP — customer-portal delivery-slip and
  return PDFs (`/my/picking/pdf/<id>`, `/my/picking/return/pdf/<id>`).
- **Views:** no new view *records* — extends `sale`/`stock` forms in place
  (~870 XML LOC). **Security:** 16 access rules, 2 record rules, 0 groups.
- **Frontend (static):** one backend OWL widget — `QtyAtDateWidget` /
  `QtyAtDatePopover`, registered `view_widgets:qty_at_date_widget` — the
  green/red ATP popover on order lines fed by the computed forecast fields; also
  patches `ProductCatalogKanbanRecord` and `StockValuationReport` prototypes. No
  outbound HTTP/SDK integrations (gap #7 empty; carrier connectors out of scope).

## Value-Configuration Classification

**Value model: `chain` · activity_class: `primary` · APQC: 4.0 Deliver Physical
Products (line-level 3.5.4.4 Determine fulfillment process).** This is a pure
value-chain bridge realizing **outbound logistics**: confirmed demand is
transformed into a physical delivery, and fulfillment progress flows back to
gate invoicing. It is classified *primary* because order fulfillment / shipping
is a core line activity, even though the module owns no standalone business
object — it only inherits `sale.*` and `stock.*` to make the
`action_confirm → picking` chain concrete.

## Fit-to-Standard

**Out-of-box:** auto delivery-order creation on confirm; MTS/MTO/drop-ship
routes; shipping policy; delivery status & dates; qty_delivered from moves;
ATP widget; incoterms propagated to invoice; lot traceability; delivery-slip
PDF. **Typical gaps:** custom procurement rules, carrier/shipping connectors
(separate `delivery` modules), bespoke ATP/reservation logic, industry return
flows. **Drive (live):** confirm a draft order in `odoo shell` and read
`so.picking_ids.mapped(('name','state'))` + `so.delivery_status`.
