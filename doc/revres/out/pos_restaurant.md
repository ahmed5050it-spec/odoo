# pos_restaurant — Reverse-Engineering Brief

> *Generated by the revres workflow (code-explorer + code-architect): facts from
> `extract_module.py` / `extract_frontend.py` + code-read of the models. Odoo 19.0.*

The **Restaurant** module (`pos_restaurant`, category *Sales/Point of Sale*,
`application=True`) adds sit-down/restaurant features on top of the Point of
Sale till — *"Bill Printing, Bill Splitting, Kitchen Order Printing."* It is
**not** auto-installed and depends on a single module, **`point_of_sale`**: it is
a pure extension that activates only when a `pos.config` has
`module_pos_restaurant=True`. Its weight is in the frontend — ~31 JS / 21 XML
files of OWL bolted into the offline POS terminal app — over a slim backend of
**3 new models** plus 7 `_inherit` extensions (1754 Python / 2744 XML LOC).

## Role & Dependencies

| Depends on | Why (inferred) |
|------------|----------------|
| `point_of_sale` | The whole base — terminal SPA, `pos.order`/`pos.session`/`pos.config`, offline sync, hardware/printing. `pos_restaurant` only adds restaurant screens + floor/table/course models on top. |

**Adds on top:** a graphical floor plan (floors + draggable tables),
table-bound orders with guest counts, meal **coursing & kitchen firing**, **bill
splitting**, **proforma bill printing** before payment, table **transfer/merge**,
and **tips** (including adjust-after-payment).

## Data Model (the ERM)

| Model (`_name`) | Description | #fields | Key relations |
|-----------------|-------------|--------:|---------------|
| **`restaurant.floor`** | Restaurant Floor | 8 | `pos_config_ids→pos.config` (m2m), `table_ids→restaurant.table` |
| **`restaurant.table`** | Restaurant Table | 11 | `floor_id→restaurant.floor`, `parent_id→restaurant.table` (grouping) |
| **`restaurant.order.course`** | POS Restaurant Order Course | 6 | `order_id→pos.order`, `line_ids→pos.order.line` |
| `pos.order` *(extension)* | +table fields | +3 | `table_id→restaurant.table`, `course_ids→restaurant.order.course`, `customer_count` |
| `pos.order.line` *(extension)* | +course link | +1 | `course_id→restaurant.order.course` |
| `pos.config` *(extension)* | +restaurant flags | +5 | `floor_ids→restaurant.floor`, `iface_splitbill`, `iface_printbill`, `set_tip_after_payment`, `default_screen` |

**Central model:** there isn't a new aggregate — the module *grafts* onto
`pos.order` (now table- and course-aware). The three new models are all
`_inherit=['pos.load.mixin']` (the contract for shipping rows into the offline
client). **7 of the 10 model entries are pure `_inherit` extensions** with no
`_name` (pos.config/order/order.line/payment/preset/session, res.config.settings).
The field mix is **geometry- and flag-heavy**: `restaurant.table` is mostly Floats
(position_h/v, width, height) that exist only to draw the floor plan; the config
extension is all Booleans/Selection feature switches.

## Behavior & Surfaces

- **Routes:** **none** (route_count 0). The module exposes no HTTP/JSON-RPC of
  its own; it rides `point_of_sale`'s `/pos/ui` app and the generic
  `pos.order.sync_from_ui` / `pos.session` data-load RPCs. Restaurant models are
  injected into the terminal only when `module_pos_restaurant` is true
  (`pos.session._load_pos_data_models`).
- **Frontend (gap #3 — the headline):** **31 JS / 21 XML files**, 7 OWL
  components and **3 new `pos_pages` screens** in `point_of_sale._assets_pos` —
  **FloorScreen** (drag-and-drop floor plan via a `makeDraggableHook`/
  `useDraggable`; table-merge detected by on-screen rectangle intersection),
  **SplitBillScreen** (split an order's lines into separate bills), **TipScreen**,
  plus an `OrderCourse` component — and **~25 prototype patches** onto base POS
  screens/models (`ProductScreen`, `ControlButtons`, `ActionpadWidget`,
  `TicketScreen`, `OrderSummary`, `PosStore`/`PosOrder`/`PosOrderline`) adding
  table transfer, guest count, course actions and proforma printing. None of this
  is reverse-engineerable from Python metadata.
- **Views:** thin back-office — list (2) / form (2) / kanban (1) / search (1) for
  configuring floors, tables and courses; the operational UX lives in the SPA.
- **Security:** **5 access rules, 0 record rules, 0 new groups** — it reuses the
  inherited `point_of_sale.group_pos_user` (read floors/tables; full CRUD on
  courses) and `group_pos_manager` (full CRUD).
- **Integrations (gap #7):** no outbound HTTP/SDK, no api-keys; the only endpoint
  is the marketing URL in `__manifest__.py`.

## Value-Configuration Classification

**Primary model: Value Chain (transform), `activity_class=primary`.**
`pos_restaurant` is a thin sell-side extension of `point_of_sale`, itself a chain
**primary** activity: the originating act is the in-restaurant **sell/checkout**
producing a paid `pos.order`, which drives the chain's outbound delivery
(`stock.picking`) and revenue/cash recognition (`account.move` at session close).
It inherits **chain**. Its own value-add is **service orchestration** (floor plan,
table assignment, coursing, split bill, tips), giving it a pronounced **shop**
(dining-encounter) overtone, and — like its parent — a strong **network/frontend**
character: nearly all logic ships as OWL screens patched into the offline,
IndexedDB-backed terminal, with **no server routes of its own**. The value logic
remains chain.

## APQC PCF Hint

**3.0 Market and Sell Products and Services** — the dine-in order is the 3.5
"manage sales orders" family realized as a table-served till (mirroring `sale`
and `point_of_sale`). Triggered side-effects still reach **4.0 Deliver Physical
Products** (stock) and **9.0 Manage Financial Resources** (AR + cash at session
close), but those are downstream of the sale, not this module's mission.

## How to Drive It

Use the `run-odoo` skill (`.claude/skills/run-odoo/`) on a database with
`-i pos_restaurant`:

```python
# odoo shell
print(env['pos.config'].search([('module_pos_restaurant','=',True)])
        .mapped(('name','iface_splitbill','iface_printbill','default_screen')))
print(env['restaurant.floor'].search([]).mapped(('name','pos_config_ids','table_ids')))
print(env['restaurant.table'].search([], limit=10)
        .mapped(('table_number','floor_id','seats','shape')))
print(env['pos.order'].search([('table_id','!=',False)], limit=5)
        .mapped(('name','table_id','customer_count','state')))
print(env['restaurant.order.course'].search([], limit=5)
        .mapped(('index','fired','fired_date')))
# launch UI:  browse /pos/ui/<config_id> on a restaurant config → FloorScreen
```

## Open Questions (verify in code)

  per-quantity vs per-seat) and how it materializes new `pos.order` rows on sync.
- The **transfer/merge-between-tables** flow: how `parent_id` grouping and
  `table_id` reassignment persist and are conflict-resolved across two offline
  devices (same `uuid`).
- How **course firing** drives the actual kitchen/bar printout — the
  preparation-change diff (`pos.session._set_last_order_preparation_change`) →
  printer path lives in the parent module / hardware proxy.

  with external payment terminals and which payment add-ons support it.
